## 二、每个环节谁在做、是不是模型

这是本项目最容易被问到的问题，直接摊开讲：

| 环节 | 谁在做 | 是不是模型 | 说明 |
|---|---|---|---|
| 菜谱解析（设备/时长/温度/依赖） | 正则规则为主 + LLM 兜底 | **半模型** | 规则毫秒级完成；规则拿不到设备参数的菜（约 8 道占位菜）走 LLM 补全，结果落盘缓存 |
| **调度语义先验**（趁热/可放/可备菜/合炉） | **LLM（离线抽取，在线读缓存）** | ✅ | 每道菜的"调度语义"只能靠语义判断，求解器结构上做不了。离线抽取一次，在线 0 延迟 |
| **目标塑形**（用户口语 → 多目标权重） | 规则快速路径 + LLM 精化 | ✅ | "一起上桌"→ 同出锅权重拉满；"赶时间"→ 总时长权重拉满 |
| **策略择优**（在 5 条策略里选） | 求解器执行 + LLM 提议/反思 | ✅ | 求解器负责"算"，模型负责"选哪条路 + 不达标时怎么调" |
| 排程求解（放置/冲突/依赖） | **三轨取优**：贪心启发式 + CP-SAT + **精确模型（RCPSP-Batch-Lag）** | ❌ 纯代码 | 模型的产物（权重/先验/策略）驱动它，但它本身是确定性求解器。精确轨实测让线上总时长 **−26.5%** / 出锅差 **−45.4%** / 连续手动 **−42.8%** |
| **动态重排姿态仲裁** | **LLM 仲裁 + 规则兜底** | ✅ | 临时加菜/设备故障时，模型决定"最小扰动 / 重新对齐 / 保热优先" |
| 重排求解（冻结 + 重排） | 求解器 | ❌ 纯代码 | 已完成步骤硬冻结，绝不推翻 |
| 对话 / 选菜 | LLM | ✅ | 自然语言选菜、解释排程 |
| 通知文案 | **LLM 语境化 + 模板兜底** | ✅ | 模板零延迟保底；开启后由模型生成口语化提醒 |

**关键设计：模型参与的是决策，不是在线算力。**
语义先验、参数补全、策略结论一律**离线算好落盘**（`scripts/warm_cache.py`）；
在线排程只读缓存，模型决策 **0 延迟、0 网络依赖**；
需要演示完整 Agent 能力时再打开在线决策，且有超时 + 熔断兜底。

> 这条约束原先是为"远端中转站一次往返约 2.5s、而赛题要求初始排程 <5s"设的。
> 现在默认换成**本地 Ollama**（热态约 0.5s）之后它依然成立 —— 本地模型同样会
> 因为"权重被换出显存"而变慢（重载 ~10s），把在线路径压成"必答题"仍然是不划算的。

### 模型接入：默认本地 Ollama

默认档位是**本地 Ollama**，免密钥：

```bash
ollama pull qwen2.5:7b     # 7.6B / Q4_K_M，约 4.7GB
ollama list                # 确认已下载（名字要和 FT_LLM_MODEL 完全一致）
```

| 变量 | 默认 | 作用 |
|---|---|---|
| `FT_LLM_PROVIDER` | `ollama` | `ollama`=本地（免密钥）；`openai`=任意 OpenAI 兼容端点（需密钥） |
| `FT_LLM_BASE_URL` | `http://127.0.0.1:11434/v1` | 端点（末尾斜杠会被去掉） |
| `FT_LLM_MODEL` | `qwen2.5:7b` | 模型名。**设了它就是最高优先级**，会覆盖设置页里存的值 |
| `FT_LLM_API_KEY` | 空 | **本地档留空是正常的**；远端档留空 = 完全离线 |

> ⚠️ **端点与模型名是跨 provider 共用的，改档必须成套改。**
> 只把 `FT_LLM_PROVIDER` 改成 `ollama`、却留着远端的 `BASE_URL`/`MODEL`，
> 请求会带着远端模型名打到本机 11434，Ollama 返回 `404 model not found`，
> 而所有调用点都**静默降级** —— 现象是"换成本地模型之后 AI 完全不工作"，
> 日志里没有任何报错。启动时会有一条 warning 兜底（"端点不像本地地址"）。
>
> ⚠️ **容器里用不了宿主机的 Ollama**：容器内的 `127.0.0.1` 指向容器自身，
> 要用宿主机的 Ollama 得换成 `host.docker.internal:11434`，并让 Ollama 监听
> `0.0.0.0`。镜像里也没有模型权重。所以 Dockerfile 默认 `FT_LLM=off`。

### 在界面上切换接入方式 / 换模型（设置 → 模型接入）

不用改环境变量也能切换：打开 Web 界面顶栏的 **设置**，第一个子页签就是「模型接入」。

| 控件 | 作用 |
|---|---|
| **接入方式** | `本地 Ollama（免密钥）` / `远程 OpenAI 兼容端点（需密钥）`。选项由后端下发，前端不自己写一份 |
| **远程接口地址** | 仅远程档可见。必须 `http(s)://` 开头 |
| **远程 API Key** | 仅远程档可见，`password` 框。**留空 = 不修改** |
| **本机已下载模型** | 仅本地档可见，列的是本机 `ollama list`（走 `GET /api/tags`） |
| **模型 ID** | 两档共用。切换接入方式时自动回填**该档上次用的模型** |

点「保存模型」才生效；只拨下拉**不会**改后端配置。两种接入方式**各记一份模型**，
来回切不会互相覆盖。

> 🔒 **密钥只存不回传。** `/api/model_settings` 是**无鉴权**的（本机演示、发布出去的
> 公开链接都能读），所以响应里只有 `remote.api_key_set: true/false`，**没有**
> `api_key` 字段，页面上也永远不回填密钥框。相应地密钥框**留空 = 保持原值**，
> 不是清空 —— 否则用户每保存一次就抹掉一次自己的密钥。
> `data/llm_settings.json` 既不进 Docker 镜像（`.dockerignore`）也不进发布目录
> （`scripts/sync_publish.py`）。

模型名是**三层优先级**，界面会明确显示当前生效的是哪一层：

```
FT_LLM_MODEL（真实环境变量）  >  data/llm_settings.json（设置页写盘）  >  provider 内置默认
```

| 界面显示 | 含义 |
|---|---|
| `环境变量` | 被 `FT_LLM_MODEL` 钉死，**设置页改不动**（输入框禁用，并给出该去哪个文件删哪一行） |
| `设置文件` | 用的是你在设置页存下来的值 |
| `内置默认` | 谁都没设，用的 provider 默认模型 |

同理，`FT_LLM_PROVIDER` 会钉死**接入方式**（下拉禁用），但**不**影响"在同一个接入方式里换模型"。

保存成功后会**顺带重置熔断器与在线闭环闸门**，并**重算超时/探测预算的默认值** ——
否则会出现"明明换成了更快的模型，闭环还是被挡着"（熔断器记的是上一个模型的失败）。
保存时若该模型不在本机，界面会提示但**不阻断**（可能只是想先把配置写好）。
远程档不报"本机有没有这个模型" —— 那个判据对远程没有意义（模型在中转站那边）。

## 三、环境变量（全部可选）

| 变量 | 默认 | 作用 |
|---|---|---|
| `FT_LLM_PROVIDER` | `ollama` | 模型服务提供方：`ollama`=本地（免密钥）/ `openai`=兼容端点（需密钥） |
| `FT_LLM_BASE_URL` | `http://127.0.0.1:11434/v1` | 端点 |
| `FT_LLM_MODEL` | `qwen2.5:7b` | 模型名。**设了它就是最高优先级**，会覆盖设置页里存的值 |
| `FT_LLM_API_KEY` | 空 | `openai` 档才需要；**本地档留空是正常的** |
| `FT_LLM` | `on` | 全局模型开关。`off` = 完全离线（评测/无网环境推荐） |
| `FT_AGENT_LLM` | `on` | 排程决策是否在线调用模型（目标塑形/策略提议/反思/重排仲裁） |
| `FT_NOTIFY_LLM` | `on` | 通知是否走 LLM 语境化（失败自动回落模板） |
| `FT_AGENT` | `on` | `off` = 关闭 Agent 闭环，退回单策略求解器（对照实验用） |
| `FT_AGENT_BUDGET` | `3.6` | 闭环总预算（秒）。超预算立刻收敛，绝不硬等模型 |
| `FT_LLM_TIMEOUT` | `30`（本地）/ `20`（远端） | 单次模型调用超时（秒）。**本地给 30s 是因为权重被换出后重载要 ~10s**，给 3s 会把正常模型判成故障；**远端给 20s 是因为实测中转站往返 2.3~2.9s，旧的 3s 贴着线**。放大它不拖慢排程：`chat()` 取 `min(调用方传入的 timeout, TIMEOUT*3)` |
| `FT_LLM_CB_THRESHOLD` | `3` | 连续失败几次后熔断（无网环境避免每次请求干等） |
| `FT_LLM_CB_COOLDOWN` | `120` | 普通失败（超时/5xx）的熔断冷却（秒） |
| `FT_LLM_CB_QUOTA` | `1800` | 额度类失败（HTTP 429）的熔断冷却（秒），且**立即**熔断不等阈值 |
| `FT_WARM_LLM` | `on` | 启动时是否探测一次模型可用性（让熔断状态在服务接客前落定） |
| `FT_WARM_LLM_BUDGET` | `60`（本地）/ `1.5`（远端） | 启动探测预算（秒）。**本地给 60s**：Ollama 首次调用要把权重读进显存（≈10s），1.5s 必然失败 ⇒ 每次启动自我熔断 |
| `FT_CPSAT_GAP_COEF` | `0.25` | CP-SAT 目标里出锅差的放大系数 |
| `FT_EXACT` | `on` | **精确模型轨总开关**（`off` 回到旧的"贪心 + CP-SAT"双轨） |
| `FT_EXACT_BUDGET` | `1.5` | 精确轨时间预算（秒）。闭环还会用 `min(1.5, 剩余预算)` 再收一次，保证不破 5s |
| `FT_CPSAT_WORKERS` | `1` | CP-SAT 搜索线程数。**默认 1 = 结果可复现**；调大换吞吐但同一输入两次可能给不同计划 |
| `FT_EXACT_WORKERS` | `1` | 精确模型搜索线程数，同上 |
| `FT_FLAG_CACHE` | `on` | 开关类环境变量的请求级缓存（省掉每次排程 11.7 万次 `os.environ` 读取）。`off` = 退回每次重读 |
| `FT_EXACT_SLACK` | `15` | 精确轨 ε-约束的松弛量。**给 0 会把对齐出锅时刻的余量也掐死**（实测出锅差 3 → 44 min） |
| `FT_EXACT_PREP` | `both` | 备菜口径：`both` 两个变体取优 / `off` 严格跟随策略（口径审计）/ `on` 只用备菜变体 |
| `FT_ALIGN_SLACK` | `0` | 出锅对齐时允许超出最晚出锅时刻的分钟数（实测 0 最优） |
| `FT_REPLAN_BUDGET` | `2.5` | 动态重排的闭环预算（秒），比赛题 3s 优秀线留足余量 |
| `FT_ALLOW_RECIPE_WRITE` | `on` | 菜谱库增删改查开关。`off` = 写接口返回 403、前端隐藏入口。写操作只落 `data/recipes_user.json`，**官方 CSV 永不被改写** |

> 熔断机制：连续失败达阈值后，模型调用在一段时间内直接返回、走规则兜底。
> 额度耗尽（429）单独处理 —— 这类失败短期内重试没有意义，直接冷却半小时。
> 这保证在**没有外网**的评审机上，性能分不会被网络超时吃掉。

### 5.1 消融实验：每一层各值多少

同一 seed、同一菜名抽样序列，逐档关模块（`python -m scripts.ablation 50 42`）。
三档的数字在上面的生成块里，这里只说**怎么读**：

**读法**：单独关掉任何一层，总时长都会明显变长；两层同时开着才是最好的一档。
**Agent 闭环决定"走哪条路"，精确模型决定"这条路能走多好"，二者缺一不可** ——
不是"各自 −15%"的叠加，而是协同：精确模型的备菜变体只有在策略集保留了
`prep_first` / `compress` 时才有意义。（消融表与上表来自同一天的两次独立运行，耗时存在秒级抖动。）

原始数据：`data/ablation_report.json`。

> **为什么数字比更早的快照（92% / 73.5 min）差了一点？** 因为 L1 修了一处正确性缺陷：
> 官方 100 道菜里有 12 句复合句（形如"…放入烤箱第3层，选择'开始烹饪'按键…烘烤结束，取出晾凉"）
> 的真实设备作业，曾被"晾凉/冷却/解冻"这类等待词**整句抹掉**。修复后解析正确性从
> **95/100 道菜有加热设备提升到 99/100**，但问题本身也变得更难更真实 ——
> 优秀率 92% → 90%、总时长 73.5 → 74.8 min。**这是一个正确的权衡：宁可分数低一点，不要靠丢任务刷指标。**

### 5.2 最优性证据（`python -m scripts.verify_model 60 11`）

| 配置 | 总时长 | 出锅差 | 连续手动 |
|---|---|---|---|
| 关第三轨 | 72.6 | 2.66 | 38.1 |
| **开第三轨（默认）** | **61.0** | **2.04** | **24.2** |
| 精确模型上限参考 | 58.4 | 2.65 | 21.1 |
| **第三轨净收益** | **−15.9%** | **−23.2%** | **−36.5%** |

- 求解状态 **`OPTIMAL` 60/60**；逐例判定（开轨 vs 关轨）**更优 30 / 打平 30 / 更差 0**；
- 冲突 0 / 依赖违规 0 / **`总时长 < 下界` 0 例**；
- 交付版与"精确模型上限参考"的差距 **≤5%**（61.0 vs 58.4）—— 差额来自 Agent 闭环的
  时间预算与策略集约束：闭环必须在 `FT_AGENT_BUDGET` 内收敛，而"上限参考"是
  离线不限时直接解该模型。**逐例"更差 0"** 才是要守的判据（见 §5.1 的读法）。

### 5.3 用户语义 → 目标权重 → 可测量的不同权衡

**同一批菜、同一套求解器，只改用户输入**（`objective.shape_policy` 把它翻成多目标权重）。
菜组：竹荪排骨汤 + 广式叉烧 + 豆沙手撕包 + 清蒸鲈鱼 + 土豆焖饭。

| 用户输入 | 总时长 | 出锅差 |
|---|---|---|
| （无） | **72 min** | 13 min |
| "家里来客人，希望所有菜一起上桌" | 91 min | **2 min** |
| "赶时间，越快越好" | **72 min** | 13 min |

读法：**"一起上桌"用 +19 分钟总时长换回了 11 分钟出锅差**（13 → 2），
这正是"多目标之间可以按用户意图取舍"的直接证据 —— 而它不是靠改代码实现的，
只靠一句话。

> ⚠ 这个效果**不是每道菜组合都能看出来**：如果求解器在该组合上本来就能同时逼近
> 两个目标，三种输入会给出同一份计划（实测另外两组 4–5 菜就是如此）。
> 判据是"**输入能改变权重与策略**"，不是"每次都必须给出不同的数字"。
> 离线档（`FT_AGENT_LLM=off`）走 `rule_pick` 规则快速路径；在线档由模型精化。

### 5.4 动态重排

`python -m scripts.demo_dynamic`（4 道菜，硬冻结已完成 6 步，临时加 1 道）：

| 阶段 | 总时长 | 出锅差 | 冲突 | 依赖违反 |
|---|---|---|---|---|
| 初始排程 | 48.0 min | 2.0 min | 0 | 0 |
| **重排后（加菜）** | **64.0 min** | **3.0 min** | **0** | **0** |

- **最小扰动**：硬冻结的 6 步**一步未动**（`notice.已完成步骤保留 = 6`）；
- 新增菜品必然增加总工作量，所以"总时长不增"不成立 —— 可验证的保证是
  **「已完成步骤零变动」+「不劣于串行追加基线」**两条（`/reschedule` 的 `pareto` 字段）；
- "蒸箱故障"时计划里不再出现蒸箱任务（改走灶具），不会 500。

### 5.5 模型不可用时的表现

实测中转站返回 `429 今日 token 额度已用完` 后，上述全部指标与耗时**没有任何变化**
（离线缓存 + 规则兜底），系统对模型可用性零依赖。

**但"第一个请求"是唯一的例外，必须单独说清楚。** 稳态 ~163 ms 是**熔断器已经打开之后**
的数字；如果预热探测没能把熔断器落定，第一个真实请求就要自己攒够失败次数 ——
每次调用各等一次超时。实测（默认档，模型端**能连通但单次响应 2.3~4.0 s**）：

| | 服务端耗时 | LLM 调用 | 熔断 |
|---|---|---|---|
| 第 1 次请求（修复前） | **6735 ~ 7813 ms** | 2 次（各等满超时） | 请求内才打开 |
| 第 2 次起 | **150 ~ 228 ms** | 0 | 已打开 |
| 第 1 次请求（修复后） | **154 ms** | 0 | 启动时已打开 |

根因有两层，都藏在"探测"这一步：① 探测走的是纯文本 `llm.chat`，而 Agent 实际用
`chat_json`（请求体不同，可能一个通一个不通）；② 判据被当成"连不连得上"，
而模型端**连通但慢**（2.3~4.0 s > 默认超时 3.0 s）时探测会报"可用"。
现在探测改为 **`chat_json` + 1.5 s 紧预算**（一次排程发 1~2 次调用，单次 >1.5 s
本来也落不进 <5 s），探不通就在启动阶段预先熔断。回归用例：
`tests/test_warmup_probe.py`（6 项，已做变异测试确认能拦）。

## 九、部署

最短路径：

```bash
docker build -t cooking-agent .
docker run -p 8000:8000 cooking-agent
```

容器内默认 `FT_LLM=off`：不依赖外网也能跑完整闭环（策略择优 + 离线语义先验）。
若已预热过缓存，把 `data/llm_agent_cache.json` 一起打进镜像即可让模型产物生效。

### 9.1 部署到云服务器（systemd，模型开箱即用）

```bash
bash deploy/pack-server.sh            # 产出 dist/cooking-agent-server.tar.gz
#  打包前会强制同步 publish/ 并做 fail-closed 校验（出厂层凭据 / 无本机状态 / 脚本 LF）

scp dist/cooking-agent-server.tar.gz root@<IP>:/tmp/
ssh root@<IP> 'mkdir -p /opt/cooking-agent && tar xzf /tmp/cooking-agent-server.tar.gz -C /opt/cooking-agent'
ssh root@<IP> 'bash /opt/cooking-agent/deploy/server-setup.sh'   # 装依赖 + systemd + 自检
```

或在本机一步到位：`HOST=<IP> bash deploy/upload.sh`（会先调 `pack-server` 再上传部署）。

**模型默认是开的** —— 出厂层 `app/agent/llm_defaults.json` 自带接入配置与凭据，
解包即可用上 AI 对话 / 通知润色 / 重排姿态仲裁，不需要再填任何 Key。
想跑离线档：`WITH_LLM=0 bash deploy/server-setup.sh`（排程质量与耗时不变）。

> ⚠️ systemd 那份 unit 在 2026-10-09 之前写的是四个 `off`，会让出厂层凭据完全用不上，
> 而界面只显示「模型已关闭」、排程与耗时一切正常 —— 没有任何报错能指向"只是开关关着"。
> 现在默认开，并有护栏钉住（`tests/test_pack_server.py`）。

完整的部署说明（环境要求 / 配置项 / 离线运行 / 故障排查 / 性能验收）见
