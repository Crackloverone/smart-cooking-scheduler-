### 1. 新增 L1 缺陷：等待词整句抹掉真实设备作业（本轮最大发现）

`SOAK` 词表（浸泡/泡发/解冻/静置/**晾凉/冷却/沥水**）命中后整句降级为 `WAIT`，
于是 `"…放入烤箱第3层，选择'开始烹饪'按键…烘烤结束，取出晾凉"` 里的**真实烤箱作业被一起抹掉**。
官方 100 道菜里 **12 句中招**，其中 6 句是"开始烹饪 + 烘烤结束 + 取出晾凉"这种标准写法。
极端例子：`法式羊排` 全菜只有 1 步，被抹掉后**整道菜没有任何设备任务**。

修法（保守，只放行信号明确的三类，`recipe_parser.py` v2.4）：
1. 同句带 `LOAD_START_VERBS`（开启电源/开始烹饪/屏幕提示）⇒ 是设备程序启动，不是等待；
2. 同句**点名加热设备 + 有显式时长** ⇒ 真实设备作业
   （反例保护：`"温水浸泡4小时"` 没有设备名，不被放行，仍归等待 —— 守住糯米烧麦那条）；
3. **灶具** + `ACTIVE_COOK` ⇒ 灶前手上活，末尾"冷却/沥水"只是收尾
   （只对灶具放行：烤箱/蒸箱的 `"烘烤结束…取出晾凉"` 是纯收尾，必须保持等待）。

效果：**有加热设备的菜 95/100 → 99/100**（唯一剩下的 `披萨面团` 只做面团，本身不含烹饪）。
回归用例：`test_soak_word_does_not_erase_a_real_device_task`（正反例各 3 条）+
`test_official_library_every_dish_has_a_heating_step`。

**代价（诚实记录）**：问题变难也更真实，优秀率 92% → **90%**、总时长 73.5 → **74.8**。
**宁可指标低一点，不要靠丢任务刷分。**

### 新增的两个探针（都在 `scripts/`，零第三方依赖）

- **`ui_probe.mjs`（jsdom，11 节 95 项）** 验**逻辑**：选择器 / 字段名 / 事件绑定 / 点了有没有反应。
  - ⚠️ **ESM 的 `import "jsdom"` 不认 `NODE_PATH`** —— 必须用
    `createRequire(<workspace>/noop.js)` 显式指解析根，否则脚本放项目里永远找不到 jsdom。
  - ⚠️ 页面的 `<script>` 在 **JSDOM 构造期就同步执行**，`fetch`/`alert`/`AudioContext`/`scrollTo`
    必须在 **`beforeParse`** 里补，构造完再赋值已经晚了（首屏直接 ReferenceError）。
  - 用 `window.__apiLog` 记录界面真实发出的每个请求 —— 排查"点了没反应"第一个要回答的
    就是"它到底有没有发请求、发了什么、后端回了什么"。
- **`ui_layout_probe.mjs`（真 Edge + CDP，65 项）** 验**排版**：压扁 / 裁切 / 横向溢出 / 重叠。
  - **`agent-browser` 没装，但不需要**：Windows 自带 Edge，CDP 手搓即可 ——
    **Node 22 内置 `WebSocket`**，零 npm 依赖。`--headless=new --remote-debugging-port`
    + `GET /json/list` 拿 `webSocketDebuggerUrl` + `Runtime.evaluate{awaitPromise:true}`。
  - jsdom **没有排版引擎**，上面这一类它一律看不见 ⇒ 两层缺一不可。

### 静态护栏 `tests/test_web_ui.py`（7 项，进 pytest，不需要后端）

无外链 / 内联处理器全部有定义 / `getElementById` 目标存在 / 行模板带 `data-name` /
`agentPlan` 不再遍历 DOM 点击 / `.sbar` padding 严格为 0 且有省略号 / `seekT` 有空值保护。
**做过变异测试**（注入 5 种缺陷确认都被拦）。其中 padding 那条第一版写成
`padding\s*:\s*0(?:\s|;)`，被 `padding:0 8px` 蒙混过关（`0` 后就是个空格）—— 已收紧为
`padding\s*:\s*0\s*(?:;|$)`。

### 三条方法论教训（比 bug 本身值钱）

1. **探针自己会说谎。** "历史记录 0 条"挂了一轮，实为**假失败**：第 2 节已进过该视图，
   等待条件命中了**陈旧 DOM**，新请求还没回来就断言了。⇒ **等待条件必须依赖新渲染的内容**，
   断言前先清空容器。同理 `jsErrors.length = 0` 必须在**触发之前**清（旧写法放在 change 之后，
   把 B2 的报错当场擦掉，害它溜过一轮）。
2. **"看着像 bug、其实不是"必须实测。** 悬浮助手发送按钮用了**样式表里根本不存在的**
   `class="btn"`（只有 `.btn-arrow`），按 CSS 推导会落到 `button{width:100%}` 上把输入框挤成
   0 宽 —— 真 Edge 实测却是 **194px / 132px 完全正常**，因为输入框 `flex:1 1 0%` 带
   `min-width:auto`，min-content 宽度成了下限。**光读 CSS 会得出错误结论。**
   ⇒ 结论：`.btn` 是死类名，当前无害但**脆弱**（谁给 `.btn` 加 width 就可能挤没输入框），本轮不改只记录。
3. **修 bug 的第一版自己也会错。** B1 第一版写成 `selected.push(x||{id:n,name:n})`，
   而 `META` 里的原始对象**没有 `id` 字段** ⇒ 去重 `s.id===n` 永远匹配不上，
   筛选状态下选 3 道只留 2 道。**这个坑是探针自己抓出来的** ⇒ 改完必须重跑探针，
   而且探针要覆盖"筛选状态"这类**非默认状态**。

## 第三轮：从 KPI 截图反查出「首个请求慢」的真因

用户发来 KPI 卡片截图（总时长 34 / 出锅差 0 / 利用率 39% / 冲突 0 / **耗时 5414.1ms**）
问"如何根据这些参数判断程序的好坏"。**5414.1ms 越过了 5000ms 优秀线**，顺着这条线查下去
挖出一个真 bug。

### 实测基线（同一台机器，`/schedule`）

| 场景 | 服务端耗时 | LLM 调用 | 熔断 |
|---|---|---|---|
| 离线档（`FT_LLM=off` 等四个 off） | 冷启动 150.6 / 热态 147.9~243.0 ms | 0 | — |
| **默认档·第 1 次请求（修复前）** | **6735 ~ 7813 ms** | 2（各等满超时） | 请求内才打开 |
| 默认档·第 2 次起 | 150 ~ 228 ms | 0 | 已打开 |
| **默认档·第 1 次请求（修复后）** | **154.3 ms** | 0 | 启动时已打开（reason=warmup） |

### 根因（两层，都在"启动探测"这一步）

1. **探测路径与 Agent 不一致**：`_warmup()` 用纯文本 `llm.chat([...ping])` 探，
   而 Agent 实际走 `llm.chat_json(..., json_mode=True)`。请求体不同，可能一个通一个不通。
2. **判据错了**：被当成"连不连得上"，而真实情况是**模型端能连通但很慢** ——
   实测 `potatoya.cn/pro100x/v1` 单次响应 **2.3~4.0 s**，而 `FT_LLM_TIMEOUT` 默认 **3.0 s**。
   调用被超时截断 → 判为失败；但探测用 3s 预算偶尔能"通过" → 报"模型可用" →
   第一个真实请求照样白等 1~2 次超时。

**正确判据是"能否在预算内返回"**：一次排程发 1~2 次调用，单次 >1.5s 本来也落不进 <5s，
所以探测用 **`chat_json` + 1.5s 紧预算**，探不通就在启动阶段 `force_open`。

### 修复

`app/api/main.py::_warmup()` 第 3 步：`llm.chat` → `llm.chat_json(..., timeout=min(TIMEOUT, 1.5))`，
`cache_key` 留 None（探测结果不落盘，免得污染语义先验缓存）。
**首请求 6735~7813 ms → 154 ms（约 44×）**，稳态数字完全不变。

### 新增回归 `tests/test_warmup_probe.py`（6 项，已做真实变异测试）

探测走 chat_json 而非纯文本 / 预算 ≤1.5s / 探测失败必熔断 / 模型可用时不误熔断 /
探测不落盘 / `FT_WARM_LLM=off` 时完全不探测。
变异测试注入 4 种缺陷（预算放松到 3s、失败不熔断、落盘污染、改回纯文本）**全部被拦**。

### 教训

**"稳态 131ms" 是熔断器打开之后的数字，不是"第一个请求"的数字。** 这类 bug 功能测试
全绿、只有首请求慢 40 倍，极难发现 —— 判据必须写清"在什么前提下测的"。
另外：**`FT_LLM_TIMEOUT` 必须大于模型端真实延迟**，否则调用被静默截断、白白走规则兜底；
但若模型单次响应就 >1.5s，调大超时也没用（1~2 次调用必然破 5s 线），此时应直接用离线档。

### 做法（`app/web/index.html`）

- `#v-plan.active{height:calc(100vh - var(--chrome));display:flex;flex-direction:column}`，
  `--chrome` 由 `fitChrome()` 用 `nav.offsetHeight + computed top` **实测**写入。
- 三列 `align-items:stretch` 等高，**每列恰好一个"会长大的"模块**：
  左 `#recipeList` / 中 `#gantt` / 右 `#notes`，`flex:1;min-height:0` 由它内部滚动。
- 甘特图画布 `min-width:max(100%, min(1200px, 110 + MAX_T*34))` —— 计划越长画布越宽，
  超出就出横向滚动条；短计划铺满容器，不为滚动而滚动。
- `#gantt` 里只放 `.gantt-inner`（nowline + 泳道同层，`seekT` 的 px 基准才对得上）；
  提前准备提示条挪到 `#gantt` **外面**（`#prepBanner`），否则会跟着时间轴被推走。
- 泳道标签 `position:sticky;left:0;z-index:6` 冻结；**`.swim` 的 overflow 必须是
  `clip` 不能是 `hidden`** —— `hidden` 会让 `.swim` 自己变成滚动容器，sticky 被锁死。

### 三个只有真内核才看得见的坑

1. **CSS 选择器撞车（花了最久）**：给三列加 `gap:14px` 的规则写成 `#v-plan .grid3>div`，
   而**中列那张卡片本身就是 `.grid3` 的 div 子元素** —— 卡片内部凭空多出 7×14=**98px**
   行距，正好把甘特图那 **97px** 余量吃光。症状：`flex:1` 的甘特区怎么都不长高，
   但 `getComputedStyle` 里 `flex-grow` 明明是 `1`、`flex-basis` 是 `0%`。
   **诊断路径**：`card.clientHeight − padding − Σ(子块 offsetHeight + margin)` = 97 ≠ 0
   → 说明余量存在却没被分配 → 逐项对账才发现漏算了 `row-gap`。
   修复：`#v-plan .grid3>div:not(.card)`。
2. **视图切换按钮被撑成整行**：全局 `button{width:100%}`（给 CTA 用的）让 `.vbtn`
   在 flex 行里拉成一条 430px 黑条。修复：`.vbtn{width:auto}`。
3. **悬浮球压住主按钮**：「已选」搬到右列后，右下角 fixed 悬浮球正好盖住「生成排程」
   （重叠 56×42px）。修复：排程页底部统一留 66px + 悬浮球在排程页缩到 48px
   （**整页统一留白而不是只给右列**，三列底边才继续对齐）。

### 教训

- **CSS 排查要看"数字对账"，不要看"属性对不对"**：`flex-grow:1` 明明生效却不生长，
  说明问题不在 flex 属性，而在"可分配空间到底是多少"。把
  `容器内容盒 − Σ子块外部尺寸` 算出来，差值不为 0 才是真线索。
- **`.grid3>div` 这类"容器子元素"选择器极危险**：同层里混着"包装用的 div"和
  "内容卡片 div"时，一定会连带命中。加 `:not()` 或者给包装层单独一个类。

## 第五轮 播放条排版：控件换皮 + 行高统一

### 先量后改：真内核量出两个真问题

```
播放条: [{"k":"playBtn","w":73,"h":33},{"k":"tSlider","w":701,"h":16},{"k":"tLabel","w":36,"h":20}]
播放条样式: tSlider {bg:rgb(255,255,255), radius:0px, shadow:none}   ← Chromium 原生皮肤
```

共同调用；已播放段 = 纯 CSS 渐变 + JS 写入的 `--p`。读数补
`font-variant-numeric:tabular-nums` + 固定宽度（否则 `t=0分 → t=100分` 整行会抖）。

## 第六轮 视图切换按钮：可读性 + 尺寸

用户发来截图（红圈标注「设备视图 / 菜品视图 / 人力轨道」一行）：
"这三个按钮太小了，拉长点宽度，还有在没选择的前提下字体和背景融合了看不出来"。

### 后一句是**真 bug**，不是主观感受

真内核量出对比度（WCAG）：

| 按钮 | 改前 字色/底/对比度 | 改后 | 尺寸 |
|---|---|---|---|
| 设备视图（选中） | `#fff`/`rgb(17,17,17)`/**18.88** ✅ | 不变 | 66×26 → **92×31** |
| 菜品视图（未选中） | `#fff`/`rgb(253,253,253)`/**1.02** ❌ | `#111`/同底/**18.53** ✅ | 同上 |
| 人力轨道（未选中） | 同上 **1.02** ❌ | **18.53** ✅ | 同上 |

**1.02 = 同色 = 完全看不见**（AA 正文线 4.5）。

### 两个根因：都是"全局样式泄漏进组件"

1. **白字压白底**：全局 `button{color:#fff}` 是给橙色 CTA 用的，`.vbtn` 只覆盖了
   `background`（浅色毛玻璃）**没覆盖 `color`** ⇒ 继承白色 ⇒ 字消失。
   同一个泄漏还带来橙色 `box-shadow` 光晕（也没清）。
2. **hover 抢成主色**：全局 `button:hover` 特异性 **(0,1,1)** > `.vbtn` **(0,1,0)**，
   只要 `.vbtn` 不写自己的 `:hover`，鼠标划过未选中的按钮就变主色橙底，
   界面上同时出现**两个"看起来是选中"的按钮**。

**特异性算术要记牢**：`.vbtn:hover` = 类+伪类 = **(0,2,0)**，压过 `button:hover` (0,1,1)；
`.vbtn.active:hover` = (0,3,0) 最稳。`.vbtn.active`(0,2,0) 与 `.vbtn:hover`(0,2,0) 平手，
靠源序（`.active` 在后）决定 —— 所以显式补 `.vbtn.active:hover` 更保险。

### 探针新增两类检查（尺寸断言永远抓不到"看不清"）

- **文字对比度**：WCAG 公式；背景必须**逐层 alpha 合成到不透明**再比 ——
  按钮是半透明毛玻璃，直接拿 `backgroundColor` 比会得出错误结论
  （合成前 `rgb(255,255,255)` vs 合成后 `rgb(253,253,253)`）。
- **真实 hover**：`Input.dispatchMouseEvent`。

### 两个"检查自身失效"的坑（都已封死）

1. **`transition` 会让立刻读取的样式是"起始值"**：`button` 上有 `transition:all .3s`，
   派发 hover 后马上读 `getComputedStyle` 拿到的是过渡起点 ⇒ "没变橙" ⇒ **假通过**。
   必须 `sleep(500)` 等过渡跑完。（我一开始就是这么被骗的，还差点得出
   "hover 不会变橙"的错误结论。）
2. **合成鼠标事件可能没生效**：同样假通过。额外加一条
   「hover 真的被触发」断言，用 `querySelectorAll(':hover')` 反查。

**纪律：检查静默失效比 bug 本身更危险 —— 它会让你以为已经守住了。**

### 这条纪律立刻抓到自己的一个假通过

`.vbtn` 的 `color` 断言原本写成子串 `"color:" in css`，而
`transition:...,color .2s ease` 与 `border-color:` 里都含 `color:` ——
"删掉 color 声明"的变异**不被捕获**（14/15）。收紧为**声明级**
`re.search(r"(?:^|;)color:", base)` 后才真正守住。

### 变异脚本自己报出过期条目

改宽 `#v-plan .vbtn` 后，旧变异串 `...font-size:11px;padding:4px 10px;width:auto}`
在文件里出现 **0 次** → 脚本打 `[跳过]` 而不是静默通过。**这就是 `count==1` 检查的价值**：
变异串过期 = 那条护栏其实已经没人验了。

### 最终

- `ui_layout_probe.mjs` 92 → **98 项**（+6），三档视口 98/0
- `tests/test_web_ui.py` 15 → **17 项**（+2）
- `pytest` 95 → **97 项**；`_mutate_web_guards` 11 → **15 条，15/15 捕获**
- 新增 `data/ui_tabs_shot.png`（按钮 3× 局部图）

### 教训

- **组件必须把"会被全局规则泄漏进来的属性"显式声明**：`color` / `box-shadow` /
  `:hover`。`background` 覆盖了不等于组件安全。
- **半透明毛玻璃上算对比度必须做 alpha 合成**，否则数字全是错的。
- **`transition` 存在时，读样式前要等**；否则所有 hover/focus 断言都是假的。
