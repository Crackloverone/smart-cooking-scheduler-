## §1 修复「进程启动后第一次排程被劣化」（真 bug）

### 1.1 怎么发现的

重打 `dist/cooking-agent-windows.zip` 后做冒烟，同一个 4 菜组合：

```
plan_recipes 第 1 次: Γ= 32.0  T= 83.0
plan_recipes 第 2 次: Γ=  3.0  T= 57.0
```

第 1 次和第 2 次跑的是**同一份代码、同一组菜**，只有"第几次"不同。

### 1.2 根因

`app/agent/orchestrator.py::_run_inner` 的顺序是
LLM 塑形 → LLM 提议 → 贪心枚举 → **精解轨**，而精解轨的预算来自"剩余时间"：

```python
left = max(0.0, time_budget - (time.time() - t0))
bud  = solver_budgets(len(recipes), left * 0.75)
```

在线时 LLM 两次调用实测吃光 `time_budget=3.6s` ⇒ `left ≈ 0`
⇒ `solver_budgets(4, 0)` 两条精解轨全 `use_*=False`
⇒ **整个精解段被跳过，交付贪心解**。

在线闸门（`FT_LLM_ONLINE_GATE`）是在本轮**结束后**才落下的
⇒ **每次进程启动后的第一次请求都中招**。

逐步定位证据：

```
solve_exact 生产预算 1.5s:  allow_preprocess=True  -> Γ=3.0 T=57.0 status=OPTIMAL
engine.schedule 只开精确轨:                        -> Γ=3.0 T=57.0 sc=277.5
生产管线 plan_recipes:                             -> Γ=32.0 T=83.0 sc=2054.0
orchestrator.run(use_llm=False):                   -> Γ=3.0 T=57.0（solver 胜出）
```

⇒ **不是求解器不行，是 orchestrator 层根本没让它跑。**

### 1.3 修复：预算从**后往前**分配

| 环节 | 预算 | 默认 3.6s 下 |
| --- | --- | --- |
| 精解轨 | `_solver_reserve(n, use_cpsat)` | **0.761s** |
| LLM（塑形 + 提议） | `llm_quota = time_budget − reserve − _ENUM_RESERVE` | 2.239s |
| 策略枚举（6 条贪心快评） | `_ENUM_RESERVE` | 0.600s |

- `app/scheduler/dispatch.py` 新增 `min_pool_for_tracks()`：**二分调用
  `solver_budgets` 本身**反解"要让某轨开起来，池至少要多少"。不照抄
  `0.45/0.55` 公式（两处各写一份必然漂移）。逐轨分别求再取 max。
- `app/agent/orchestrator.py` 新增 `_solver_reserve()` / `_ENUM_RESERVE` /
  `_LLM_MIN_ROUNDTRIP`；`_run_inner` 里三处预算各守其位：
  LLM 用 `llm_quota`、枚举用 `llm_budget`、**精解段仍用 `time_budget`**。
- 连带缺陷：`propose_strategies` 的 `max(0.5, …)` 下限让 LLM **超支**
  （预留 0.761s 实际只剩 0.26s）⇒ 改为"剩余 < 0.5s 就跳过提议，直接枚举全策略"。
