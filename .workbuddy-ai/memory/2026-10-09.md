## 同日第二轮 · L5 性能优化（指令"能优化一下排程生成速度吗 / 继续优化"）

### ★ 最重要的发现：**排程结果原本不可复现**（比"慢"严重得多）

两个求解器都写死了 `num_search_workers = 4`（多线程并行搜索）+ 墙钟超时 +
接受 `FEASIBLE` 次优解。三者叠加 ⇒ **同一输入两次排程给不同计划**：
- 12 菜连跑 6 次：makespan **134 / 135 / 139 / 143**（4 种）
- 20 菜：**194 与 373.4**（差近 2 倍），4 次跑出 4 种不同的 `dish_finish`

评分要核对"总耗时与理论最优解对比" ⇒ 不可复现这项**根本没法算**。
修：`cpsat.py` 与 `model.py` 默认 **workers=1**（+ 固定 `random_seed`），
可用 `FT_CPSAT_WORKERS` / `FT_EXACT_WORKERS` 换吞吐（会牺牲可复现性）。

**代价实测可接受**：bench 耗时均值 121→163ms，max ~0.5s→~1.5s（仍 ≪ 5s 优秀线）。
⚠ 有趣的反例：**12/20 菜上单线程反而更快**（1698 vs 1789ms、2014 vs 2027ms）——
多 worker 在大问题上的协调开销 + 预算被切成多份，抵消了并行收益。

### ❌ 被实测否决的方案（写下来防止再捡）

1. **"贪心解已达下界 ⇒ 跳过精解轨"** —— 想法很合理（83% 时间在精解轨，
   而下界是放松），**45 组里 3 组变差**，且都很严重：Γ 0→10、T 30→74、T 55→76。
   根因：`lower_bound_from_plan` 是**从计划反推**的下界，只在**同一任务集口径**内
   成立 —— 而精解轨本来就会换口径（`slim` 丢掉提前准备步）。拿贪心口径的下界去判
   精解口径的解 ⇒ **假下界**。这正是 `model.py` 自己警告过的事，我把它用在了
   它明确不适用的地方。副作用：下界本身要算，45 组只命中 2 组，净效果**慢 3%**。
   代码已删，`tests/test_reproducible.py` 里钉住"别捡回来"。
2. **降 `FT_EXACT_BUDGET`（1.5→0.4）** —— max 从 1503→1574ms，**毫无效果**。
   因为 orchestrator 会把固定池重新分配，总预算不变。
3. **关 CP-SAT（`FT_CPSAT=off`）** —— 反而**更慢**（max 3624ms vs 1503ms）且质量变差
   （Γ 2.9→3.5）。CP-SAT 是加速器不是累赘。

### ✅ 保留下来的优化

- **开关缓存**（`FT_FLAG_CACHE`）：`cooldown_enabled()` 一次排程被调 **116,895 次**，
  每次读 `os.environ`（含 `strip/lower/encodekey`），合计 0.85s/6.93s = **12%**。
  改成请求级缓存。
  ⚠ **踩坑**：第一版用"入口 reset 一次、之后一直缓存" ⇒ `test_insight` 三条 +
  `test_core` 一条当场变红（同一个用例内先 setenv off 再 setenv on，缓存跨过了那次改动）。
  修法：`@_flag_scope` 装饰器把缓存**严格限制在 `_schedule_once` / `schedule` 执行期间**，
  出作用域即失效；且 `_flag` 在**无作用域时完全不缓存**（否则任何零散调用都会留下残留值）。
- 三轨消融实测（bench 50）：完整 82%·2.9·62.0·21.1·151ms / 只 CP-SAT 76%·3.7·70.4·31.7·50ms /
  只精确 82%·3.5·61.0·20.2·631ms ⇒ **单独任何一轨都更差，没有安全的削减空间**。

## 同日第三轮 · 诊断"apikey 调用有问题"（用户截图：徽标「AI在线」+ 助手回「已切换到离线模式」）

### 根因：**不是代码问题，是中转站账号未实名**

直连实测（`urllib` 绕过代理，两种方式都试）：

```
HTTP 502   https://potatoya.cn/pro100x/v1   model=gpt-5.6-sol
{"error":{"message":"real-name verification is required for your free step plan
 before calling this API. please complete face verification at
 https://account.stepfun.com/security?action=realname","code":"upstream_failed"}}
```

key 格式正确（54 字符、`sk-pro1…ESb0`）、已装载、中转站可达 —— 但**上游是阶跃星辰
StepFun，该账号未完成人脸实名认证**，一律 502。

**三条出路**（给用户）：① 去 stepfun 账号做实名；② 换一个可用端点/密钥；
③ 切本地 Ollama（`FT_LLM_PROVIDER=ollama`，免密钥，需本机 pull 模型）。

### ★ 顺带修掉的**真缺陷**：这个故障在界面上根本看不出来

两个根因：

1. **徽标只看熔断器**（开关开着 + 凭据非空），**不反映调用是否成功**。
   熔断阈值是 3 次，用户只试 1–2 次 ⇒ 徽标一直挂绿色「AI在线」，
   而助手已经回「已切换到离线模式」—— 两句话互相矛盾，用户无从下手。
2. **响应体在 `_post` 里被直接丢掉**（`return "http", None, e.code`）⇒
   系统里**根本不存在**"为什么失败"这个信息。502 和 401 长得一模一样。

修法（四处）：

| 位置 | 改动 |
|---|---|
| `llm.py` | 新增 `_record_failure(code, body)` / `last_failure()` / `_hint_of()`；`_post` 读出响应体并记账 |
| `llm.py` | **确定性失败立刻熔断**（401/402/403/429 + 上游含实名/额度/凭据关键词）⇒ `_trip("auth")` |
| `assistant.py` | 降级文案追加 `_why_line()`：「原因：最近一次调用失败：HTTP 502（上游要求账号完成实名认证）」 |
| `main.py` + `index.html` | `/api/llm_status` 暴露 `last_failure`；徽标在 `state=online 但 last_failure 有值` 时显示 `⚠ 模型调用失败` + tooltip |

**效果实测**：第二次请求从白等 ~900ms 降到 **5ms**（熔断已打开）；
助手回复直接说明原因；排程完全不受影响（`/api/plan` 200）。

⚠ **铁律守住**：`_hint_of` 剥掉 URL（上游报错自带文档链接），
`last_failure` 与助手文案里**不含任何第三方域名**（护栏 4 条断言）。

### 变异自检踩到**两次**"判据被兜住"（同类陷阱第 N 次）

1. 我的替身 `_fake_post` **自己调了** `_record_failure` ⇒ 把真实 `_post` 里那行
   删掉**测不出来**（16 项全绿但功能已废）。修：加一条走**真实 `_post`** 的用例
   （mock `urlopen` 抛 `HTTPError`）。
2. `assert "模型调用失败" in html` —— 变异把 `failing` 写死成 false 后，
   文案仍在页面上 ⇒ 照样通过。修：必须判**定义式**（`const failing=…` 里含 `lf.code`），
   不能只判"页面里有这几个字"。

⇒ **规律**：判"某个分支接上了没有"时，**必须判它的输入源**，
不能判它产出的文案/变量名是否出现。

### 基线

`pytest` **635**（新增 `test_llm_diagnostics.py` 17 项）· 变异 **7/7 捕获** ·
端到端全绿（助手文案带原因 / 状态端点暴露 / 立即熔断 / 二次请求 5ms / 排程不受影响）。
