## 二、三个"差点误判"的坑（都留了证据）

### 坑 1：中转站偶发卡满 20s —— 其实是**开发机代理**造成的
- 现象：`llm.chat()` 返回 `None`、`STATS.ms=0.0`、`failures=1`；20s 超时下 **12/15 成功**，
  失败的 3 次**全部精确卡到 20.4s**（双峰，不是渐变长尾）。
- 裸测同一端点却 **8/8 全绿、1.3~3.5s**。
- 根因：开发机有 `http_proxy=http://127.0.0.1:50696`（沙箱代理），urllib 默认走它。
  **禁用代理直连后暴露出真实失败模式：`HTTP 429`（限流）**，~480ms 就返回。
- ⚠ **服务器上没有这个代理**，所以"20s 卡死"是**本机环境假象**。
- 真实结论：中转站会**限流 429**；项目对 429 的处理是 `_trip("quota")` →
  `CB_QUOTA_COOLDOWN = 1800s`（**熔断 30 分钟**）。正常聊天（几秒一句）不触发，
  刚配好就猛点「测试连接」会撞上。
- 另一个真实观察：填 `gpt-5.6-sol`，中转站**实际路由到 `step-3.7-flash`** 并在响应里如实回报。

### 坑 2：`pip` 报 `from versions: none` —— 是**清华源**，不是包名/版本
- `pip.ini` 里配着 `index-url = https://pypi.tuna.tsinghua.edu.cn/simple`。
- `curl` 取该镜像页 **200**，venv 的 python `urllib` 也 **200（169KB）**，
  **只有 pip 一个版本都找不到**（连 `Collecting` 都不打印）。
- 换 `-i https://pypi.org/simple/ --trusted-host pypi.org` → **立刻装上**。
- 教训：`from versions: none` **≠ 包不存在**，先怀疑源。（已按 `pip-install-forensics` 技能取证。）

### 坑 3：`/api/llm_status` 的 `online_usable` / `reachable` 返回 `null`
- 不是缺陷：该字段在离线/无 provider 场景下本就允许 `null`。不影响任何功能。

## 七、用户问"为什么打包不带 API Key"（答疑 + 教程补强）

**结论：刻意排除，不是漏打。** 链路：开发机 `data/llm_settings.json`（**存着密钥**，
实测 provider=openai / base_url=potatoya / api_key=sk-pro100x-…）
→ `sync_publish.py` 的 `SKIP_NAMES = frozenset({"llm_settings.json"})` **明确跳过**
→ `publish/data/` 里没有它 → `pack.ps1` 只打 `publish/* + deploy/` → zip 天然无密钥。

**密钥的三处来源**（`llm.py`）：`FT_LLM_API_KEY`（env，**最高优先**）>
`data/llm_settings.json` 的 `remote.api_key` > 空串。
`_resolve_api_key()` **只在 provider=openai 档**取 saved 里的密钥 ——
切回 ollama 时故意不取，免得把远程密钥发给本地 Ollama。

**迁移后的表现**：包里没有 `llm_settings.json` ⇒ 新机器 `provider` 默认回落 **ollama**
⇒ 启动就是"本地 Ollama"档 ⇒ 无 Ollama ⇒ AI 对话离线。
**必须在设置页切「远程」+ 重填 Key**，或走另两条路（拷设置文件 / 写 `.env.local` 三行）。

**教程补强**：`docs/Windows服务器部署教程.md` 附 A 加了
①"包刻意不含密钥、必须重填"的显式说明（含"搜不到 sk- 是正常的"）
②「想让密钥跟着走：三种补法」对照表（网页重填 / 拷 json / 写 .env.local 钉死）
③提醒 env 三行会**禁用设置页下拉** + `.env.local` 必须无 BOM。

⚠ 开发机 `.env.local` 里那行 `# FT_LLM_API_KEY=...` 是**注释掉的**（`#` 开头）
⇒ 当前**不生效**，别误以为"配好了"。仓库**不是 git 仓库**（`git ls-files` 报
not a git repository）⇒ 无仓库泄漏面；但密钥仍以明文躺在磁盘上。

## 十、排程算法深挖：解析层三类"假设备" + 调度层两处口径（指令 F）

用户指令："找几个菜谱组合 → 检查甘特图 → 找出算法可优化点与漏洞 → 找到最优排程算法"。
做法：先做**全语料审计**（`app/spec/recipe_store.all_records()` 100 条）把"设备步"逐个

### 10.1 解析层：兜底推断把"名词里的烹饪动词"当成动作（20 步 / 虚占设备 149 分钟）

审计脚本 `.cache/_parse_audit.py`：官方 100 道菜占加热设备的步骤数 **230**。
三类成因，共同点是**烹饪动词出现在名词里**，而不是本步在做饭：

| 类 | 例子 | 旧判 |
|---|---|---|
| ① 完成态引用 | 小碗蒸肉#10「用筷子将**炖好的**猪肉，挨个放到碗里，再淋肉汁」 | 灶具 45min |
| ① 变体（熟/沸/过） | 芋头蛋卷#7「把**煎好的**蛋饼放案板，涂上**碾压好的**芋泥」 | 烤箱 25min |
| ② 器皿名 | 香烤鲫鱼#3「在烤盘中铺锡纸，将**烤串**放在烤架上，刷油」 | 烤箱 25min |
| ③ 调料名 | 金银蒜蒸鸡胸肉#3「加入**蒸鱼豉油**…腌制1小时」 | 蒸箱 60min |
| ③ 子菜名标签 | 轻松一锅蒸#4「**腊味合蒸**：处理食材，切片，铺在小碗中」 | 蒸箱 15min |
| ④ 量词 | 麻辣对虾(第二条)#4 占位句；食材里「食用油3**汤**匙」 | 灶具 45min |

修法（`app/parser/recipe_parser.py`，全在 `need_fb` 的探针文本上做减法）：
`_fb_probe = _DONE_STATE_RE.sub("", _SEASONING_RE.sub("", _ds.strip_parts(_LABEL_RE.sub("", stext))))`
- `_DONE_STATE_RE` = `(?:烤|蒸|炒|煎|炸|煮|炖|焖|烧|卤|焯|煸|焗|煲)(?:好|熟|透|沸|软|烂|过)[^，。；、\s]{0,2}?(?:的|了|后)`
  ⚠ 状态词表**只收 好/熟/透/沸/软/烂/过**，且必须带 的/了/后。
  **不收 开/至/成/干/香** ⇒ "烧开后""炒至微黄后""水分炒干""炒香后的"全部放行
  （摘了这些会把整道菜的真实灶具作业也摘掉，`test_completion_state_guard_keeps_real_cooking` 钉住）。
- `_SEASONING_RE` = 蒸鱼豉油/蒸鱼酱油/蒸鱼油/蒸肉粉（全语料只 `蒸鱼豉油` 命中 12 次）。
- `_LABEL_RE` = 行首 `^[^，。；、\s：]{2,12}[：:]`（套餐子菜名标签，16 条带标签 / 3 条中招）。
- `app/spec/device_spec.py` 的 `PART_WORDS` 补 `烤碗/烤串/烤网/蒸碟`。
- `_infer_from` 的炖煮分支：`汤` → **`汤(?!匙|勺)`**（"汤匙"是量词，不是"炖汤"）。

**实测**：占加热设备步数 **230 → 210（−8.7%）**，"有加热设备的菜" **始终 99/100**；
bench 总时长 **82.0 → 79.2**、连续手动 27.2 → 26.3、出锅差中位 2.0 不变、冲突 0。

⚠ **试过但必须记住的失败方向**：给 `need_fb` 再加一条"设备装载信号"
（`水箱|加水|第N层|中间层`）+ 把 `香` 收进状态词表 ⇒ 加热步数**顶回 213**，
新增 6 条**全是错的**：「豆沙松糕#3 **边加水边翻拌**成半湿状态」→ 蒸箱 15min、

⇒ **只摘完成态引用，绝不另外放宽 `need_fb` 的触发面**。

## 十一、指令 F 续：最优性判据实验 → 揪出 3 个真漏洞

### 11.1 硬判据实验：生产解 vs 足预算解（`.cache/_opt_probe.py`）

把同一套求解器的时间预算放大 20~40 倍（CP-SAT 20s / 精确 60s），看能否突破生产解。
结果 **0/10 有改进，且足预算解反而更差**（如 #4 生产 54 vs 足预算 65）。
⇒ **瓶颈不是时间预算**，是策略多样性（生产跑 6 条策略 × 3 轨，单策略给再多时间也追不上）。
⇒ 结论：**算法本身没有"因为时间不够而次优"的问题**。

### 11.2 漏洞 A：`lower_bound_from_plan` 依赖边**全被静默丢弃**（键类型错配）

```python
"deps": [tuple(d.split("#")) for d in (t.depends_on or [])]
```
`ScheduledTask.step_id` 是 **int**，而 `split("#")` 产出**字符串** ⇒ `("菜","3")` vs `("菜",3)`
⇒ `_critical_path` 里 `[d for d in deps if d in dur]` **恒为空** ⇒ 关键路退化成"最长单步时长"。

实测 5 菜实例（三味蒸鳗鱼+油醋汁剁肉饼蒸和乐蟹+香辣烤小龙虾+红豆糯米糕+金银蒜蒸鸡胸肉）：
真实活跃关键路 **54**（=makespan）被报成 **18** ⇒ LB 27 ⇒ **gap 从 0% 虚报成 100%**。

修复：新增 `model._dep_key()`，显式 `int()` 化 step_id（异常不抛）。

### 11.3 漏洞 B：`等待`步被排除出**关键路径**（不是排除出能量/人工）

同一函数里 `t.unit_id not in ("等待","提前准备")` 一刀切。理由（不占机器/人手）对
**批次机产能 / 人工总工时**成立，对**关键路径不成立** —— 腌制/浸泡/放凉是**真实流逝时间**，
且是依赖链上的节点。摘掉它等于把链切断：
三味蒸鳗鱼真实活跃关键路 54，摘掉等待后只剩 25。

修复：拆成 `live`（含等待，喂 `_critical_path`）与 `live 去掉等待/提前准备`（喂 energy/hand）。

**两个缺陷都让 lb_cp 静默变小，都不会报错**，且三条旧护栏结构上抓不到：
- `test_critical_path_*` 自造 dict，键类型本来就匹配，走不到转换那行；
- `test_lower_bound_from_plan_never_exceeds_makespan` 只断言 `lb <= makespan`，低估时**恒真**；
- `lb_probe` 只报数，从不与"手算关键路"对照。

### 11.4 修正后的真实最优性

`lb_probe 60 seed=11`：**gap 中位 0.0% / 均值 2.2% / p90 8.7% / max 34.8%**，
**43/60（72%）实例 makespan 恰好等于可证下界**，0 违反。
（改前报的是中位 28.6% / max 100% —— 全是坏下界造出来的假象。）
⇒ **交付的计划在 makespan 上基本就是可证最优的**。剩余 gap 的来源是
① 下界忽略机器"最早可开工时刻"（#15：烤箱容量 1，饼干 45 分才能进炉 ⇒ 45+48=93 是最优，
而 LB 只算 48）；② 目标以 Γ（对齐）为第一优先，会主动牺牲 makespan。

### 11.5 漏洞 C：出锅差 Γ 可被"把收尾步停到最后"刷小（保热惩罚被掩掉）

`dish_finish[dish] = 该菜所有 t>=0 任务的 max end`，同时喂给 ① Γ（评分口径）② 冷等待/保热惩罚。
把一条 1 分钟的收尾步（"尽情品尝吧"/"撒葱花"）停在时间线末端 ⇒ `F_d == T` ⇒ `cold = 0` ⇒
**惩罚被完全掩掉**，求解器反而**被奖励**去"早做熟、干等到最后"。

实测 60 组：报告 Γ 与"真实烹饪跨度"差额 **中位 23.0 / 均值 30.2 / max 175**，49/60 组差 >5min。
典型 #55（酿苦瓜+手工鸡蛋豆腐+原味墨西哥面包）：两道蒸菜真实 8/16 min 就出锅，
却把两条"尽情品尝吧"停在 190-192 ⇒ 报出 **Γ=2.0，而菜实际凉了 177 min**。

修复（**分两处，量过再定**）：

| 位置 | 改法 | 效果 |
|---|---|---|
| `model.solve_exact` 的 cold/over | 基准改 `F_cook`（最后一次进加热设备结束） | 差额中位 **23.0 → 7.5**，**零指标代价**（<5min 90.3% 不变，总时长 63.6） |
| `objective.score_plan` 的保热项 | **刻意不改**（保持 `plan.dish_finish`） | 改了会让 <5min **90.3% → 80.0%**（6 seed 系统性下降） |

为什么两处结论相反：`model` 里 cold 是**字典序最低层**（排在 Γ、T 之后），改基准不跟 Γ 抢；
`score_plan` 里它是**无界加权项**，一道菜等 170min ⇒ `30×0.9×170 ≈ 4590` ≫ `w_gap·Γ = 180`，
于是**策略择优被整个改写**，违背"Γ ≫ 保热"的评分优先级。
真要把它做成方向盘，正确做法是给 `over` 加**上界**，不是换基准。

### 11.6 又一个"静默降级"教训（我自己踩的）

加 `FT_COLD_BASE` 开关时在 `model.py` 里写了 `os.environ`，但**那个文件没有 `import os`**
⇒ `solve_exact` 抛 `NameError` ⇒ 被 `engine.schedule` 的 `except Exception: pass` **静默吞掉**
⇒ 精确轨整个失效（bench 总时长 63.9 → 72.5）。**是 pytest 抓到的**（有测试直接调 `solve_exact`）。
⇒ 教训：给"被 try/except 包住"的模块加新全局依赖时，必须有一条**直接调用**它的测试。

## 十二、漏洞 D：跨午夜 HH:mm 回绕 → "偶发红一次"的护栏

**现象**：全量测试在 23:0x 那次报 `test_official_api_spec_conformance` 红；单独跑又绿；连跑两次全绿。

**根因**：`adapter.hhmm(offset) = (now + timedelta(minutes=offset)).strftime("%H:%M")`。
`now=23:10` + 50 分钟 ⇒ **"00:00"**。而该测试的"要求3"裸比分钟值：

```python
max_end = max(mm(x["endTime"]) ...)      # 23:52 → 1432
if mm(ov["finishTime"]) < max_end:       # 00:00 → 0  ⇒ 假报违规
```

**复现**（把 `now` 钉死）：`23:10` 时 8 组里 **1 组**中招；`22:50`/`23:00`/`23:55` 为 0
（窗口 = "now 到午夜" 短于计划跨度时）。所以只在**临近午夜**复现。

**修法**：改成**环形差**判据 —— `dish_end <= makespan` ⇒
`(mm(finish) − mm(end)) % 1440 == makespan − end <= makespan`。对回绕免疫，且不改口径
（HH:mm 表达不了"次日"，回绕是格式限制；语义上 00:00 确实晚于 23:52，错的是比较方式）。

**新护栏** `test_api_times_are_rollover_safe`（把时钟钉在 23:10，让场景**必现**）。
验证：修复后全量在 **23:11 本地时间**跑过 390 passed —— 正是原来会红的时刻。

**教训（第四条铁律候选）**：**依赖墙上时钟的护栏 = 定时炸弹**。凡是拿 `datetime.now()`
参与断言的用例，都要么把时钟钉死，要么把比较做成对日期回绕免疫的。
"偶发红一次"比"一直红"更危险 —— 它会训练人忽略红灯。

### 13.1 主导工序先验：**72/100 道菜被判成"爆炒"**

而 `_FRY` 又收了"烤|酥"。两条叠加，分布退化成 **fry 72 / steam 18 / cold 3 / other 7**

新判据按"**上桌时的状态**"：
1. **末道设备工序是冷藏/冷冻 ⇒ cold**。判据要严：冰箱步之后只剩上桌动作，**且原文没说"趁热"**
   —— 否则会把「冷藏醒面」（玛格丽特 #2 后面还有烘烤）和「蒸好后…**趁热**或冷藏后食用」
   （皂角银耳羹 #4）误判成冷食。
2. **菜名强信号**，顺序即优先级：冷食 > 烘焙 > 蒸 > 汤羹 > 炒炸。
   ⚠ `蛋羹` 必须先于 `羹` 判（鸡蛋羹是蒸出来的，归汤羹会把 hold 从 10 放宽到 45）。
3. **加热步的主导设备**（平票按 蒸箱 > 烤箱 > 灶具）。淋热油/焯水这类灶具收尾步在官方菜谱里
   非常多，按"有没有炒"判必被它带偏。

新增 `bake` 一档（0.75 / hold 20）。新分布 `bake 36 / steam 39 / fry 13 / soup 6 / cold 6`。
顺带删掉旧实现里 99-108 行那段**永远走不到**的死代码（重复的 4 个 return）。

**量化结论（诚实版）**：对排程指标**几乎无影响**（6 seed × 50 组：`<5min` 90.3%→90.3%、
总时长 68.75→68.82、连续手动 25.40→25.72，全在噪声内）。原因见 13.3：保热项在策略择优里
本来就没话语权。它的价值是**语义正确**（通知文案、`freeze_hot` 仲裁、精解轨第 ③ 层、
`serve_hot ≥ 0.85` 的"趁热上桌"提醒），以及不再往目标里灌错信号。

### 13.2 保热项：从"恒 ≈ 0"到"以 Γ 计价的方向盘"

`score_plan` 的保热项原本只有两个坏形态：
- **完成时刻基准** ⇒ 把 1 分钟收尾步停到时间线末端就恒 ≈ 0 ⇒ **等于没参与过择优**；
- **出锅时刻 + 无界** ⇒ 一道菜等 170 min 就是 4590，`w_gap·Γ` 只有 180 ⇒ **夺走 Γ 的权**（`<5min` 90.3%→80.3%）。

**第一版修法（错的）**：给 per-dish `over` 加上界 `FT_HOT_CAP`。实测 CAP=5/10/20 只把
`<5min` 救回 89.3/88.3/86.7%，**仍低于旧口径** —— 因为 per-dish 上界管不住"多道菜累加"。

**第二版修法（采用）**：把预算**按 Γ 计价** —— `min(hot, w_gap × FT_HOT_BUDGET)`，
语义 = "**保热最多花掉 N 分钟的 Γ**"。任何 Γ 领先超过 N 分钟的方案都不会被翻盘。
开关 `FT_HOT_BASE`（cook 默认 / finish 旧口径）+ `FT_HOT_BUDGET`（默认 **0.5**，0 = 等价旧行为，off = 无界）。

| budget | `<5min`(6seed) | makespan==可证下界(4seed) | gap 均值 | 保热违规 |
|---|---|---|---|---|
| 旧口径（完成时刻，无界） | 90.3% | 65.0% | 3.43 | 3.68 |
| **0.5 ← 采用** | **90.3%** | **65.0%** | **3.23** | ~3.5 |
| 2 | 90.3% | 62.8% | 3.60 | 3.40 |
| off（无界） | 80.7% | — | — | 1.04 |

读法：**出锅差对 [0, 4] 整个区间免疫**（评分表主项必须是平的）；但预算一大就开始用
makespan 去换保热。0.5 是三条轴上都不劣于旧口径的最小值。

### 13.3 一个更本质的发现：**候选集太粗，语义项根本没有"破平局"的空间**

预算从 0 加到 4，**出锅差完全不动** —— 说明 6 条贪心策略 + 3 轨给出的候选**彼此差得很远**，
几乎没有"Γ 接近"的候选对可供挑选。所以语义先验在这一层只能"微调"。
**要让语义真正参与决策，方向是在精解轨做局部搜索（邻域再生成候选），不是继续调系数。**

### 13.4 又一个"排程一改、护栏就假红"（第五条铁律候选）

`tests/test_audit_doc.py::test_the_false_alarm_is_reachable` 把"能造出跨零点场景"的时刻
**钉死在 22:00**。本轮保热口径一改、排程变短，22:00 从"3 条旧口径误报"退化成
"**0 个跨零点场景**" ⇒ 当场变红，报"测试前提不成立"。**不是审计坏了，是排程变好了。**

修法：不钉死单一时刻 —— 先试首选（重扫后实测最优的 **23:15**：跨零点 10 组 / 旧口径误报 4 条），
造不出场景就**自动扫候选池**，最终仍断言"这个误报确实可达"（前提消失必须报错，不许静默跳过）。
docstring 里那张"冻结时刻 → 误报数"表也按新排程重测（`.cache/_trigger_scan.py` 可复现）。

⇒ **教训：断言"某个前提成立"的测试，前提本身会随被测代码变好而失效。
把前提写成"在候选集里搜一个满足的"，而不是"钉死一个"，否则每次优化都要来修它。**

## 十四、指令 F 第三轮：最优性证书 + 三个"看起来像漏洞"的东西

> 目标从"找漏洞"升级成"给最优性**出证明**"。前两轮的判据是"gap vs 放松下界"，
> 只能说明"离下界不远"；本轮直接读**求解器自己报的证明状态**，并补上 Γ 的下界。

### 14.1 可证最优率 ~98–100%（生产 1.5s 预算）

`model.solve_exact` 会写 `plan.solver_status = "OPTIMAL" if st == OPTIMAL else "FEASIBLE"`
（`model.py:751`，是**真状态**不是默认值）。实测：

| 规模 | 1.5s（生产） | 30s |
|---|---|---|
| 3–5 菜（100 组 seed=42） | **OPTIMAL 100/100** | 99/100 ※ |
| 6–9 菜（60 组 seed=42） | **OPTIMAL 60/60** | 59/60 ※ |

※ 两列是**不同实例集** —— 探针的 `random.seed` 在两个预算循环**之前**只调一次。
不是"时间越多越差"。

**证书可信性**（`_cert_verify.py` 60 组 seed=11）：模型自报 (Γ,T) 与独立 `evaluate()`
**逐位一致**（0/60 不一致），`check_plan` 全部可行（0 冲突 / 0 依赖违反）。

### 14.2 公平版预算探针：0/20，输出逐位相同（`.cache/_opt_fair.py`）

⚠ 旧的 `_opt_probe.py` 的"足预算解"用**默认单策略**，生产是"6 策略择优 + 三轨" ——
两边候选集不同，测出来的是**策略选择**的收益。新脚本把两边钉在**同一策略**只放大预算：
**20 组全部 dT = dG = 0.0（逐位相同），0/20 有改进。**
⇒ 精确模型 1.5s 内已收敛并证明最优，多余预算一点没用上。

### 14.3 补上 Γ 的下界（本轮唯一代码改动）

此前只有 **T** 的下界，**Γ（评分表主项）完全没有下界**。新增
`model.gamma_lb_from_plan(plan)`：

> **Γ_lb = Σd − max d**，d 取同一**容量 1** 资源上各菜的**末步**时长。

**三条必须排除**（漏任何一条都会造出"下界 > 真实 Γ"的假下界）：
① **蒸箱**（`unit_id` 是腔体槽位不是机器，同温无限共享）；
② **容量 > 1 的资源**（灶具 = 2 灶眼）；③ **`等待`/`提前准备`**（不占资源）。

已接进 `scripts/lb_probe.py` + 4 条护栏（`tests/test_model.py` §6）。**60 组 seed=11**：
`Γ_等于下界占比 68% (41/60)`、`Γ−Γ_lb 中位 0.0 / 均值 0.5 / max 7.0`、`Γ_下界违反数 0`。
⇒ **68% 的实例出锅差恰好等于可证下界**。

### 14.4 排除掉的三个"看起来像漏洞"的东西

| 怀疑 | 结论 | 证据 |
|---|---|---|
| **ε 约束方向反了**（先压 T、再在 `T≤T*+15` 内压 Γ，而评分表是 Γ 主序） | **不成立** | `FT_EXACT_SLACK` 15→999 最终指标**逐项完全相同**。多轨 + `score_plan`(60:1) 已补掉短板：`solve_exact` 在 #15 单独给 Γ=24，**贪心给 Γ=1**，择优选了贪心 |
| **灶具平票永远选 `灶具-1`**（`earliest_slot` 平票取 `u=0`） | **无害** | 平票 = 两灶眼同时空闲 ⇒ 放哪个都不影响后续可达性 |
| **择优用加权和而非 (Γ,T) 字典序** | **20/20 一致** | `_pick_gap.py`：两种口径挑出的方案 (Γ,T) 完全相同 |

### 14.5 三个潜伏问题（当前规模不触发，已记录）

1. **蒸箱容量两套口径**：`engine.RESOURCE_UNITS[蒸箱]=1`（一个腔体）vs
   `model.capacities()[蒸箱]=BATCH_Q=4`（腔体批次容量）。引擎 `_temp_share_fit`
   对同温任务**永不阻挡**（并行无上限），模型上限 4，`checker` 只查温度不查数量。
   实测 60 组：最大同温并行 **4 盘**、**0 超限**、**0 异温并行** ⇒ 未触发。
2. **`solve_exact` 在 ε 卡紧时可能不如贪心**（#15：exact Γ=24 / 贪心 Γ=1）——
   被多轨掩盖；若将来只跑精确轨，质量会掉。
3. **`solver_status` 未对外暴露** —— "已证明最优"这个最强声明 API 看不到。

"连续手动操作时长"是 25 分项的一部分，但 `FT_HAND_CAP` 默认未设 ⇒ 精确模型**不优化它**
