### 2. 🔴 真问题一：探针 `fitExpr` 的 `colTracks` 恒为 1（桌面分支从未执行）

**症状**：`VP=1280x720` 跑出 `95 通过 / 1 失败`（`窄屏：甘特图仍有可用高度 ≥200px`，实测 104px），
而文档声称"1280×720 也跑过，108/0"。

**取证链**：
1. `colTracks` 报 **1**，但 CSS 里 1280 > 1024 ⇒ `.grid3` 应是三列（`260px 1.8fr 260px`）。
   且同一次测量里 `vpH=655`、`midH=579`、`colH=[579,579]` —— **全是桌面三列的特征**。
2. `fitExpr` 是一段**模板字符串**（`const fitExpr = \`…\`;`），会被送进 CDP 当 JS 源码求值。
   里面写的是 `t.split(/\s+/)` —— **单反斜杠**。
3. 模板字符串会把 `\s` 解析成 `s`（反斜杠被吃掉）⇒ 求值时是 `split(/s+/)`；
   而 `"260px 639px 260px"` 里**没有任何字母 s** ⇒ 永远只切出 1 段 ⇒ `colTracks` 恒为 1。
4. 同文件 `VP_MEASURE` 写的是 `split(/\\s+/)`（**双反斜杠，正确**）。只有 `fitExpr` 漏了一个。

**后果（比想象中严重）**：`stacked = fit.colTracks !== 3` 恒为 true ⇒ **永远走"窄屏"分支**
⇒ 桌面分支那 **7 条检查从未执行过**：
`页面无纵向滚动条 / 计划视图内部不溢出 / 悬浮球不遮挡 / 中列卡片无浪费空间 /
任务明细已收窄 / 时间轴高度显著大于任务明细 / 三列等高`。
而窄屏分支在桌面尺寸下**也照样全绿**（`vpScrollH>=vpClientH-1`、`vpH>=innerH-2` 在桌面也成立）
⇒ 探针一直报"通过"，典型的**"绿得毫无意义"**。

**修复**：
- `split(/\s+/)` → `split(/\\s+/)`，并加注释说明**这段是模板串、注释里不能出现反引号**
  （改的时候真踩了：注释里写 `` `/\s+/` `` 直接把模板串提前闭合，`node --check` 报语法错）。
- **加互证护栏**：新增 `colTracksByLayout`（按子元素左边界去重数真实列数），
  断言 `colTracks === colTracksByLayout`。分支选错就硬失败，不允许静默。
- **加静态护栏** `tests/test_probe_source.py`（2 项）：扫 `scripts/*.mjs` 的**模板字符串**，
  禁止出现"单个反斜杠 + 词类字符"（`\s \d \w \S \D \W \b \B`）的正则片段；
  第 2 项是**变异自检**（把双反斜杠改回单个，扫描器必须报出来）⇒ 证明护栏有牙齿。
  扫描器跳过**行首 `//` 注释**（注释里出现 `\s` 是合理说明，`${}` 内的真代码不跳）。

### 过程中发现并修掉的 4 个真缺陷
1. **远端档默认超时 3.0s 是"贴着线"的** —— 实测 2.27~2.90s。贴线 ⇒ "聊天时好时坏"，
   而 llm 的失败是**静默降级**、现场零报错。→ `_DEFAULT_TIMEOUT["openai"]` 上调到 **20**。
   确认**不拖慢排程**：`chat()` 取 `min(传入, TIMEOUT*3)`，闭环仍 3.6s/2.5s。
2. **启动探测超时会连 AI 对话一起关掉 120s** —— 远端档预算 1.5s，中转站必超 ⇒
   **每次重启都熔断**，而那正是用户第一次点 AI 对话的时刻。→ 新增
   `probe_miss_is_fatal()`（判据是**预算宽窄**，不是 provider 名字）：宽预算(≥10s)才
   `force_open`，紧预算只 `mark_online_too_slow`（只关排程闭环）。
3. **`_resolve_model` 只读全局 `model`** —— 界面切远程后再用 `FT_LLM_PROVIDER=ollama`
   钉回本地，会拿着 `gpt-5.6-sol` 打本机 11434 ⇒ 404 且**静默降级**。→ 改成优先读 `models[provider]`。
4. **`verified` 对远程档误报** —— 远程模型名在中转站那边，本机 Ollama 当然没有，
   照旧报 `False` 会让界面显示"⚠ 本机没有这个模型，调用会返回 404"，把正常切换吓成失败。
   → 只有本地档才判，远程档给 `None`。

### 安全（**这一条最重要**）
`/api/model_settings` 是**无鉴权**的（本机演示 + 发布出去的公开链接都能读）⇒
**密钥只存不回传**：`remote_view()` 只给 `api_key_set: bool`，**没有** `api_key` 字段；
页面上也**永不回填**密钥框。对应地 **空串 = "保持原样"而非"清空"**（否则用户每保存一次
就抹掉一次自己的密钥，而且是静默的）。已复核：`data/llm_settings.json` **既不进
Docker 镜像**（`.dockerignore`）**也不进发布目录**（`sync_publish.py` 的 `SKIP_NAMES`）。

### setup.ps1 的六步
定位项目（多套一层自动下探）→ 找 Python 建 venv 装依赖（**只有 3.14 才用 `requirements.lock.txt`**）
→ 写 `.env.local`（标记块包裹 + 无 BOM）→ 生成 `run-server.cmd`（纯 ASCII/CRLF，`:loop` 崩溃自拉）
→ `New-NetFirewallRule` + `Register-ScheduledTask`（SYSTEM/AtStartup/`ExecutionTimeLimit=0`）
→ 自检 `/health` `/ready` `POST /api/plan` 并打印对外链接与令牌。

### 实测抓到的真缺陷（四个，全被护栏/变异钉住）
1. **`.ps1` 无 BOM ⇒ PowerShell 5.1 按 GBK 解码 ⇒ 解析直接失败。**
   报「语句块或类型定义中缺少右 }」「字符串缺少终止符」。**阴在**：把同一文件按 UTF-8
   显式读进来解析是**完全正常**的 ⇒ 开发机用编辑器看、换工具检查都发现不了。
   ⇒ 三个 `.ps1` 全部补 `EF BB BF`。⚠ 与项目另外两条**方向相反**：
   `.env.local` **必须无 BOM**、`run-server.cmd` **必须纯 ASCII**。
2. **`pack.ps1` 用了 `Warn` 但只定义了 `Say/Ok/Die`。** PowerShell 不在解析期报错，
   跑到那一行才 `CommandNotFoundException` ⇒ 前面几步都成功、突然 `exit 1`，
   看起来像"打包失败"。⇒ 加护栏「每个 helper 调用必须有同文件定义」。
3. **自检菜名「番茄炒蛋」根本不在官方菜库**（只有「芝士番茄土豆泥」）。
   `/api/plan` 对未命中菜名**只在服务端日志留痕**，响应里看不出 ⇒ 自检报
   `recipeCount=1`（请求 2 道排 1 道），部署像失败。⇒ 改「家常鲈鱼」+「豉汁蒸草鱼」，
   并**真的去调 `recipe_store` 核对菜名**，再补一条「请求几道 vs 排了几道」的判据。
4. **`Compress-Archive` 与 `ZipFile::CreateFromDirectory` 都产出反斜杠条目名。**
   实测原始字节 `app\api\main.py`。`.NET Framework` 的 `CreateFromDirectory`
   直到 **.NET Core 3.0** 才修好，而 PS 5.1 跑在 .NET Framework 上。
   这种包在 7-Zip / 宝塔 / Linux unzip 下会把目录解平 —— **要到服务器上才发现**。
   ⇒ 改**手工逐条 `CreateEntryFromFile`** 并 `.Replace('\','/')`。
   ⚠ 少加载 `System.IO.Compression` 会报「找不到类型 `[IO.Compression.ZipArchiveMode]`」
   （`ZipFile` 在 `.FileSystem.dll`，`ZipArchiveMode` 在 `.dll`，两个都要 `Add-Type`）。

### 变异测试连抓两次「子串空转护栏」
- `test_pack_syncs_publish_before_packaging` 原本只断言 `"sync_publish" in text` ——
  而**脚本顶部注释里就有这个词**，把真正的调用 `-m scripts.sync_publish` 改成
  `-m scripts.noop` 照样全绿。⇒ 改成锚定**命令行** `re.search(r"-m\s+scripts\.sync_publish\s*$", ...)`。
- `test_setup_cmd_has_restart_loop_and_single_worker` 断言 `"goto loop" in body` ——
  被 `rem goto loop` 蒙混。⇒ 改成整行锚点 `(?m)^goto\s+loop\s*$`。

### `-Token -` 这种「减号当哨兵值」不要用
PowerShell 参数绑定对单独的 `-` 行为不明确 ⇒ 改成显式开关 `-NoAuth`，教程里也不会教错。

## 顺手修掉两个既有缺陷（都不是本轮引入的）

### 1. `audit_doc` 的 5.1 跨零点假报警（**审计脚本自己错**）
21:58 跑 `audit_doc` 报 3 条 `finish_lt_end`。排查：`finishTime=00:04`（**跨了零点**），
菜品止于 `23:44/23:56/23:57`。原判据是 `ct["endTime"] > ov["finishTime"]` —— **比 "HH:MM" 字符串**，
`"23:44" > "00:04"` 字典序成立 ⇒ 误判"菜品比上桌还晚"。**排程完全正确**。
触发窗口实测（seed=42 那 40 组）：21:00→0 条、**22:00→3 条**、23:00→1 条、23:30→0 条
⇒ **这个审计的结论取决于你几点跑它**。改成算「顺时针距离」：
`delta = (_hm_to_min(finish) - _hm_to_min(end)) % 1440; if delta > span`。
新增 `tests/test_audit_doc.py`（4 条，含**负向对照**：证明 22:00 确实能让旧口径误报，
否则这条回归测试就是空转）。`audit_doc` 恢复 **9/9 缺陷 0**。

### 2. `test_llm_provider.py` 6 条红 —— **夹具只"用完还原"、没"开始前复位"**
