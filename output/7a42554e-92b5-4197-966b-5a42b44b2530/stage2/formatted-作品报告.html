一、作品概述

本章说明作品要解决的问题、对赛题两层挑战的判断，以及一组可直接核对的实测指标。

1.1 一句话概括

本作品是一套面向家庭多菜并行烹饪场景的智能调度系统：输入是用户选定的若干道菜与厨房设备条件，输出是一份可直接执行的烹饪计划（含每道菜各步骤的设备、起止时刻与参数），并在执行过程中支持动态重排与关键节点提醒。

1.2 赛题定位与我们的判断

赛题把挑战明确划分为两层：理解层（从自然语言菜谱中提取设备、时间、依赖等结构化信息）与规划层（多资源约束下的任务调度优化）。我们对这两层的判断是：

  • 理解层是"脏活"——官方 100 道菜共 767 个步骤，写法极不统一，同一件事有几十种表述方式；
  • 规划层是"硬活"——它本质上是一个带批次机与滞后约束的资源受限项目调度问题（RCPSP），单纯靠提示词让大模型"排一排"，不可能同时满足零冲突、零依赖违反与最优性。

因此我们没有把系统做成"一个大模型加几个工具调用"，而是做成模型与求解器分工明确的双引擎结构。这构成本作品最主要的设计立场。

二、问题分析

本章把"多菜并行烹饪"这个生活场景翻译成可求解的工程问题，并说明它与通用调度问题的差别。

2.1 家庭烹饪的三重困境

赛题描述的场景痛点可以拆成三个互相纠缠的问题：

  1. 设备资源有限：灶具通常 2 个灶眼，蒸箱、烤箱各 1 台，冰箱 1 台。设备一旦被占用，其他菜只能等——而蒸箱和烤箱恰恰是最容易成为瓶颈的两台。
  2. 步骤依赖复杂：腌制必须早于蒸制、焯水必须早于炖煮，而"腌制 2 小时"这类长等待又恰恰是插入其他操作的黄金窗口。
  3. 时序协调困难：用户真正想要的不是"最快做完"，而是一起上桌——凉了的菜再快也没有意义。

这三者构成了一个典型的多目标冲突：追求同时出锅会拉长总时长，追求总时长最短会让菜凉掉。

2.2 与通用调度问题的差别

本问题不能直接套用教科书模型，有三处特殊结构：

  • 批次机（Batch Machine）：蒸箱和烤箱一次可以放多盘，但只有同温才能合炉。赛题原文明确"蒸箱不能同时进行不同温度的蒸制"，这意味着设备占用不是简单的"同一时刻只能一个任务"，而是"同一时刻只能一个温度档"。异温切换还要留降温时间。
  • 可抢占的人工与不可抢占的设备：人在"腌制 2 小时"期间是空闲的，可以去做另一道菜的切配；但设备一旦启动就不能中断。这决定了依赖图不能是纯线性链。
  • 软性的"热"约束：菜出锅后能放多久取决于菜品本身（蒸鱼几分钟就凉，卤味可以放很久），这是一个语义属性，无法从步骤文本的语法结构中推出。

第三点尤其关键：它说明规划层必须向理解层索取语义信息，而不是只拿结构化的时间与设备。

2.3 由此确定的三条设计原则

上述结构决定了三条贯穿全系统的设计原则，后续每一处技术选择都可由它们推出。

  1. 硬约束只做可行性，不进目标函数。设备冲突与依赖违反是"能不能做"的问题，把它们塞进目标函数会让求解器学会"用违反换分数"。
  2. 目标函数不得包含可被反向利用的代理量。例如"设备利用率"看起来很合理，但优化它会诱导求解器故意拉长占用时间。利用率只能是仪表盘，不能是方向盘。
  3. 口径必须与赛题评分表逐字对齐。例如"同出锅时间差"，我们严格采用评分表定义的原始跨度 max F − min F，而不是更"语义正确"的冷等待加权和——后者在冷菜可以早出锅时会给出相反的方向。

关键设计：模型参与的是决策，不是在线算力。语义先验、参数补全、策略结论一律离线算好落盘；在线排程只读缓存，模型决策 0 延迟、0 网络依赖。需要演示完整 Agent 能力时再打开在线决策，且有超时与熔断兜底。

这条约束的直接收益是：在没有外网、甚至没有装模型的评审机上，系统的全部指标与耗时不变。

3.3 三处关键取舍

以下三处取舍决定了系统的整体形态，也是答辩时最常被追问的地方。

取舍一：为什么不用"端到端大模型排程"

我们实测过让模型直接输出时间轴。结论是它无法同时守住零冲突与零依赖违反——不是提示词不够好，而是这类约束需要全局一致性，而自回归生成天生是局部的。把求解交给确定性求解器之后，约束从"希望它遵守"变成了"结构上不可能违反"。

取舍二：为什么保留三条求解轨而不是只留最好的一条

精确模型在 3–5 菜规模上几乎总能给出最优解，但它依赖一个前提：问题实例能被完整建模。设备故障、硬冻结、预算不足这些情况下，贪心启发式反而是唯一能出解的那条。三轨取优的意义不是"三个都算一遍选最好"，而是任何单轨失效时系统仍然出得来合法计划。

取舍三：为什么宁可分数低一点也不丢任务

解析层修过一处正确性缺陷：官方菜谱里有 12 句复合句（形如"放入烤箱第 3 层，烘烤结束，取出晾凉"）的真实设备作业，曾被"晾凉 / 冷却"这类等待词整句抹掉。修复后解析正确性从 95/100 提升到 99/100，但问题本身也变得更难更真实——优秀率 92% 降至 90%、总时长 73.5 分钟升至 74.8 分钟。我们保留了这个权衡：宁可指标低一点，也不要靠丢任务刷分。

四、关键技术实现

本章按赛题的五层要求逐层说明实现方式，每层都给出对应的实测数据或可验证的保证。

4.1 L1 结构化解析

解析器输出赛题要求的五要素：设备（七类 + 人工）、温度、持续时间、步骤依赖、是否需人工介入，另附工作模式、是否无人值守、步骤类别等调度需要的附加信息。

三处必须处理好的细节：

  1. 等待词的双向守住。中文菜谱里"浸泡 / 泡发 / 解冻 / 过夜 / 静置 / 醒面 / 晾凉 / 放凉 / 冷却 / 沥水"既是真实等待、又常与真实加热动作出现在同一句里。我们的处理是：命中等待词即把整句降级为"等待"；但放行三类例外——明确的装载动词、点名加热设备并带显式时长的句子、灶具上的主动烹饪动作。漏降级会把"浸泡 4 小时"变成蒸箱独占 4 小时；乱降级会把"烘烤结束，取出晾凉"里真实的烤箱作业整句抹掉。
  2. 假设备的两大来源。一是名词里嵌的烹饪动词（"蒸烤盘 / 烤盘 / 蒸架"是配件不是设备），二是把纯装载句（"将烤盘放入烤箱中"）当成设备作业。前者会造出凭空占用的蒸箱任务，后者会造出时长靠猜的虚假占用。
  3. 复合设备消歧。方太的蒸烤一体机同时具备蒸与烤能力，菜谱写"放入机器中间层"时并未指明用哪个功能。我们按同菜上下文消歧：出现水箱 / 加水 / 蒸制信号判蒸箱，出现烤盘 / 油纸 / 锡纸 / 烘烤信号判烤箱。

准确率如何证明。我们建了一份人工标注集（20 道菜 / 148 步，四类设备全覆盖），标注只依据菜谱原文、不参考解析器输出。对照结果如下：

时长提取100.0%20 / 20

4.2 L2 多菜并行调度

本层是整个系统的核心。我们把它拆成"问题建模、三轨取优、独立校验"三部分。

问题建模

我们把问题写成严格的数学规划：以"批次机 + 两阶段 ε-约束 + 三层字典序目标"刻画蒸烤设备的同温合炉、异温降温、出锅对齐等结构。关键约束包括：

  • 设备容量约束（灶具 2 灶眼、蒸箱 / 烤箱 / 冰箱按温区计容量）；
  • 同温合炉与异温降温缓冲（只罚降温、不罚升温，容差与同温合炉共用同一常量）；
  • 步骤依赖与提前备菜的前缀闭包（提前做人工准备时，必须保证其所有祖先也已完成）；
  • 连续手动操作时长上限（赛题 L3 的独立评分项）。

三轨取优

在线路径依次尝试三条求解轨：

  1. 贪心启发式（6 条策略）：毫秒级，永远能出解，是兜底；
  2. CP-SAT：在贪心解的基础上做精解；
  3. 精确模型：把问题完整写成数学规划求解，支持硬冻结（动态重排必需）。

三轨结果按出锅差 Γ 与总时长 T 的字典序取优。这一顺序直接对应赛题的评分权重——同出锅时间差是 25 分里的首要项。

独立校验

返回前由独立校验模块对计划做一次复验，检查设备冲突与依赖违反。求解器与校验器是两套代码，前者出错后者能拦住。

4.3 L3 多目标优化

赛题给了三个观察点：同出锅时间差、用户连续手动操作时长、总烹饪时间压缩率。我们的处理是把它们组织成有优先级的字典序，而不是拍脑袋加权求和：

  • 第一优先：出锅差 Γ。这是赛题明确"优秀"的指标，也是用户真实诉求。
  • 第二优先：总时长 T。
  • 第三优先：语义冷等待（保热）。
一个必须避开的建模陷阱

如果直接用"完成时刻"计算保热等待，求解器会学会"提前很久把菜做好然后干等"——实测中位数会恶化到 23 分钟。我们改用"最后一次进入加热设备结束"作为保热基准，并且以 Γ 计价（取保热等待与 Γ 预算的较小值），否则一道菜等 170 分钟就能夺走 Γ 的权重。

用户语义的作用。用户说一句"家里来客人，希望所有菜一起上桌"，系统会把它翻成"出锅差权重拉满"；说"赶时间，越快越好"，则翻成"总时长权重拉满"。实测（同一批 5 道菜、同一套求解器，只改这一句话）：

用户输入总时长出锅差
（无）72 分钟13 分钟
"家里来客人，希望所有菜一起上桌"91 分钟2 分钟
"赶时间，越快越好"72 分钟13 分钟

用 19 分钟总时长换回了 11 分钟出锅差，而且不是靠改代码，只靠一句话。

4.4 L4 动态重排与通知

本层要解决的是"计划赶不上变化"：用户临时加菜、设备突然故障、某一步实际耗时超出预估。

动态重排的两条硬要求

不推翻已完成步骤、重排后不新增冲突。我们的实现是硬冻结 + 姿态仲裁：已完成的步骤作为硬约束传给求解器，时间一格不动；由模型仲裁本次重排的姿态（最小扰动 / 重新对齐 / 保热优先），姿态决定候选策略的排序，但最终仍由求解器在多策略中择优。

"不劣化"如何证明

"重排后 Pareto 不劣化"这句话如果不写清楚基准就是空话——新增一道菜必然增加总工作量，"总时长不增"根本不可能成立。所以我们把它拆成两条当场可判真伪的断言：

  1. 已完成步骤零变动（硬保证，逐任务比对开始时刻）；
  2. 不劣于串行基线（基线 = 原计划不动 + 新菜整体串行接在末尾，这是一个必然可行的朴素解）。

三项指标（出锅差 / 总时长 / 连续手动）的前后涨跌如实列出，不粉饰。

设备故障的处理

临时把该设备容量置 0，相关任务按顶替关系改走灶具（蒸锅隔水蒸、煎制），顶替设备也不可用时才降级为人工操作。这里有一个并发陷阱值得一提——早期实现是改全局容量字典、排完再恢复，在线程池下两个并发请求会互相踩：A 请求把蒸箱置 0 排程期间，B 请求读到的蒸箱也是 0，于是 B 的计划里蒸箱凭空消失。现在改为请求级上下文覆盖，全局字典永不被改写。

通知生成

通知分四类节点，直接对应赛题原文的示例：

离线档走确定性模板（零延迟、可离线断言），在线档由模型语境化，失败自动回落模板。

六、创新点

本作品的创新集中在"模型与求解器如何协作"这一层，具体有六点：

  1. 模型与求解器的职责切分，并用离线预热解耦。模型负责语义与决策、求解器负责约束与最优性；模型产物离线算好落盘，在线零延迟。这使系统同时具备"模型在环"的智能与"评审机可复现"的确定性。
  2. 三轨取优 + 独立校验的求解架构。贪心 / CP-SAT / 精确模型三条轨按（Γ, T）字典序取优，任何单轨失效系统仍出合法解；返回前由独立校验器复验冲突与依赖。
  3. 保热项以 Γ 计价的有界建模。避免了"用完成时刻算保热"导致的求解器被奖励"早做熟干等"，也避免了无界保热项夺走出锅差的权重。
  4. 可验证的"不劣化"保证。把"Pareto 不劣化"拆成两条当场可判真伪的断言（已完成步骤零变动 + 不劣于串行基线），而不是一句无法证伪的口号。
  5. 请求级资源覆盖消除并发竞态。设备故障与厨房配置覆盖均走请求级上下文，全局容量字典永不被改写，同一份输入可复现同一份计划。
  6. 以人工标注集把"解析准确率"从自证变成可测。20 道菜 / 148 步人工标注（只依据原文），五项指标逐项对照，并给出准确率下限护栏，防止后续改动静默退化。

七、局限与后续工作

我们如实列出当前已知的不足：

  1. L1 仍有 4 类解析残留：少量纯装载 / 取放句被判成设备作业，造出时长靠猜的虚假占用；「水箱 / 加水」被当作蒸箱信号，而方太蒸烤一体机的烤菜同样需要加水，导致部分烤菜被判成蒸箱；少量真实设备步被"纯装载句"守卫误抹；合成预热步插入后，后置步漏了对它的依赖（当前影响 2 道菜）。
  2. 出锅差优秀率 82%：蒸箱与烤箱各仅 1 台，是物理硬瓶颈；剩余 18% 的组合（多为两道菜同时需要蒸或烤）无法做到同时出锅。
  3. 七类设备中三类当前空置：官方 100 道菜里"洗碗机 / 烟机"出现 0 次，"净咖一体机"仅作为食材来源（"加纯净水"）被提到，因此这三类设备的容量虽已在册，但没有任务使用。
  4. 菜谱库边界：官方给定的 100 道菜为只读基线；超出该库的菜名需要调用方随请求提供步骤，否则接口会显式返回 422，而不是给出一份残缺计划。

后续工作的优先级：先修 L1 的设备判定（尤其"水箱"信号与纯装载句的边界），再考虑把出锅差优秀率从 82% 往上推——后者受限于物理设备数量，空间有限。
