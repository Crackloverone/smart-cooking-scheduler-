## 1. P-01 手机端 UI 界面操作不便

### 1.1 问题描述

界面为纯桌面布局，在手机上三栏被硬压进窄屏，文字与控件互相挤压；甘特条等关键控件靠鼠标事件驱动，触屏下既难点中也拖不动。

### 1.2 根因定位（代码事实）

| 事实 | 位置 | 后果 |
|---|---|---|
| 响应式断点数量 = **0**（全文件 `@media` 出现 0 次） | `app/web/index.html` | 任何屏幕宽度都套用桌面栅格，无单列降级 |
| `.grid3{grid-template-columns:260px 1.8fr 260px}` | `:54` | 两侧列**固定 260px**，共 520px；390px 手机屏装不下 |
| `#v-plan .grid3{grid-template-columns:260px minmax(0,1.8fr) 260px}` | `:245-246` | 排程页同样固定 260px 侧列，中列（甘特图）被压到极窄 |
| `.grid2{grid-template-columns:1fr 1fr}` | `:55` | 档案/设备页固定双列（档案已删，现只剩设备页） |
| `.view{max-width:1440px;padding:28px 16px 48px}` | `:50` | 移动端左右仅 16px 内边距，纵向留白也按桌面给 |
| `.menu` 单行 7 个按钮（主页/排程/对话/菜谱/设备/档案/记录）—— **现为 5 个** | `:352-359` | 窄屏下导航拥挤或换行错位 |
| 触控事件绑定数量 = **0**（无 `touchstart` / `pointerdown` / `touchmove`） | 全文件 | 触屏手势完全没处理 |
| 甘特条拖拽只绑 `mousedown / mousemove / mouseup` | `:842-858`（`bindDrag`） | 触屏拖不动；且 `e.preventDefault()` 会与页面滚动抢手势 |
| 点击目标偏小：`.sbar{height:30px}`、`.vbtn{padding:6px 18px;font-size:12px}`、`.item{padding:10px 12px;font-size:13px}`、`.menu button{padding:9px 18px}` | `:141` / `:156` / `:166` / `:42` | 均 < 44×44 CSS px，手指易误触 |
| 大量 `:hover` 承载交互反馈（`.menu button:hover`、`.card:hover`、`.item:hover`、`.vbtn:hover`、`button:hover`、`.fab:hover` 等 10+ 处） | 多处 | 触屏无 hover 态，用户得不到"这里可以点"的反馈 |

### 1.3 影响范围

- 全部 7 个视图（`home / plan / chat / recipes / devices / profiles / history`）在手机端均受影响；
  **2026-10-02 收敛为 5 个**（`home / plan / recipes / devices / history` —— 对话并入悬浮球、档案删除）；
- 影响最重的是**排程视图**：三栏中"选菜 / 甘特图 / 通知与重排"三块都不可用，等于移动端无法完成主任务；
- 甘特图在移动端不仅窄，而且**不可拖拽**，播放条拖动体验也未针对触屏优化。

### 1.4 复现条件

1. 手机浏览器或桌面浏览器开发者工具切到 390×844（iPhone 14 档）打开 `/app`；
2. 进入「智能排程」，观察三栏被压扁、甘特条宽度不足、按钮密集；
3. 手指点击甘特条并尝试横向拖动 → 无响应或触发页面滚动。

> 复现工具：项目已有真实浏览器探针 `scripts/ui_layout_probe.mjs`，支持 `VP=390x844` 换视口。
> **注意**：该探针目前只校验"不溢出/不压扁/不重叠"，**量不出"挤但没坏"**。P-01 需要补充"点击目标尺寸"与"单列降级"两类断言，不能只看现有绿灯。

### 1.5 预期修复结果（可验收）

1. **布局**：新增响应式断点（建议 `≤640px` 手机、`641–1024px` 平板）。手机端 `grid3 / grid2` 一律降级为**单列**，纵向堆叠；排程页在手机上按「选菜 → 甘特图 → 明细 → 通知/重排」顺序排列。
2. **导航**：手机端导航改为可横向滚动或折叠菜单，**每个入口**均可达且不换行错位（当时 7 个，现 5 个）。
3. **触控**：所有可点元素有效点击区 **≥ 44×44 CSS px**（含 `.sbar`、`.vbtn`、`.item`、导航按钮）；甘特条拖拽改用 **Pointer Events**（`pointerdown/move/up`），并处理 `touch-action` 以免与滚动抢手势。
4. **反馈**：为触屏补齐非 hover 的可点性提示（如常态描边/图标），不依赖 `:hover` 传达可交互性。
5. **回归**：`VP=390x844` 与 `VP=1440x900` 两档都纳入回归；新增断言：①无横向溢出；②无点击目标 < 44px；③手机端栅格列数 = 1。

### 1.6 风险与边界

- 甘特图按时间比例渲染（`GANTT_PX_PER_MIN=34`，上限 1200px），手机上必然出现横向滚动 —— 这是**设计如此**（保证时间轴诚实），不要求压成屏宽，只要求滚动顺滑、首屏能看到泳道标签。
- 极短任务条仅约 5px 宽（`3%` 最小宽度兜底），手机上无法可靠点中。P-04 的"点击查看步骤"需要提供**替代入口**（如点击明细表行），不能只依赖甘特条。

## 2. P-02 远程访问时 LLM 无法正常使用

### 2.1 问题描述

本地运行正常，一旦部署到服务器/容器后远程访问，LLM 相关能力（自然语言排菜、AI 对话、通知语境化）整体失效或静默降级，界面无任何提示，用户无法判断原因。

### 2.2 根因定位（按可能性排序，均为代码事实）

| # | 根因 | 证据位置 | 说明 |
|---|---|---|---|
| ① | **容器镜像默认关闭 LLM** | `Dockerfile`：`ENV FT_LLM=off FT_AGENT_LLM=off` | 容器内所有 LLM 路径从启动起就被关闭，属**默认行为**而非故障 |
| ② | **`.env` 不进镜像 → 无密钥 → 静默离线** | `.dockerignore` 排除 `.env`；`llm.py:145-154` `enabled()` 在 `API_KEY` 为空时直接返回 `False` | 不报错、不重试，直接全链路规则兜底；用户侧只表现为"AI 变笨了" |
| ③ | **`start.bat` 只监听回环地址** | `start.bat:163`：`--host 127.0.0.1` | 局域网/手机**根本连不上**。注意：此条会让"整个页面打不开"，不只是 LLM；若用户描述的是"页面能开、只有 LLM 不行"，则根因在 ①/②/④ |
| ④ | **启动探测按 1.5s 紧预算，远端高延迟直接熔断** | `main.py:80-92`：`probe_budget = min(llm.TIMEOUT, 1.5)`，失败即 `llm.force_open("warmup")` | 远端主机到中转站 RTT 偏高时，探测超时 → 启动即熔断 `CB_COOLDOWN`（默认 120s）；期间所有调用零延迟返回 `None` |
| ⑤ | **前端零可观测性** | `/schedule` 已返回 `agent.llm.{enabled, breaker_open, breaker_reason, breaker_until, stats}`（`main.py:410-420`），而 `index.html` 中引用次数 = **0** | 后端已经报出"为什么没用上模型"，前端一个字段都没展示 |

> 排除项：**不是 CORS**（`FT_CORS_ORIGINS` 默认 `*`，`main.py:106-111`）；**不是前端直连模型**（调用全在服务端）。

### 2.3 影响范围

- `/api/agent_plan`（一句话排菜）→ 退化为规则选菜；
- `/chat` AI 对话 → 退化为固定话术；
- `/schedule` 的通知语境化 → 退化为模板文案；
- `app/agent/orchestrator` 的策略择优与反思 → 跳过模型环节。
- 系统整体**仍能出排程**（这是既有的降级设计，属优点），但用户会认为"AI 功能坏了"，且无从判断是配置问题还是模型故障。

### 2.4 复现条件

- 路径 A（配置缺失）：`docker build` 后运行容器，不注入任何 LLM 环境变量 → 观察 `/schedule` 响应中 `agent.llm.enabled === false`。
- 路径 B（延迟熔断）：远端主机部署，令 `FT_LLM_TIMEOUT=3.0`（默认）而中转站单次响应 > 1.5s → 启动日志出现"启动探测: 模型不可用或超出在线预算(1.5s), 已预先熔断"。
- 路径 C（未配置密钥）：`.env` 未随部署包下发 → `API_KEY=""` → `enabled()` 恒为 `False`。

### 2.5 预期修复结果（可验收）

1. **配置显式化**：部署文档与启动脚本给出 LLM 所需环境变量清单（`FT_LLM_PROVIDER / FT_LLM_BASE_URL / FT_LLM_API_KEY / FT_LLM_MODEL / FT_LLM`），并明确"容器默认离线"是**有意为之**，需主动开启。
   > 2026-10-04 更新：默认 provider 已换成**本地 Ollama**（免密钥），
   > `FT_LLM_API_KEY` 只在 `FT_LLM_PROVIDER=openai` 时才是必填项。
   > 清单与自查项见 `docs/部署文档.md` §4.1 与 `.env.example` 末尾。
2. **状态可观测**：新增只读接口（如 `GET /api/llm_status`）返回 `{enabled, breaker_open, breaker_reason, breaker_until, stats}`；界面顶栏或设置页展示状态徽标，三态可辨：**在线可用 / 熔断中（含原因与剩余时间）/ 已关闭或未配置**。
3. **首次降级有提示**：当一次排程因 LLM 不可用而降级时，界面给出**一次性**非阻塞提示（说明"本次为规则模式，原因：额度/网络/未配置"），不重复打扰。
4. **探测预算可配**：`FT_WARM_LLM_BUDGET` 允许远端部署放宽；或允许远端场景 `FT_WARM_LLM=off` 跳过启动探测、由首个真实请求决定。
   > 2026-10-04 更新：默认值改为**按 provider 分流** —— 远端 `1.5s`（保持原判据：
   > 单次 >1.5s 本来也落不进 <5s 评分线），本地 Ollama `60s`（首次调用要把权重
   > 读进显存，实测 ≈10s；用 1.5s 必然失败 ⇒ 每次启动自我熔断）。
   > 见 `app/agent/llm.py::_DEFAULT_WARMUP` 与 `tests/test_warmup_probe.py`。
5. **监听地址可配**：`start.bat` 增加 `--host` 参数（默认仍为 `127.0.0.1`，避免默认对外暴露），并在帮助文本中说明局域网访问用法。

### 2.6 风险与边界

- 放宽探测预算会**牺牲首请求耗时**（`<5s` 是硬性性能线）。二者需权衡：建议**仅在显式配置时才放宽**，默认维持现状。
- 熔断是**保护机制**，不要为了"让 LLM 看起来可用"而移除它；要修的是**可观测性与配置引导**，不是熔断策略本身。

## 3. P-03 支持删除健康档案 → **整条链路已下线**（2026-10-02）

> **本节结论：需求前提消失，功能整体删除。**
> 2026-10-01 按本文实现过"档案删除/恢复"（用户层文件 + 软删除 + 开关）；
> 2026-10-02 用户指令"档案站点没有用可以删除了"，且明确选择**前端 + 后端 + 数据一起删**。
> 现在 `v-profiles`、`/api/profiles` 三条接口、`FT_ALLOW_PROFILE_WRITE`、
> `data/profiles.json`(50 条) 与 `data/profiles_user.json` **全部不存在**。
> 下表保留为历史记录，供理解当时的决策依据。

### 3.1 原始问题描述

健康档案只能查看与搜索，没有任何删除入口；用户无法移除不再需要的档案。

### 3.2 当时的现状定位（代码事实，现已全部作废）

| 项 | 位置 | 当时现状 |
|---|---|---|
| 后端接口 | `main.py` `GET /api/profiles` | **仅只读**。全仓无 `POST/PUT/DELETE /api/profiles` |
| 数据文件 | `data/profiles.json` | **50 条**，`id` 为 1..50，含性别/年龄/劳动强度/特殊人群/孕周期/口味偏好/过敏食材/健康需求/身高/体重/BMI/体检指标 |
| 读取方式 | `_load_json_cached` | 按 **mtime 失效**缓存 → 写回文件后缓存自动失效 |
| 前端 | `index.html` `v-profiles` 视图 + `loadProf` / `loadProfDetail` | 无任何删除控件 |
| 关联依赖 | 全仓检索 | 只有 `/api/profiles` 读该文件；排程链路不依赖档案 |

### 3.3 当时定死的三个决策（**本轮菜谱库 CRUD 原样沿用**）

> 这三条口径经受住了检验 —— 2026-10-02 的菜谱库增删改查**逐条照搬**，只换了对象。

1. **删的是哪份数据？** 官方数据是**随包发布的样例数据集**，硬删会破坏原始数据且无恢复途径。
   → **只读基线 + 用户层**：官方文件永不改写，用户改动只写 `data/*_user.json`，展示时合并。
   （档案层是 `profiles.json` + `profiles_user.json`；菜谱层是 `recipes_official_100.csv` + `recipes_user.json`。）
2. **谁有权删？** 无鉴权时任何能打开页面的人都能删。
   → **写开关 + 二次确认**：档案是 `FT_ALLOW_PROFILE_WRITE`，菜谱是 `FT_ALLOW_RECIPE_WRITE`（**均默认开启**；设 `off` 时返回 403 并说明，前端入口同步隐藏）；删除**必须**有二次确认。
3. **并发写怎么处理？**
   → **原子写**：临时文件 + `os.replace()`，并显式失效缓存。

### 3.4 当时的验收用例（历史，已随功能删除）

| 步骤 | 期望 |
|---|---|
| 删除 `id=1` | 总数 50 → 49，列表少一行，详情区清空 |
| 刷新页面 / 重启服务 | 仍为 49 |
| 删除不存在的 `id=9999` | 不报 500，数据不变 |
| 关闭写开关后删除 | 403，数据不变 |
| 恢复（软删除/用户层方案） | 回到 50 |

### 3.5 本轮替代：菜谱库增删改查

需求、接口、数据纪律与实测见 **§0.2 三**。与 P-03 的关键差异只有三处：

| 差异点 | 档案（旧） | 菜谱（新） |
|---|---|---|
| 删除语义 | 只有软删（可恢复） | **按来源分**：官方菜 → 墓碑软删（可恢复）；**自建菜 → 真删**（否则留下"谁也看不见、也恢复不了"的墓碑垃圾） |
| 对排程的影响 | 无（排程不读档案） | **有**：新增的菜必须能排进甘特图 ⇒ `adapter` 缓存改为按 `recipe_store.version()` 失效 |
| 恢复不存在的记录 | 静默 `deleted: 0` | **404**（不许静默成功） |

## 3A. P-08 菜谱库只有 2000 道样例数据、且不可增删改（2026-10-02 新增）

> 编号跳过 P-06/P-07：那两条（前端访问令牌、列表口径）在 `tests/test_product_fixes.py` 里已落地并有护栏，

### 3A.1 问题描述

菜谱库只有查看与搜索：**不能新增、不能改、不能删**。用户想把自己常做的菜加进排程，

| 4 | 2000 道数据的步骤无编号 | `demo_schedule` 曾试图改读它，结果"整道菜只切出 1 步" |

2. 提供 `POST / PUT / DELETE /api/recipes[/{id}]` + `POST /api/recipes/{id}/restore`，见 §0.2 三。

4. 新增的菜**能直接排进甘特图**（缓存按版本失效）。
5. 前端菜谱库提供「+ 新增 / 编辑 / 删除 / 显示已删除 / 恢复」，删除有二次确认且**说清能否恢复**。
6. 角标口径正确：搜索态报「匹配 M 道 / 库中 N 道」，非搜索态报「共 N 道」。

### 3A.4 验收用例

|---|---|
| 打开菜谱库 | 角标「共 100 道」，列表 100 行 |
| 新增一道菜 | 角标 101；详情切到新菜；**排程页能选中并排出甘特条** |

| 关闭 `FT_ALLOW_RECIPE_WRITE` | 写操作 403，数据不变 |

## 4A. P-05 后端不可达时界面永远停在「加载中...」

> 这一条是 **P-01～P-04 落地后由实际使用反馈新增的**（用户直接双击 `index.html`
> 或从静态预览打开时，左侧菜谱列表一直显示「加载中...」，右上角显示「状态未知」）。

### 4A.1 问题描述

打开界面后，左侧「选择菜品」列表永远停在初始占位符 **「加载中...」**，
右上角模型徽标显示 **「○ 状态未知」**，但页面不报任何错、也不提示该做什么。
用户无法区分"还在加载"和"已经失败"，只能一直等。

### 4A.2 根因定位（代码事实）

| # | 事实 | 位置 |
|---|---|---|
| 1 | 页面是**薄客户端**：菜谱 / 设备 / 排程 / 记录全部来自 FastAPI，前端只做渲染 | `app/web/index.html` 中 18 处 `fetch('/api/…')` |
| 2 | 后端入口是 `http://127.0.0.1:8137/app`（`start.bat` 会自动打开它）；`/` 是重定向到 `/docs` | `app/api/main.py:888`、`start.bat:167` |
| 3 | **两种必然失败的打开方式**：① 双击 `index.html`（`file://`）⇒ 相对路径 `/api/*` 解析成 `file:///api/*`；② 从静态预览/静态服务器打开 ⇒ 有 HTML 但没有后端 | — |
| 4 | `loadRecipes()` 的 `await fetch(...)` **没有 try/catch**，失败直接 reject ⇒ 占位符永远停在「加载中...」 | `index.html` 原 `loadRecipes()` |
| 5 | `refreshLlmStatus()` 有 try/catch，但 catch 里写的是含糊的「状态未知」——把"连不上"说成了"不知道" | `index.html` 原 `refreshLlmStatus()` |
| 6 | 同类问题存在于 `loadLib` / `loadDetail` / `loadDevices` / `loadHist` —— 每个视图都可能各自"永远转圈" | 同上 |

**结论：这不是后端故障，是前端缺失败态。** 后端没起、或页面用错方式打开时，
前端必须自己把这件事说清楚。

### 4A.3 影响范围

- 首次接触项目的用户 100% 会踩到（"双击 HTML"是最自然的动作）。
- 表现具有强误导性：看起来在加载 ⇒ 用户等而不是查。
- 每个数据视图各有一份独立的失败路径，修一处不能覆盖全部。

### 4A.4 复现条件

1. 不起后端，直接双击 `app/web/index.html`；或
2. 用任意静态服务器托管 `app/web/` 后打开 `index.html`。
⇒ 左侧列表恒为「加载中...」，徽标恒为「状态未知」，控制台只有 fetch 失败。

### 4A.5 预期修复结果（已实现）

| 机制 | 实现 |
|---|---|
| **统一请求出口** | `apiFetch(url, opts)` —— 全文件只允许存在 **1 处** `fetch(`，就在它内部。漏一处就会出现"某个视图永远转圈"，且只在那个视图复现 |
| **区分两类失败** | `fetch` **reject** ⇒ 后端不可达 ⇒ 弹横幅 + 抛错；**HTTP 4xx/5xx** ⇒ 后端是活的 ⇒ 原样返回 `r`，由调用方按自己的语义处理（**保住 P-03 的 403「写入已关闭」提示**） |
| **失败态可见** | `markBackendDown()`：① 显示 `#offlineBar` 横幅；② 把所有仍是「加载中...」的占位替换为「后端未连接」；③ 徽标改为「○ 后端未连接」 |
| **`file://` 专门提示** | `backendHint()` 识别 `location.protocol==='file:'`，直接给出"双击 `start.bat`，再访问 `http://127.0.0.1:8137/app`" |
| **可恢复** | 横幅带「重试」按钮 ⇒ `retryBackend()` 重新拉当前打开的视图；任一请求成功即 `markBackendUp()` 自动收起横幅 |
| **徽标不覆盖** | `refreshLlmStatus()` 的 catch 增加 `if(BACKEND_DOWN)return;`，不再把「后端未连接」盖回「状态未知」 |

### 4A.6 验收用例

| 用例 | 期望 |
|---|---|
| 后端未起，打开页面 | 横幅出现，文案含 `start.bat` 与 `127.0.0.1:8137/app`；列表显示「后端未连接」（**不含**「加载中」）；徽标显示「○ 后端未连接」 |
| 后端恢复后点「重试」 | 列表渲染出真实菜谱行；横幅自动收起 |
| 切到菜谱库 / 设备 / 记录 | 各自都不再停在「加载中...」 |
| 服务端 `FT_ALLOW_RECIPE_WRITE=off` 下写菜谱 | 仍弹「删除失败: …」（403 的详细原因），**不被误报成"连不上后端"** |
| 全场景 | 无未捕获 JS 异常 |

### 4A.7 风险与边界

- 横幅用 `position:fixed`（与 `.llm-toast` 同理）：排程页高度是三列 flex 算出来的，
  往流内插元素会触发整页重算。
- `apiFetch` **只**负责网络层失败。把 HTTP 4xx 也当成"后端挂了"会掩盖真实错误原因
  —— 这条已写进护栏（`test_http_error_is_not_mistaken_for_backend_down`）。
- 静态预览/`file://` 下**排程功能本质不可用**（算法在服务端），修复只是把这件事
  说清楚，不是让静态页面能跑起来。
