## 一、环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Windows 10/11 · Linux · macOS | 主开发环境为 Windows；Linux/macOS 命令差异在文中标注 |
| Python | **3.11+**（实测 3.11 / 3.13 均可） | `start.bat` 优先用 `py -3`，回落到 `python` |
| 内存 | ≥ 1 GB 可用 | OR-Tools CP-SAT 求解 5 菜实例峰值 < 200 MB |
| 磁盘 | ≥ 300 MB | 依赖约 200 MB（OR-Tools 占大头），代码与数据 < 20 MB |
| CPU | 任意 x86-64 / ARM64 | CP-SAT 支持多线程，但本项目单次求解预算仅 1.5 s，单核足够 |
| 网络 | **可选** | 系统对网络零依赖；仅"在线模型决策"与"离线预热"需要外网 |
| 端口 | 默认 **8137**（Docker 内 **8000**） | 可配置，见 §四 |

**核心依赖**（`requirements.txt`，共 5 个）：

```
fastapi>=0.110
uvicorn[standard]>=0.29
pydantic>=2.0
ortools>=9.10          # 唯一的重依赖，提供 CP-SAT 求解器
pytest>=8.0            # 仅用于自检
```

> 仓库**没有**任何代码 import `httpx`。接口体检（`scripts/api_probe.py`）走的是"直接调用路由函数"，
> 不需要 `fastapi.testclient.TestClient`。因此 `httpx` 不在依赖里 —— 少装一个用不上的包。

## 二、快速部署

### 2.1 Windows 一键（推荐）

双击 `start.bat`。它会依次完成：

```
[0/4] 检查/创建 .venv            (py -3 -m venv .venv，失败回落 python -m venv)
[1/4] 检查/安装依赖              (import fastapi,uvicorn,pydantic,ortools 失败才装)
[2/4] 离线自检                   (python tests/test_core.py)
[3/4] 设置模型开关               (默认在线；--offline 强制离线)
[4/4] 检查端口占用 → 启动服务 → 打开浏览器
```

可选参数（可组合）：

| 参数 | 作用 |
|---|---|
| `--fast` | 跳过依赖检查与自检，直接起服务 |
| `--offline` | 强制 `FT_LLM=off`，全程不联网 |
| `--no-browser` | 不自动打开浏览器 |
| `--port 8138` | 换端口（默认 8137） |

> **评审/演示环境建议**：`start.bat --offline`。这样启动阶段不会去探测模型，
> 首个请求的耗时就是稳态耗时（实测 ~110 ms）。

### 2.2 手动部署（Windows / Linux / macOS 通用）

```bash
# 1) 建虚拟环境
python -m venv .venv

# 2) 激活
#    Windows (cmd)      .venv\Scripts\activate
#    Windows (bash)     source .venv/Scripts/activate
#    Linux / macOS      source .venv/bin/activate

# 3) 装依赖
pip install -r requirements.txt

# 4) 自检（297 项，完全离线）
python -m pytest tests/ -q

# 5) 起服务
python -m uvicorn app.api.main:app --host 127.0.0.1 --port 8137
```

**对外提供服务**时把 `--host` 改成 `0.0.0.0`：

```bash
python -m uvicorn app.api.main:app --host 0.0.0.0 --port 8137
```

## 四、配置项

全部通过**环境变量**或项目根目录的 **`.env`** 文件配置。`.env` 的写法：

```bash
cp .env.example .env      # Windows: copy .env.example .env
```

**优先级**：已存在的环境变量 > `.env.local` > `.env` > 代码默认值。
（`.env` / `.env.local` 只在键不存在时写入 `os.environ`，不会覆盖已有变量。
两个文件的分工：`.env` 放非敏感配置、可随项目走；`.env.local` 放凭据、单独排除。）

> **安全**：`.env` 与 `.env.local` 都已被 `.dockerignore` 与 `.gitignore` 排除，
> **源码里没有任何凭据**。请勿把 `.env*` 提交到仓库或打进镜像。

### 4.1 模型服务（默认：本地 Ollama）

默认档位是**本地 Ollama**，免密钥，装好就能用：

```bash
ollama pull qwen2.5:7b     # 7.6B / Q4_K_M，约 4.7GB；首次跑之前必须先拉模型
ollama list                # 确认已下载
```

| 变量 | 默认（`ollama` 档） | 说明 |
|---|---|---|
| `FT_LLM_PROVIDER` | `ollama` | `ollama` = 本地（免密钥）；`openai` = 任意 OpenAI 兼容端点（需密钥） |
| `FT_LLM_BASE_URL` | `http://127.0.0.1:11434/v1` | OpenAI 兼容的 `/chat/completions` 端点 |
| `FT_LLM_MODEL` | `qwen2.5:7b` | 模型名。`ollama list` 里的名字要完全一致 |
| `FT_LLM_API_KEY` | 空 | **`ollama` 档留空是正常的**；`openai` 档留空 = 完全离线 |

> ⚠️ **端点与模型名是跨 provider 共用的环境变量，改档必须成套改。**
> 只把 `FT_LLM_PROVIDER` 改成 `ollama`、却留着远端的 `BASE_URL` / `MODEL`，
> 请求会带着远端模型名（如 `gpt-5.6-sol`）打到本机 11434 端口，Ollama 返回
> `404 model not found`，而所有调用点都是**静默降级** —— 现象是"换成本地模型之后
> AI 完全不工作"，日志里没有任何报错。`llm.py` 对此有一条启动期 warning 兜底
> （"端点不像本地地址"），看到它就说明档位配串了。

切回远端 OpenAI 兼容端点（中转站 / 云厂商）：

```bash
FT_LLM_PROVIDER=openai
FT_LLM_BASE_URL=https://your-endpoint/v1
FT_LLM_API_KEY=sk-...
FT_LLM_MODEL=你的模型名
```

> **容器里用不了宿主机的 Ollama**：容器内的 `127.0.0.1` 指向容器自身。
> 要用宿主机的 Ollama 得把端点换成 `host.docker.internal:11434`
> （Linux 还需 `--add-host=host.docker.internal:host-gateway`），并让 Ollama
> 监听 `0.0.0.0`（`OLLAMA_HOST=0.0.0.0:11434` 后重启）。镜像里也没有模型权重。

#### 4.1.1 在界面上切换接入方式 / 换模型（推荐）

不改环境变量也能切换：Web 界面顶栏 **设置 → 模型接入**。

| 控件 | 作用 |
|---|---|
| **接入方式**（下拉） | `本地 Ollama（免密钥）` / `远程 OpenAI 兼容端点（需密钥）`。选项由后端 `/api/model_settings` 的 `providers` 下发，前端不自己写一份 |
| **远程接口地址** | 仅远程档可见。必须 `http://` 或 `https://` 开头，保存时自动裁掉尾部 `/` |
| **远程 API Key** | 仅远程档可见，`type=password`。**留空 = 不修改**（见下方安全说明） |
| **本机已下载模型** | 仅本地档可见，列的是本机 `ollama list` |
| **模型 ID** | 两档共用。切换接入方式时会自动回填**该档上次用的模型** |

选好之后点「保存模型」才生效；只拨下拉**不会**改后端配置。

两种接入方式**各记一份模型**：在远程档填 `gpt-5.6-sol`、切回本地仍是你原来的
`qwen2.5:7b`，来回切不会互相覆盖。

| 界面显示 | 含义 | 想改的话 |
|---|---|---|
| `环境变量` | 被 `FT_LLM_MODEL` 钉死 | 删掉/改掉环境变量后重启（输入框会禁用并给出提示） |
| `设置文件` | 用的是设置页存的值 | 直接在界面上换 |
| `内置默认` | 谁都没设 | 直接在界面上换 |

写入落 `data/llm_settings.json`（**原子写**：临时文件 + `os.replace`）。这个文件是
**可选层** —— 缺失或损坏一律当 `{}` 处理，不会让服务起不来。结构：

```json
{ "provider": "ollama",
  "model": "qwen2.5:7b",
  "models":  { "ollama": "qwen2.5:7b", "openai": "gpt-5.6-sol" },
  "remote":  { "base_url": "https://your-endpoint/v1", "api_key": "sk-..." } }
```

> ⚠️ **密钥只存不回传。** `/api/model_settings` 是**无鉴权**的（本机演示、
> 发布出去的公开链接都能读），所以响应里只有 `remote.api_key_set: true/false`，
> **没有** `api_key` 字段，页面上也永远不回填密钥框。相应地：
> **密钥框留空 = 保持原值，不是清空** —— 否则用户每保存一次就抹掉一次自己的密钥。
> 密钥框在页面上始终是空的，占位文字会写"已配置（留空 = 不修改）"。
>
> `data/llm_settings.json` **不会**进 Docker 镜像（`.dockerignore`）也**不会**
> 进发布目录（`scripts/sync_publish.py` 的 `SKIP_NAMES`）—— 线上要配远程端点，
> 请在宿主机上设 `FT_LLM_API_KEY` 环境变量，或部署后在设置页里填。

> 保存成功后会**顺带重置熔断器与在线闭环闸门**，并**重算超时/探测预算的默认值**
> （远端档 20 s / 本地档 30 s）。不重置的话会出现"换成了更快的模型，闭环还是被挡着"
> ——熔断器记的是**上一个模型**的失败。
>
> 目标模型不在本机时界面会提示但**不阻断**（可能只是想先把配置写好）。
> 非法的模型名会被后端以 **400** 拒绝，**不会静默成功**。远程档不报"本机有没有
> 这个模型"——那个判据对远程没有意义（模型在中转站那边）。

### 4.2 开关

| 变量 | 默认 | 作用 |
|---|---|---|
| `FT_LLM` | `on` | 全局模型开关。`off` = 完全离线（**评测/无网环境推荐**） |
| `FT_AGENT_LLM` | `on` | 排程决策是否在线调模型（目标塑形/策略提议/反思/重排仲裁） |
| `FT_NOTIFY_LLM` | `on` | 通知是否走 LLM 语境化（失败自动回落模板） |
| `FT_WARM_LLM` | `on` | 启动时是否探测一次模型可用性 |
| `FT_AGENT` | `on` | `off` = 关闭 Agent 闭环，退回单策略求解器（**仅对照实验用**） |
| `FT_EXACT` | `on` | 精确模型轨总开关。`off` 回到旧的"贪心 + CP-SAT"双轨 |

### 4.3 超时与熔断

| 变量 | 默认 | 作用 |
|---|---|---|
| `FT_LLM_TIMEOUT` | `30`（本地）/ `20`（远端） | 单次模型调用超时（秒） |
| `FT_LLM_CB_THRESHOLD` | `3` | 连续失败几次后熔断 |
| `FT_LLM_CB_COOLDOWN` | `120` | 普通失败（超时/5xx）的熔断冷却（秒） |
| `FT_LLM_CB_QUOTA` | `1800` | 额度类失败（HTTP 429）的熔断冷却（秒），**且立即熔断不等阈值** |
| `FT_WARM_LLM_BUDGET` | `60`（本地）/ `1.5`（远端） | 启动探测预算（秒） |

> ⚠️ **`FT_LLM_TIMEOUT` 必须大于模型端的真实响应时间，否则调用会被静默截断。**
> 远端实测某推理型模型单次响应 **2.3~4.0 s**，而旧默认超时 3.0 s —— 于是大部分
> 调用都撞超时、被判成"模型不可用"，白白走规则兜底。**2026-10-03 接土豆中转站时
> 复测仍是 2.3~2.9 s**，因此远端档默认值已由 3.0 上调到 **20**。判断方法：直接量
> `llm.chat([{"role":"user","content":"ping"}])` 的耗时，取 P95 留 2 倍余量。
> 反过来说，**若模型单次响应就超过 ~1.5 s，它本来也落不进 <5 s 的评分线**
> （一次排程会发 1~2 次调用），此时更该用离线档而不是调大超时。
>
> ⚠️ **把 `FT_LLM_TIMEOUT` 放大不会拖慢排程。** `chat()` 取的是
> `min(调用方传入的 timeout, TIMEOUT * 3)` —— `orchestrator` 的闭环仍传 3.6 s /
> 2.5 s，与这个默认值无关。它只决定"不赶时间的调用（AI 对话 / 通知 / 离线预热）
> 愿意等多久"。

> ⚠️ **本地档的默认值是 30 s，不是 3 s，这是有意的。**
> Ollama 的**热态**只要 0.5 s，但权重被换出显存后**重新加载要 ~10 s**。
> 给 3 s 会把"模型好着、只是刚被换出"误判成故障 → 攒够 3 次失败 → 熔断 120 s，
> 于是本地模型"用着用着就永久降级成规则模式"。
> 这个默认值**不会拖慢 `/api/plan`**：真正在意延迟的调用方自己传更小的 timeout，
> `orchestrator` 的 `time_budget`（默认 3.6 s）已经把在线排程卡住了。

> **启动探测的判据是"能否在预算内返回"，不是"连不连得上"。**
> 预热走 `chat_json`（与 Agent 完全相同的调用路径）探一次。
> 预算**按 provider 分流**：
> - 远端档 **1.5 s** 的紧预算 —— 单次 >1.5 s 本来也落不进 <5 s 评分线；
> - 本地档 **60 s** —— Ollama 首次调用要把权重读进显存（实测 7B/Q4 ≈10 s），
>   用 1.5 s 探测必然失败 ⇒ **每次启动都自我熔断，本地模型等于永远用不上**。
>   这 60 s 同时起到"焐热模型"的作用：冷启动成本花在启动阶段，而不是让第一个
>   用户请求去承担。
> - 实际预算取 `min(FT_LLM_TIMEOUT, FT_WARM_LLM_BUDGET)` —— 探测预算不该超过
>   单次调用超时，否则"探测通过"就是假话（真调用一样会超时）。
>
> ⚠️ **探测超时后"熔断"还是"只关闸门"，取决于预算有多紧**（`llm.probe_miss_is_fatal()`）：
> - **宽预算档**（本地 60 s）：连它都答不出来 = 模型没装 / 服务没起 ⇒ 直接
>   `force_open("warmup")` 熔断，把代价留在启动而不是第一个真实请求上
>   （实测首个 `/schedule` 会从 0.15 s 变成 6.7~7.8 s）。
> - **紧预算档**（远端 1.5 s）：超时只说明"比在线闭环那几秒的预算慢"，**不说明
>   服务坏了**。远端实测单次往返 2.3~2.9 s，**必然**超这个预算 —— 若照旧熔断，
>   每次重启都会把 **AI 对话** 一起关掉 120 s，而那恰好是用户第一次点它的时刻。
>   所以只落在线闭环闸门（`mark_online_too_slow`）：排程立刻改走规则（不再白等），
>   对话 / 通知照常用模型。
> 这两点都踩过坑，回归用例见 `tests/test_warmup_probe.py`。

### 4.4 求解预算（一般不需要改）

| 变量 | 默认 | 作用 |
|---|---|---|
| `FT_AGENT_BUDGET` | `3.6` | 闭环总预算（秒）。超预算立刻收敛，绝不硬等模型 |
| `FT_EXACT_BUDGET` | `1.5` | 精确模型轨时间预算（秒）。闭环还会用 `min(1.5, 剩余预算)` 再收一次 |
| `FT_EXACT_SLACK` | `15` | 精确轨 ε-约束的松弛量。**给 0 会把对齐出锅时刻的余量也掐死**（实测出锅差 3 → 44 min） |
| `FT_EXACT_PREP` | `both` | 备菜口径：`both` 两变体取优 / `off` 严格跟随策略 / `on` 只用备菜变体 |
| `FT_ALIGN_SLACK` | `0` | 出锅对齐允许超出最晚出锅时刻的分钟数（实测 0 最优） |
| `FT_REPLAN_BUDGET` | `2.5` | 动态重排的闭环预算（秒），比赛题 3 s 优秀线留足余量 |
| `FT_CPSAT_GAP_COEF` | `0.25` | CP-SAT 目标里出锅差的放大系数 |

## 五、离线运行（评审机 / 无外网环境）

**这是推荐的部署姿态。** 系统在设计上把"模型参与"和"网络依赖"解耦了：

- 语义先验、参数补全、组合策略结论**离线算好落盘**（`data/llm_agent_cache.json`）；
- 在线排程**只读缓存**，模型决策 **0 延迟、0 网络依赖**。

### 5.1 启动方式

```bash
# 方式 A：start.bat 参数
start.bat --offline

# 方式 B：手动设环境变量
FT_LLM=off FT_AGENT_LLM=off FT_NOTIFY_LLM=off FT_WARM_LLM=off \
  python -m uvicorn app.api.main:app --host 0.0.0.0 --port 8137
```

`FT_LLM=off` 时 `llm.enabled()` 直接返回 `False`，**不会发起任何网络请求** ——
既不会白等超时，也不需要熔断介入。

### 5.2 实测：模型不可用时的表现

中转站返回 `429 今日 token 额度已用完` 后，50 组基准的**全部质量指标与耗时没有任何变化**：

| 指标 | 模型可用 | 模型 429 |
|---|---|---|
| 出锅差 <5min 占比 | 90% | **90%** |
| 总时长 均值 | 74.8 min | **74.8 min** |
| 排程耗时 均值 | 131 ms | **131 ms** |

即：**系统对模型可用性零依赖**。模型在环提升的是决策质量，不是可用性前提。

## 七、离线预热（可选：开启完整模型能力）

如果希望"模型在环"真正生效（语义先验 + L1 参数补全 + 组合策略结论），
**在部署阶段**跑一次预热，之后在线路径全程只读缓存：

```bash
# 本地 Ollama 档：先把服务起起来、模型拉下来（见 §四 4.1），无需任何密钥
# 远端 openai 档：需要配置 FT_LLM_PROVIDER=openai + FT_LLM_API_KEY（见 §四）
python -m scripts.warm_cache               # 100 道菜的语义先验 + 参数补全
python -m scripts.warm_cache --combos 30   # 额外预热 30 组常见组合的策略结论
python -m scripts.warm_cache --force       # 忽略已有缓存，重新问模型
```

产物：`data/llm_agent_cache.json`。当前仓库内已有 **97 条**（46 条语义先验 + 51 条参数补全）。

> 预热脚本会把 `FT_LLM_TIMEOUT` 提到 20 s、把熔断阈值提到 999 ——
> 预热是离线动作不赶时间，且**中途不该被熔断打断**；在线路径仍按 provider 走
> 各自默认值（本地 30 s / 远端 3 s）。20 s 对本地冷启动（≈10 s）留了一倍余量；
> 若你用的是 14B 以上的大模型，用 `FT_LLM_TIMEOUT=60 python -m scripts.warm_cache` 覆盖。
> 这两个环境变量必须在 import `app.agent.llm` **之前**设置，脚本内部已处理。
>
> **缓存的键不含模型名**（`prior::<菜名>` / `enrich::<菜名>`），所以换模型**不会**
> 让已有先验失效 —— 语义先验是"这道菜该怎么排"的知识，与用哪个模型问出来无关。
> 反过来，若你确实想用新模型重算，用 `--force`。

**没有预热也能跑**：未命中缓存的菜自动回落到规则先验（`source="rule"`），
功能完整，只是决策质量略低。

## 九、常见故障排查

### 9.1 端口被占用

```
[Errno 98] Address already in use    /    [WinError 10048]
```

- Windows：`start.bat --port 8138`，或先 `netstat -ano | findstr :8137` 找到 PID 再 `taskkill /F /PID <pid>`
- Linux/macOS：`lsof -i :8137` 或 `ss -lptn 'sport = :8137'`

`start.bat` 已内置端口检查，会提示占用进程并询问是否结束。

### 9.2 `start.bat` 报 `'p65001' is not recognized` / 乱码 / 语法错误

`.bat` 文件被编辑器存成了 **LF 换行**或加了 **BOM**。修复：

- 用 `start.bat` 的原始版本（仓库内文件是 **纯 ASCII + CRLF**）；
- 若要自己改，**只能写 ASCII**，不要写中文 —— cmd.exe 按当前代码页分块读取 `.bat`，
  `chcp 65001` 只在中途生效，多字节字符会导致字节错位、把半行当命令执行。
  中文输出请交给 Python（脚本已设 `PYTHONUTF8=1`）。

> 根目录的 `start.bat.bak` / `start.bat.utf8` 是排查过程中的历史副本，**不是运行所需文件**。

### 9.3 依赖安装失败

```
ERROR: Could not find a version that satisfies the requirement ortools>=9.10
```

- 确认 Python ≥ 3.11（`python --version`）；
- 国内网络慢时可换源：`pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple`；
- 确认虚拟环境已激活（`where python` 应指向 `.venv`）。

### 9.4 首个请求特别慢（3–4 s）

原因通常是**冷启动**：OR-Tools 首次 import 需要 2–3 s。
系统已在服务启动阶段（`lifespan` → `_warmup()`）完成三件预热：
导入 CP-SAT、跑一遍真实闭环、探测模型可用性。

如果仍然慢，检查是否被绕过：

- 直接用 `uvicorn app.api.main:app` 启动（走 `lifespan`）→ 正常；
- 在脚本里直接 `from app.spec.adapter import plan_recipes` 而跳过服务启动 → 会吃到冷启动。

**模型不可达时首个请求慢**：说明预热探测**没有把熔断器落定**，于是第一个真实请求
要自己攒够失败次数 —— 每次调用各等一次超时（实测首个 `/schedule` **6735~7813 ms**，
熔断打开后同一实例只要 **150~228 ms**）。

排查顺序（**别只看 `FT_WARM_LLM`**）：

1. 确认 `FT_WARM_LLM` 没被设成 `off`（设了就等于关掉探测）；
2. **确认模型端是不是"能连通但很慢"** —— 这是最容易漏的一种。实测该端点可连通，
   但单次响应 2.3~4.0 s > 旧默认超时 3.0 s，旧版探测（纯文本 `chat` + 3 s 预算）
   会报"模型可用"，首请求照样白等。现在探测已改成
   **`chat_json`（与 Agent 同路径）+ 按档位的预算**：
   - 本地档 60 s：答不出来 ⇒ 判成不可用并预先熔断；
   - 远端档 1.5 s：慢于预算 ⇒ **只关闭在线闭环**（AI 对话仍可用），
     因为"比闭环慢"不等于"服务坏了"。此时 `/schedule` 走规则，耗时是毫秒级。
3. 看服务端启动日志：宽预算档是 `启动探测: 模型不可用或超出预算(…)`，
   紧预算档是 `启动探测: 模型比 … 的预算慢(…)`；
4. 想彻底免掉这一项，直接用离线档：
   `FT_LLM=off FT_AGENT_LLM=off FT_NOTIFY_LLM=off FT_WARM_LLM=off`（首请求 ~150 ms）。

### 9.5 `/api/plan` 返回空计划 / 菜名未命中

- 检查菜名是否在 `GET /api/recipe_names` 里（**必须完全一致**，含括号与全角字符）；
- 菜名未命中时系统**只在服务端留日志，不污染响应结构**（响应仍是合法 schema）；
- 确认 `data/recipes_official_100.csv` 存在且为 `utf-8-sig`。

### 9.6 模型相关告警

| 现象 | 含义 | 处理 |
|---|---|---|
| `_LOG.warning: 自然语言选菜未拿到模型结果` | 模型失败，已回落规则选菜 | 无需处理；如需模型生效，查 `/api/llm_status` 的 `state` 与 `breaker_reason` |
| `_LOG.warning: FT_LLM_PROVIDER=ollama 但端点 … 不像本地地址` | 档位配串了（provider 与端点不配套） | 见 §4.1 的告警说明；要么把端点改回本地，要么设 `FT_LLM_PROVIDER=openai` |
| `_LOG.warning: 启动探测: 模型不可用或超出预算` | 启动阶段就探不通，已预先熔断（**宽预算档**） | 本地档看 Ollama 是否在跑、模型是否已 pull；远端档看 RTT 与 `FT_WARM_LLM_BUDGET` |
| `_LOG.warning: 启动探测: 模型比 … 的预算慢` | 只关闭了在线闭环，**AI 对话仍可用**（**紧预算档**，如远端 1.5 s） | 正常现象：远端 RTT 2.3~2.9 s 必然超 1.5 s。排程走规则（毫秒级），对话/通知照常用模型。想让闭环也硬试：`FT_LLM_ONLINE_GATE=off` |
| `/schedule` 响应里 `agent.llm.breaker_open = true` | 熔断已打开 | 看 `breaker_reason`：`quota`=额度耗尽（冷却 30 min），`error`=网络/5xx（冷却 2 min），`warmup`=启动探测未通过 |
| `/api/llm_status` 里 `state = "off"` | 显式关掉了，或（`openai` 档）没配密钥 | 看 `api_key_required`：`true` 才需要 `FT_LLM_API_KEY`；`false`（本地档）时"密钥未配置"是**正常**的 |

`/schedule` 的 `agent.llm` 字段把"模型到底用上没有、为什么没用上"显性化：

```json
"llm": { "calls": 1, "ms": 0.0, "enabled": true,
         "breaker_open": true, "breaker_reason": "quota",
         "stats": {"calls":1,"hits":0,"failures":1,"skipped":1,"rate_limited":1} }
```

### 9.7 测试失败

```bash
python -m pytest tests/ -q -x      # 首个失败即停，看完整堆栈
python tests/test_core.py          # 单文件形式（45 项）
```

若 `test_model.py` 失败且报求解超时，说明机器负载过高 —— 精确模型轨有 1.5 s 预算，
在 CPU 被抢占时会解不出来。重跑一次或降低并发即可。
