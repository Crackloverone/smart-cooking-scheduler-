## 1. 硬判据实验：算法是"时间不够"还是"本身次优"？

把同一套求解器的时间预算放大 20~40 倍（CP-SAT 20s / 精确模型 60s），看能否突破生产解：

```
生产解 vs 足预算解（10 组 seed=11）
#    P_T  B_T  ΔT      #    P_T  B_T  ΔT
4    54   65  -11     8    76  112  -36
1    64  108  -44     6    51  111  -60
...
有改进的组: 0/10
```

**0/10 有改进，且足预算解反而更差。** ⇒ 瓶颈**不是时间预算**，而是策略多样性
（生产跑 6 条策略 × 3 轨；单策略给再多时间也追不上）。
**结论：不存在"因为时间不够而次优"的问题。**

## 2. 漏洞 A/B：下界口径被两个静默缺陷压低

### A. 键类型错配 → 所有依赖边被丢弃

```python
# app/scheduler/model.py（旧）
"deps": [tuple(d.split("#")) for d in (t.depends_on or [])]
```

`ScheduledTask.step_id` 是 `int`，而 `str.split("#")` 产出**字符串**：
键 `("菜","3")` vs `("菜",3)` 永不相等 ⇒ `_critical_path` 内 `[d for d in deps if d in dur]`
**恒为空** ⇒ 关键路径退化成"最长单步时长"。

**实测**（5 菜：三味蒸鳗鱼&香茅烤鳗鱼同烹 / 油醋汁剁肉饼蒸和乐蟹 / 香辣烤小龙虾 / 红豆糯米糕 / 金银蒜蒸鸡胸肉）：
真实活跃关键路 **54**（=makespan）→ 报成 **18** ⇒ LB 27 ⇒ **gap 从 0% 虚报成 100%**。

### B. `等待`步被排除出关键路径

同一函数里 `t.unit_id not in ("等待","提前准备")` 一刀切。理由（不占机器/人手）
对 **批次机产能 / 人工总工时** 成立，对**关键路径不成立**：腌制/浸泡/放凉是
**真实流逝的时间**，而且是依赖链上的节点。摘掉它等于把链切断（54 → 25）。

### 为什么长期潜伏

| 旧护栏 | 为什么抓不到 |
|---|---|
| `test_critical_path_parallel_branches_not_sum` | 自造 dict，键类型**本来就匹配**，走不到转换那行 |
| `test_lower_bound_from_plan_never_exceeds_makespan` | 只断言 `lb <= makespan`，下界被低估时**恒真** |
| `lb_probe` | 只报数，从不与"手算关键路"对照 |

### 修后：真实最优性

```
lb_probe 60 组 seed=11
gap 中位 0.0%   均值 2.2%   p90 8.7%   max 34.8%
makespan == 可证下界: 43/60（72%）    下界违反: 0
```

剩余 gap 的来源（**不是算法缺陷**）：

1. 下界忽略机器"最早可开工时刻"。例：烤箱容量 1，饼干最早 45 分才能进炉
   ⇒ 45 + 48（烤箱总工时）= 93 才是最优，而下界只算 48。
2. 目标以 Γ（对齐）为第一优先，会**主动**牺牲 makespan。

## 3. 漏洞 C：出锅差 Γ 可被"把收尾步停到最后"刷小

`dish_finish[dish] = 该菜所有 t≥0 任务的 max end`，它同时喂给
① Γ（评分口径）② 冷等待/保热惩罚。

把一条 1 分钟的收尾步（"尽情品尝吧"/"撒葱花"）停在时间线末端 ⇒ `F_d == T` ⇒ `cold = 0`
⇒ **惩罚被完全掩掉**，求解器反而**被奖励**去"早做熟、干等到最后"。

### 证据

60 组随机实例：报告 Γ 与"真实烹饪跨度"的差额 **中位 23.0 / 均值 30.2 / max 175 分钟**，49/60 组差 > 5 分钟。

**典型（#55：酿苦瓜 + 手工鸡蛋豆腐 + 原味墨西哥面包）**

```
酿苦瓜       真实烹饪结束   8.0   dish_finish 192.0
手工鸡蛋豆腐   真实烹饪结束  16.0   dish_finish 191.0
原味墨西哥面包 真实烹饪结束 185.0   dish_finish 190.0
      ...
   188.0  190.0   2.0  人工  双手-1   原味墨西哥面包  选择"开始烹饪"按键，按屏幕提示操作
   190.0  191.0   1.0  人工  双手-1   手工鸡蛋豆腐    尽情品尝吧
   191.0  192.0   1.0  人工  双手-1   酿苦瓜         尽情品尝吧
```

报告 **Γ = 2.0**，而两道蒸菜真实 **8 / 16 分钟**就出锅了 —— **菜实际凉了 177 分钟**。

### 修法（分两处，都量过）

| 位置 | 改法 | 效果 |
|---|---|---|
| `model.solve_exact` 的 `cold/over` | 基准改 `F_cook`（最后一次进加热设备结束） | 差额中位 **23.0 → 7.5**，**零指标代价**（<5min 90.3% 不变，总时长 63.6） |
| `objective.score_plan` 的保热项 | 基准改 `F_cook` + **以 Γ 计价的总预算**（见 §9.2） | 出锅差 **不变**（90.3%），`gap 均值 3.43→3.23`，保热违规 −5% |

**为什么两处必须用不同手段**：`model` 里 cold 是**字典序最低层**（排在 Γ、T 之后），改基准不跟 Γ 抢；
`score_plan` 里它是**无界加权项** —— 一道菜等 170 min ⇒ `30 × 0.9 × 170 ≈ 4590`，
而 `w_gap·Γ` 只有 180，于是**策略择优被整个改写**（实测 `<5min` 90.3% → 80.3%）。
所以那里换基准的同时**必须给它一个预算**，否则只是把一个"没用"的项换成一个"夺权"的项。
（第一版曾试图用"per-dish over 上界"，实测预算取 5/10/20 分别只能把 `<5min` 救回 89.3/88.3/86.7%，
仍然比旧口径低 —— 真正有效的口径是**按 Γ 计价**，见 §9.2。）

## 4. 漏洞 D：跨午夜 `HH:mm` 回绕 → 护栏"偶发红一次"

**现象**：全量测试在 23:0x 报 `test_official_api_spec_conformance` 红；单跑又绿。

**根因**：`adapter.hhmm(offset) = (now + timedelta(minutes=offset)).strftime("%H:%M")`。
`now = 23:10` 排 50 分钟 ⇒ **"00:00"**。而测试"要求3"裸比分钟值：

```python
max_end = max(mm(x["endTime"]) ...)   # 23:52 → 1432
if mm(ov["finishTime"]) < max_end:    # 00:00 → 0   ⇒ 假报违规
```

**复现**（把 `now` 钉死）：`23:10` 时 8 组里 **1 组**中招；`22:50 / 23:00 / 23:55` 为 0
—— 窗口 = "now 到午夜"短于计划跨度时。

**修法**：环形差判据 —— `dish_end <= makespan` ⇒
`(mm(finish) − mm(end)) % 1440 == makespan − end <= makespan`。对回绕免疫，且**不改口径**
（HH:mm 表达不了"次日"，语义上 00:00 确实晚于 23:52，错的是比较方式）。
新增护栏 `test_api_times_are_rollover_safe` 把时钟钉在 23:10，让场景**必现**。

## 9. 续：先验判定与保热预算（2026-10-04 第二轮）

### 9.1 主导工序先验：**72/100 道菜被判成"爆炒"**

`app/agent/priors.py::_kind_of` 决定 `serve_hot / hold_min` 两档保热语义。旧判据是
"**步骤里出现任意一个**灶具/烤箱的炒烤步 ⇒ `fry`"，而 `_FRY` 又收了"烤|酥"。两条叠加：

| 受害菜 | 旧判定 | 为什么错 |
|---|---|---|
| 雪媚娘 | `fry` 0.95/6 | #1「准备熟糯米粉：**炒锅**慢火炒至微黄色」是**辅料处理**，整道菜是冰皮冷甜品 |
| 黑森林蛋糕 / 糖霜饼干 / 红豆糯米糕 / 广式月饼 | `fry` 0.95/6 | 烘焙甜点被判成"**6 分钟内必须吃掉**" |
| 清蒸鲈鱼 / 家常鲈鱼 / 竹荪排骨汤 | `fry` 0.95/6 | 最后「**烧热油淋在鱼身上**」的收尾步**盖过了蒸箱**；汤的 hold 从 45 被压到 6 |
| 京韵酱香烤鸡 | `cold` 0.15/180 | 菜名里的"**酱**"被判成卤酱凉菜（实际是烤箱烤鸡） |

**分布**：旧 `fry 72 / steam 18 / cold 3 / other 7` —— 单类占 72%，这个先验基本没信息量。
新：`bake 36 / steam 39 / fry 13 / soup 6 / cold 6`（新增 `bake` 一档，`0.75 / hold 20`）。

新判据按"**上桌时的状态**"，三个信号依次为：

1. **末道设备工序是冷藏/冷冻 ⇒ `cold`**。判据要严：冰箱步之后只剩上桌动作，
   且原文没说"趁热" —— 否则会把「冷藏醒面」（玛格丽特 #2 后面还有烘烤）和
   「蒸好后…**趁热**或冷藏后食用」（皂角银耳羹 #4）误判成冷食。
2. **菜名强信号**，顺序即优先级：冷食 > 烘焙 > 蒸 > 汤羹 > 炒炸。
   （`蛋羹` 必须先于 `羹` 判 —— 鸡蛋羹是蒸出来的。）
3. **加热步的主导设备**（平票按 蒸箱 > 烤箱 > 灶具）。淋热油/焯水这类灶具收尾步在官方
   菜谱里非常多，按"有没有炒"判必被它带偏。

⚠ **诚实的量化结论**：这个修正对**排程指标几乎无影响**（6 seed × 50 组：`<5min` 90.3%→90.3%、
总时长 68.75→68.82、连续手动 25.40→25.72，全部在噪声内）。原因见 §7.4：保热项在策略择优里
本来就几乎没有话语权。它的价值在于**语义正确**（通知文案、重排仲裁 `freeze_hot`、
精解轨第 ③ 层、以及 `serve_hot ≥ 0.85` 的"趁热上桌"提醒），以及不再往目标里灌错信号。

### 9.2 保热项：从"恒 ≈ 0"到"以 Γ 计价的方向盘"

`score_plan` 的保热项原本有两个互斥的坏形态：

- **用完成时刻**（`plan.dish_finish`）⇒ 把一条 1 分钟的收尾步停在时间线末端就让该项恒 ≈ 0，
  **等于从来没参与过择优**；
- **用出锅时刻 + 无界** ⇒ 一道菜等 170 min 就是 4590，`w_gap·Γ` 只有 180 ⇒ **夺走 Γ 的权**
  （`<5min` 90.3% → 80.3%）。

正确形态是**两者都要**：基准用 `dish_cook_finish`（出锅时刻），同时给它一个**以 Γ 计价的总预算**
`min(hot, w_gap × FT_HOT_BUDGET)` —— 语义变成"**保热最多花掉 N 分钟的 Γ**"，任何 Γ 领先超过
N 分钟的方案都不会被保热翻盘。

扫描结果（4 seed × 60 组 lb_probe + 6 seed × 50 组 bench）：

| budget | `<5min` | makespan == 可证下界 | gap 均值 | 保热违规 |
|---|---|---|---|---|
| 旧口径（完成时刻，无界） | 90.3% | 65.0% | 3.43 | 3.68 |
| 0 | 90.3% | 65.8% | 3.18 | 3.68 |
| **0.5（采用）** | **90.3%** | **65.0%** | **3.23** | **~3.5** |
| 1 | 90.3% | 64.5% | 3.43 | 3.38 |
| 2 | 90.3% | 62.8% | 3.60 | 3.40 |
| 4 | 90.3% | 62.0% | 3.75 | 3.17 |
| off（无界） | 80.7% | — | — | 1.04 |

读法：**出锅差对 `[0, 4]` 整个区间免疫**（评分表主项，必须是平的）；但预算一大就开始用
makespan 去换保热 —— 2 已经掉了 2pp 的"makespan == 可证下界"。取 `0.5` —— 三条轴上都不劣于旧口径的最小值。

### 9.3 又一个"排程一改、护栏就假红"的教训

`tests/test_audit_doc.py::test_the_false_alarm_is_reachable` 把"能造出跨零点场景"的时刻**钉死在 22:00**。
本轮保热口径一改，排程变短，22:00 从"3 条旧口径误报"退化成"**0 个跨零点场景**" ⇒ 当场变红，
报的是"测试前提不成立"。**不是审计坏了，是排程变好了。**

修法：不再钉死单一时刻 —— 先试首选（实测最优的 23:15），造不出场景就**自动扫候选池**，
最终仍然断言"这个误报确实可达"（前提消失时必须报错，不能静默跳过）。
模块 docstring 里那张"冻结时刻 → 误报数"的表也按新排程重测了一遍。

⇒ **教训（第五条铁律候选）：断言"某个前提成立"的测试，前提本身会随被测代码变好而失效。
把前提写成"在候选集里搜一个满足的"而不是"钉死一个"，否则每次优化都要来修它。**

## 10. 续：最优性证书，与三个"看起来像漏洞"的东西（2026-10-04 第三轮）

前两轮的判据是"gap vs **放松**下界"，只能说明"离下界不远"。本轮换成**求解器自己报的
证明状态**，并把 Γ 的下界补上。

### 10.1 硬判据升级：从"下界对照"到"可证最优"

| 规模 | 预算 **1.5s**（= 生产） | 预算 30s |
|---|---|---|
| 3–5 菜（100 组 seed=42） | **OPTIMAL 100/100** | 99/100 ※ |
| 6–9 菜（60 组 seed=42） | **OPTIMAL 60/60** | 59/60 ※ |

※ 两列是**不同实例集** —— 探针的 `random.seed` 在两个预算循环**之前**只调一次，
第二个循环拿到的是后 N 个样本。所以 30s 那组的 1 次超时不是"时间越多越差"。

**证书可信性单独验证**（60 组 seed=11）：模型自报的 (Γ,T) 与独立 `evaluate()`
**逐位一致**（0/60 不一致），`check_plan` 全部可行（0 冲突 / 0 依赖违反）。
⇒ "OPTIMAL" 是对**交付口径**的目标最优，不是对它自己某个写错的目标最优。

### 10.2 公平版预算探针：0/20，且输出逐位相同

`.cache/_opt_probe.py`（旧）的"足预算解"用的是**默认单策略**，而生产是"6 策略择优 + 三轨"
—— 两边候选集不同，测出来的是**策略选择**的收益，不是预算的收益。新写
`.cache/_opt_fair.py`：把两边钉在**同一策略**，只放大预算（1.2/1.5s → 20/60s）。

**20 组全部 `dT = dG = 0.0`（逐位相同），0/20 有改进。**

⇒ 与 10.1 完全一致：精确模型在 1.5s 内已收敛并证明最优，多余预算一点没用上。

### 10.3 补上 Γ 的下界（本轮唯一的代码改动）

此前 `lower_bound_from_plan` 只给**总时长 T** 的下界，**Γ（评分表主项）完全没有下界**
—— "Γ 是不是最优"只能靠"相信求解器"。新增 `model.gamma_lb_from_plan(plan)`：

> **Γ_lb = Σd − max d**，`d` 取同一**容量 1** 资源上各菜的**末步**时长。
> 理由：同组末步必须串行，首末差距 ≥ (s₁+Σd) − (s₁+d_π(1)) ≥ Σd − max d。

三条**必须排除**的东西（漏任何一条都会造出"下界 > 真实 Γ"的假下界）：

| 排除项 | 为什么 |
|---|---|
| **蒸箱** | `unit_id` 是"腔体槽位"不是机器，同温可**无限共享** ⇒ 组内并非串行 |
| **容量 > 1 的资源**（灶具 = 2 灶眼） | 可分到多个工位并行 |
| **`等待` / `提前准备`** | 不占资源，不是"末步"意义上的工序 |

已接进 `scripts/lb_probe.py` 报告 + 4 条护栏（`tests/test_model.py` §6）。
**60 组 seed=11 实测**：

```
Γ_等于下界占比 68% (41/60)    Γ − Γ_lb  中位 0.0 / 均值 0.5 / max 7.0    Γ_下界违反数 0
```

⇒ **68% 的实例出锅差恰好等于可证下界**（= 可证 Γ 最优），其余残差最大只有 7 分钟。

### 10.4 排除掉的三个"看起来像漏洞"的东西（都量过）

| 怀疑 | 结论 | 证据 |
|---|---|---|
| **ε 约束方向反了**：模型先压 T、再在 `T ≤ T*+15` 内压 Γ，而评分表是 Γ 主序 | **不成立** | `FT_EXACT_SLACK` 取 15/30/60/120/999，最终指标**逐项完全相同**（`<5min` 91.7%、Γ 中位 1.0、T 中位 54.5）。多轨 + `score_plan`(60:1) 已把短板补掉：`solve_exact` 在 #15 单独给 Γ=24，但**贪心给 Γ=1**，择优自然选了贪心 |

模型报 `status=OPTIMAL`，且 slack 0→60 都不变 ⇒ **Γ=7 就是真最优**。

## 11. 续：一个"只在进程启动后第一次出现"的真 bug（第四轮）

> 触发点：重新打包后做冒烟，同一个 4 菜组合，
> 第 1 次跑 **Γ=32 / T=83**，第 2 次跑 **Γ=3 / T=57**。

### 11.1 现象与根因

**不是算法次优，是整条质量最好的轨被静默跳过了。**

`app/agent/orchestrator.py::_run_inner` 的顺序是：
LLM 目标塑形 → LLM 策略提议 → 贪心枚举择优 → **精解轨**。

而精解轨的预算来自"剩余时间"：

```python
left = max(0.0, time_budget - (time.time() - t0))
bud  = solver_budgets(len(recipes), left * 0.75)
```

在线时 LLM 的两次调用实测能吃光 `time_budget=3.6s`
⇒ `left ≈ 0` ⇒ `solver_budgets(4, 0)` 两条精解轨全 `use_*=False`
⇒ **精解段整块被跳过，交付贪心解**。

在线闸门（`FT_LLM_ONLINE_GATE`）是在本轮**结束后**才落下的，
所以**每次进程启动后的第一次请求都中招**，之后才恢复正常 ——
这正是"第 1 次差、第 2 次好"的来源。

**为什么这次值得单独立一节**：这条路径的量级最大。
第三轨净收益是 **T −21.6% / Γ −32.0%**（`verify_model` 实测），
"LLM 慢"却升级成了"丢掉质量最好的那条轨"。

### 11.2 修复：给精解轨一份**不可被抢**的保底

预算按"从后往前"分配，而不是"先到先得"：

| 环节 | 预算来源 | 默认 3.6s 下 |
| --- | --- | --- |
| 精解轨（CP-SAT + 精确模型） | `_solver_reserve(n, use_cpsat)` | **0.761s** |
| LLM（塑形 + 提议） | `llm_quota = time_budget − reserve − _ENUM_RESERVE` | 2.239s |
| 策略枚举（6 条贪心快评） | `_ENUM_RESERVE` | 0.600s |

三条改动：

1. `app/scheduler/dispatch.py::min_pool_for_tracks(n, …)` —— **反解**"要让某条轨
   开起来，池至少要多少"。用**二分调用 `solver_budgets` 本身**求，
   而不是把 `0.45/0.55` 公式再抄一遍（两处各写一份必然漂移，
   本项目已有前科：备菜判据三轨各写各的，精解轨靠"少排几步"刷出 +54% 虚高）。
2. `orchestrator._solver_reserve()` —— 把它换算成"未乘 0.75 余量前的剩余时间"，
   再加 2% 浮点余量（`solver_budgets` 的判据是 `>=`，差 1ulp 就整轨关）。
3. `_run_inner` 里三处预算各守其位：
   LLM 的 timeout / 剩余判断用 `llm_quota`；枚举的 break 用 `llm_budget`；
   **精解段的 `left` 仍用 `time_budget`** —— 所以走到那里一定 `≥ reserve`。

顺带修掉一个连带缺陷：`propose_strategies` 的 `max(0.5, …)` 下限会让 LLM
**超支**（剩余 −0.001s 也照样给 0.5s），于是"预留了 0.761s"实际只剩 0.26s。
现在改成"剩余不足 `_LLM_MIN_ROUNDTRIP` 就**跳过**这次提议，直接枚举全策略"。

### 11.3 量化对比（4 菜，seed=11，`time_budget=3.6s`）

| | Γ | T | 耗时 | 精解轨 |
| --- | --- | --- | --- | --- |
| 离线基准 | 1.0 | 37.0 | — | 跑 |
| 修复前·慢模型首请求 | **8.0** | **52.0** | 4.10s | **跳过** |
| 修复后·慢模型首请求 | **1.0** | **37.0** | **2.29s** | 跑（`+cpsat`） |

修复后**逐位等于离线基准**，而且**更快** —— 因为跳过了那次注定落空的
提议往返（原本白等 0.5s 才回落规则）。

反向回归也守住了：模型很快（200ms 返回）时，
目标塑形仍命中（`policy.source == "llm"`）、提议仍生效（trace 只 3 条候选）、
精解轨仍跑，耗时 0.51s。

  (c) Γ/T 不劣于同预算的离线基准；

## 12. 续：甘特图 t=0 之后那段"设备全空"（2026-10-06）

> 触发点：用户看单菜排程（三味蒸鳗鱼&香茅烤鳗鱼同烹）的甘特图，
> 问"前面空缺的一段时间在干什么"，并要求修复。

### 12.1 现象与根因

甘特图上 **t=0 到 t=8（单菜最长到 13）** 这一段，灶具/蒸箱/烤箱/双手四行全空，
只有"等待"行有内容。最简复现（一道菜，两步）：

| | 腌制 | 烤箱 | 总时长 | 前 10 分钟 |
| --- | --- | --- | --- | --- |
| 修复前 | 0 → 10 | 10 → 35 | 35 | **烤箱全空** |
| 修复后 | −10 → 0 | 0 → 25 | 25 | 烤箱在跑 |

**根因**：`t=0` 的语义是「**提前准备段的结束**」——
`engine._prepare_tasks` 把备菜步"整体右对齐到 t=0"（`engine.py:281`），
而 `_to_plan` 的判据是 `cooking = [t for t in tasks if t.start_min >= 0]`
（`engine.py:785`）。于是：

- 备菜段（`unit_id="提前准备"`）右对齐到 0 ⇒ 它的结束就是 t=0；
- 但备菜之后、第一个**占用资源**的任务之前，还夹着一段**纯等待**
  （"腌制 10 分钟"），它不占设备 ⇒ 甘特图上 t=0 之后一段设备全空；
- 更糟的是这个等待任务**跨过 t=0**（`−2 → 8`），既不算"提前准备"，
  又把第一个资源任务推到 8 之后。

**这不是排程没排满，是锚点放错了位置。**

### 12.2 修复：把锚点挪到「第一个占用资源的任务」

新增 `engine._rebase_to_first_resource(plan)`，在 `schedule()` 的最后调用：

```python
plan = _add_kitchen_semantics(_restore_missing_steps(best, recipes))
if not hard_frozen:                       # 有冻结任务时绝不平移
    plan = _rebase_to_first_resource(plan)
```

它把时间轴整体左移，使 `min(start of 资源任务) == 0`，然后交给 `_to_plan`
重算 `makespan / dish_finish / 出锅差`（**口径唯一，不另写一份公式**）。

**为什么这不是"刷指标"**：`_to_plan` 的口径本来就是
"`start < 0` 的算提前准备、不计入当天烹饪"。腌制不占资源，
把它整体放进 `t<0` 正是这个口径想要的结果 —— 修复让"当天烹饪"的起点
回到了它本该在的地方：**第一个真正动用厨房资源的时刻**。

**为什么有冻结时不平移**：动态重排的 `hard_frozen` 任务代表"已经发生的事"，
时间必须与现实一致，移位会让甘特图对不上实际。

开关 `FT_ANCHOR=off` 可退回旧行为（供 A/B）。

### 12.3 影响面（量过）

| | 修复前 | 修复后 |
| --- | --- | --- |
| 单菜（鳗鱼 13 步） | T=52，首个资源任务 t=8 | **T=44，首个资源任务 t=0** |
| 单菜（腌制+烤箱，2 步） | T=35，烤箱 t=10 才开 | **T=25，烤箱 t=0 就开** |
| 两菜（鸡仔饼+鳗鱼） | Γ=1 / T=52 | **Γ=1 / T=44**（出锅差不变） |
| `bench 50`（seed=42） | 总时长均值 63.2 | **62.9**（几乎不动） |

**多菜组合影响很小**：只要有一道菜的资源任务本来就在 t=0，`shift` 就是 0。
所以修复的价值集中在**单菜**、以及"所有菜都要先腌制"的场景 ——
而这恰好是用户截图里的那一种。

### 12.4 护栏

- **改** `test_no_negative_preheat`：原断言写成 `all(t.start_min >= 0)`
  （"所有任务不许为负"），而它的本意是"**预热节点**不许为负"。
  这条过宽的断言在锚点修复后当场变红 —— 修复是对的，红的是断言。
  现在只查 `raw_text ∈ {蒸箱预热, 烤箱预热}` 且 `start < 0`。

  ② 第一个资源任务必须**正好**在 `t=0`。
- 冻结场景由既有的 `test_agent_loop_respects_frozen_tasks` 守住。

## 13. 甘特图随机抽查：两个真实缺陷（2026-10-06）

> 指令：**"随机抽查几个菜谱的甘特图看看是否准确"**。

> 以及把结论固化成护栏的方式。

### 13.1 方法：先证明"审计会响"，再拿它查

新建 **独立**审计脚本 `.cache/_gantt_audit.py`（不复用被测代码，避免"用被测
代码验被测代码"），逐菜校验 **10 项**：

| # | 检查项 | 判据 |
| --- | --- | --- |
| 1 | 时长/区间自洽 | `end - start == dur`，`dur >= 0` |
| 2 | 单位重叠 | 同 `unit_id` 区间不许重叠（豁免：蒸箱同温 ±15℃、预热共享 ±10℃） |
| 3 | 依赖边 | 每个 `depends_on` 的前置 `end <= 本步 start` |
| 4 | 锚点与 t<0 纯净性 | 首个资源任务在 `t=0`；`t<0` 只允许 `等待/提前准备` |
| 5 | **独立重算 T/Γ** | 不复用 `metrics`，自己算 `max F − min F` / 当天最大 `end`，与 KPI 对账 |
| 6 | 步骤连续号 | `_idx` 连续无缺号 |
| 7 | 声明步数 vs 解析步数 | **排除合成预热节点**后计数（`insert_preheat_steps` 本就重编号 1..M） |
| 8 | 凭空任务 | 每个任务都能追溯到某菜的某步 |
| 9 | device/unit 自洽 | `device` 与 `unit_id` 前缀必须匹配（防顶替只改一半） |
| 10 | 应用自检 vs 独立结论 | `check_plan` 说可行而独立审计报冲突（或反之）⇒ 打架 |

**关键前置：变异自检**。给审计注入 10 类已知缺陷（单位重叠 / 依赖倒挂 /
锚点漂移 / t<0 资源任务 / 时长不符 / 步骤缺号 / 删末步 / 凭空任务 /
device-unit 矛盾 / KPI 时长口径错），**10/10 全部命中**才拿它去查真数据。
> 其中一条变异抓出"护栏挂错入口"：`test_no_resource_task_before_day_start`
> 初版**裸调** `engine.schedule()` **复现不出**缺陷（走的是另一组策略集）⇒
> 必须走 `adapter.plan_recipes`（Agent 闭环 = 线上真实路径）。

配套：`.cache/_gantt_scan100.py`（全量 100 道扫 [A] 资源任务 t<0 /
[B] 整道无资源任务 / [C] 首个资源任务 != 0）。

### 13.2 缺陷 A：占设备/占人工的步骤被排到 t<0（8/100 道）

**现象**（抽查 20 道 seed=20261006 + 全量 100 道）：

| 菜 | 步骤 | 设备 | 区间 |
| --- | --- | --- | --- |
| 低温牛排 | #2 | 蒸箱 | **−2 → 6** |
| 芋头蛋卷 | #2 | 蒸箱 | **−2 → 6** |
| 血糯米仙草奶茶 | #8 | 蒸箱 | **−2 → 6** |
| 油醋汁剁肉饼蒸和乐蟹 | #6 | 蒸箱 | **−2 → 3** |
| 麻辣对虾 | #4 | 双手 | **−15 → …** |
| 金龙吐瑞 | #4 | 双手 | **−15 → …** |
| 轻松一锅蒸 | #3 | 双手 | **−10 → …** |
| 金银蒜蒸鸡胸肉 | #4 | 双手 | **−60 → …** |

**根因**：备菜步在 `engine._build_tasks` 里整体**右对齐到 0**（`cur = -sum(dur)`），
所以它的 `end_min` 是**负数**。贪心轨的
`dep_ready = max(done[d].end_min for d in t["depends_on"])` 若某烹饪步的前置
恰好是一个**结束在 −2 的备菜步**，`dep_ready` 就是 −2 ⇒ 贪心把这条**占设备 /
占人工**的步骤排到 `t < 0`。

**后果（静默，最难发现）**：`_to_plan` 用 `cooking = [t for t in tasks if t.start_min >= 0]`
筛"当天任务" ⇒ 这些 `start<0` 的资源任务**既不计入 T/Γ、也不进 `check_plan`**
—— 甘特图上"设备昨天就在干活"，指标却完全看不见。

**修复**（`engine.py`）：

```python
# ⚠ 非备菜任务不得早于 t=0。备菜步右对齐到 0 ⇒ 其 end_min 为负；
# 若烹饪步的前置只是"早早结束的备菜步"，dep_ready 会是负数 ⇒ 占资源的步被排到 t<0。
dep_ready = max(0.0, max((done[d].end_min for d in t["depends_on"]), default=0.0))
```

**影响面**：资源任务落在 `t<0` 的菜 **8/100 → 0**。

**护栏**：`tests/test_core.py::test_no_resource_task_before_day_start`，
用例 `["低温牛排", "金银蒜蒸鸡胸肉", "芋头蛋卷"]`。
⚠ **必须走 `adapter.plan_recipes`** —— 裸调 `engine.schedule()` 复现不出
（策略集不同），初版护栏因此没能在变异下变红。

### 13.3 缺陷 B：复合设备继承被灶具步挡住（`玛格丽特`）

**现象**：`玛格丽特` 当天只剩 3 分钟"晾凉"，`T=3.0`、设备利用率 **0%** ——
**烘烤段在甘特图上根本不存在**。

**根因**：`app/parser/recipe_parser.py` 里复合设备继承的守卫写的是

```python
if not any(s.device in HEATING_DEVICES for s in recipe_steps):   # HEATING_DEVICES 含灶具!
```

`HEATING_DEVICES = (灶具, 蒸箱, 烤箱)` **含灶具** ⇒ 菜里**只要有一个灶具步**
（哪怕只是"煮鸡蛋 15 分钟"），蒸烤一体机的继承就**整段跳过**，真正的烘烤步停在
"人工" ⇒ 被 `rule_prior`（`device == DEVICE_NONE and not unattended` 一律算备菜）
当成备菜 ⇒ 整道 4 步落进 `t<0`。

**判据自相矛盾**：同一句"放入蒸烤箱…"在**没有灶具步**的菜里能判成烤箱，
在有灶具步的菜里却判不出来 —— 说明挡住它的是**灶具**这个无关因素。

**修复**（`app/parser/recipe_parser.py`，复合设备继承守卫）：

```python
# 只看蒸箱/烤箱：灶具步不该挡住蒸烤一体机的推断
if not any(s.device in (DEVICE_STEAMER, DEVICE_OVEN) for s in recipe_steps):
```

**影响面**：`heat_steps` 指纹 **210 → 212**（+2 步：`玛格丽特#4`、
`芝士番茄土豆泥#12`，均 `device_source='(复合设备推断)'`，原文可印证）。
修复后 `玛格丽特`：`T = 3.0 → 11.0`、利用率 **0% → 18.2%**。

**护栏**：`tests/test_core.py::test_combo_device_inheritance_survives_stove_step`，
用例 `{"玛格丽特": "烤箱", "芝士番茄土豆泥": "烤箱"}`，断言该菜**含灶具步**
**且**烤箱步没被挡掉。

### 13.4 排除的假警报

`原味墨西哥面包` 抽查时 `T=190min` 且**无独立烘烤步**，一度疑似"漏排烘烤"。
回原文核对：该菜谱**本身只有 7 步**，190min 来自**两次发酵（120 + 65）**，
排程**忠实**。⇒ 这类"看起来不合理"必须回原文核，不能凭直觉报缺陷。

### 13.6 教训

1. **抽查要独立于被测代码** —— 复用 `metrics` 重算 KPI 等于没查；
   必须自己按口径重算一遍再对账。
2. **审计工具先自证** —— 注入已知缺陷证明它**会响**，否则"全绿"毫无意义。
3. **护栏要挂在对的入口** —— 同一个缺陷在裸调 `schedule()` 里复现不出，
   护栏挂错入口就永远不红。
4. **`t<0` 是"指标黑洞"** —— 任何 `start<0` 的资源任务都会**同时**从
   T/Γ 和可行性检查里消失；锚点相关改动必须扫全量。
