## 二、检查方法（为什么必须分三段）

有些东西**只能**在某一段验，混在一起就会漏：

| 段 | 能验什么 | 验不了什么 |
|---|---|---|
| **A 静态接线** | 模块是否真被加载 / 延迟导入是否真可达 / 有没有死代码 | 任何运行时行为 |
| **B HTTP 链路** | 24 个路由 + L1→L4→L5 串联、动态重排、前端静态资源 | 不在响应里暴露的环节 |
| **C 层内直调** | L2 先验三态 / L3 权重随文本变化 / L4 三轨是否都在 | 端到端可达性 |

**代码新鲜度探针（B0）是前提**：如果端口被旧进程占着，健康检查会打到**旧代码**，
后面所有结论都是废的。所以第一步就验"未命中的菜谱 id 必须返回 404"——
本次在**干净端口 8142/8143** 上实测通过（`404 {"detail": "菜谱不存在: ..."}`）。

## 四、发现与处置

### 4.1 真缺陷 ①：设备顶替后 `device` 标签不同步

**现象**：`failed_device=蒸箱` 后，计划里仍有 4 个任务 `device == "蒸箱"`。

**根因**（`app/scheduler/engine.py::_schedule_once`）：

```python
# 顶替时只改了 res（真实占用），没改 device（对外标签）
alt = DEVICE_FALLBACK.get(t["res"])
if alt and units.get(alt, 0) > 0:
    t = dict(t, res=alt)          # ← device 仍是 "蒸箱"
...
st = ScheduledTask(device=t["device"],      # ← 旧设备名
                   unit_id=unit_id)         # ← 由 res 生成 → "灶具-1"
```

于是产出 `device="蒸箱"` + `unit_id="灶具-1"` 的**自相矛盾任务**。

**规模**：实测 6 个场景（正常 + 5 类设备置 0）共 **68 条**不一致。

**后果不是"显示难看"**：`checker.overlap_allowed()` 是按 `device` 判
"蒸箱同温可共享腔体"豁免的 —— 一个其实占着灶具、却仍标蒸箱的任务会套用该豁免，
**把真实的灶具冲突判成合法重叠**（静默漏报）。

**修复**：`device` 跟着 `res` 一起改（顶替→顶替设备名；降级→`DEVICE_NONE`）。

### 4.2 真缺陷 ②：设备故障时连"精确轨"一起被关掉

**现象**：`orchestrator.py` 精解块写成 `if use_cpsat:`，而设备故障时调用方传 `use_cpsat=False`
（理由：CP-SAT 的模型不读资源容量覆盖）。结果**整个精解块被跳过**，
连**认容量覆盖的精确轨**也一起丢了。

**实测证据**（逐轨隔离）：

| 场景 | 蒸箱=0 后的实际占用 |
|---|---|
| 仅贪心 `use_cpsat=False` | 任务落到 `灶具-1` ✓ |
| 贪心+精确 `use_exact=True` | 任务落到 `灶具-1` ✓（精确轨判不可行→回落贪心，**不越权排蒸箱**） |
| 全三轨（含 CP-SAT） | **仍排 `蒸箱-1`** ✗（CP-SAT 确实不读覆盖） |

⇒ 结论：**该关的只有 CP-SAT**。精确轨走 `model.capacities() → engine.resource_units()`，是认覆盖的。

**修复**：门控改为 `use_cpsat_here or bud["use_exact"]`，其中
`use_cpsat_here = bud["use_cpsat"] and 调用方的 use_cpsat`。精解轨的 trace 后缀相应区分
`+cpsat` / `+exact`，`explain()` 的后缀还原改用正则。

### 4.3 死代码（3 处，全仓库零引用，文档零提及）

| 位置 | 内容 | 证据 |
|---|---|---|
| `app/models/kitchen.py` | `default_kitchen()` | 除自身外零 import；真实配置走 `main.py::_DEVICE_CFG` + `engine.RESOURCE_UNITS` |
| `app/models/schema.py` | `DeviceConfig` / `DeviceUnit` 两个类 | 只被 `kitchen.py` 引用；能力表唯一实现在 `spec/device_spec.py::DEVICE_SPEC` |
| `app/parser/recipe_parser.py` | `find_device_ex()` | 只是 `_ds.find_device()` 的透传包装，零调用 |

**为什么必须删而不是留着**：留着会让读代码的人以为"设备配置在这里"，
而真实位置是 `engine.RESOURCE_UNITS`（容量）+ `spec/device_spec.py`（能力）。
已在 `schema.py` 留下指向正确位置的注释。

### 4.4 缺护栏：两个"写了却说没人用"的函数

`app/spec/device_spec.py`：

- `is_legal()` 的 docstring 明写「**供自检/测试用**」—— 但全仓库**没有任何自检或测试调用它**。
- `legal_modes()` —— 零引用。

这类"半成品"最危险：它看起来像"参数合法性已经验过了"，实际是**零覆盖**
（而设计文档 3.1.3 恰好就是「参数合法性」）。

**处置**：补 `tests/test_device_params.py`（32 项），判据用**闭包性质**而不是逐个举例：

> `clamp_params / fit_mode` 的输出，必须**永远**能被 `is_legal` 判为合法。

遍历 `设备 × 模式(含非法) × 温度(含越界) × 时长(含越界)` 的笛卡尔积，
外加一条真链路断言（官方 100 道菜解析出的每一步都必须合法）。

### 4.5 检查探针自身的 4 处假警报（全部已修）

**假警报比漏报更贵** —— 它会让人去改没坏的代码。本次 4 处：

| # | 假警报 | 根因 | 修法 |
|---|---|---|---|
| 1 | 「4 道菜全部进计划 FAIL」 | 探针**手写**了 `清蒸鳜鱼/蒜蓉西兰花/凉拌黄瓜` 三个菜名，**都不在官方 100 道库里**。程序行为完全正确（把未命中的菜放进 `warnings` 显式报出来了） | 菜名改为**从官方库运行时取**，并按设备覆盖面优选；另加一条"幽灵菜名必须被显式报出"的**正**断言 |
| 2 | 「断链」「死代码」同时 FAIL | 断链判据是"源码里有没有写过 import"，把**零引用模块**也算成断链，与死代码判据互相打架 | 断链判据改为**真的 import 一遍**（导不进来才叫断链）；死代码单独判 |
| 3 | 「L2 先验层可用 FAIL」 | 用 `type("R",(),{"name":...})()` 造**假 Recipe**，先验层要读 `steps` ⇒ `AttributeError` | 改用真 Recipe（官方库补全后解析） |
| 4 | 「先验含保热/等待字段 FAIL」 | `DishPrior` 是 **dataclass 不是 dict**，探针只认 dict ⇒ 判定恒 False | 用 `dataclasses.asdict()` |

**第 5 处不是假警报，是判据本身写错了**：

「同菜步骤顺序正确」原判据假设"`step_id` 大 ⇒ 时间晚"，于是把 `#3@0.0` 与 `#4@-2.0` 报成错误。
实际上 `#3` 与 `#4` 的 `depends_on` **都只有 `#2`** —— 它们是**并行分支**；
而且 `#4` 是被刻意前移到 `t<0` 的「提前准备」行（备菜早做是对的）。
**真正的不变量是：对每条依赖边 `u → v`，必须 `end(u) ≤ start(v)`。**
已改为按依赖边判定；原先那个（错误的）观察保留为**附注**，用来提示疑似漏边（见 §六）。

## 六、记录在案的缺口（不修，理由如下）

| 缺口 | 说明 | 为什么不修 |
|---|---|---|
| **CP-SAT 轨不读容量覆盖** | `cpsat.py` 的模型不认 `resource_override`，会把故障设备照旧排进去 | 已有规避（故障时关掉它），且现在**只关它一个**，精确轨仍在跑。重写 CP-SAT 建模收益不抵风险 |
| **L1 依赖漏边** | 「三味蒸鳗鱼&香茅烤鳗鱼同烹」#4 原文是"将**腌制好的**鳗鱼夹出"，逻辑上必须晚于 #3 的"腌制10分钟"，但 `depends_on` 只有 `#2` | 属依赖推断的语义覆盖问题（回指型指代未识别）。不影响可行性（无依赖边 = 允许更早，不会造违反），且改推断规则会牵动已验收的 99/100 解析正确性 |
| **`/parse` 契约差异** | 只给菜名（不带 steps 原文）时返回空 —— 它**不做**官方菜库补全，而 `/schedule`、`/reschedule`、`/notify` 都会自动补全 | 已在探针里作为 note 显式记录。是否统一属接口设计决策，需与接口规范对齐后再动 |
| **`publish/` 仍是旧代码** | 拷贝而非链接，改源码后需 `python -m scripts.sync_publish` | 属**发布动作**，等上线决定 |
