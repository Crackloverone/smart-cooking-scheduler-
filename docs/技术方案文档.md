# 智能烹饪调度 Agent 技术方案

## 1. 总体架构

系统分四层，对应赛题五个 Level：

```
自然语言菜谱 ──> [L1 解析层] ──> 结构化 Recipe(JSON)
                                    │
用户选菜(3-5道) + 设备配置 ──> [L2/L3 调度层] ──> SchedulePlan(时间线)
                                    │
执行中事件 ──> [L4 重排+通知层] ──> 新排程 + 用户通知
                                    │
                              [FastAPI 评测接口]
```

设计原则：**解析可解释、调度纯启发式（不调用大模型）、性能优先**。大模型只在 L1 模糊句兜底时按需调用，排程全程不走 LLM，保证 L5 性能。

## 2. L1 菜谱结构化解析

### 2.1 输出 Schema（单步）
```json
{
  "step_id": 1,
  "raw_text": "原文",
  "device": "蒸箱",
  "temperature_c": 100.0,
  "duration_min": 5.0,
  "needs_human": true,
  "unattended": false,
  "prep_type": "烹饪",
  "depends_on": [0]
}
```

### 2.2 规则设计
- **设备识别**：按"长词优先"词典归一。蒸烤一体机/蒸烤箱→蒸箱；烤箱→烤箱；冰箱/冷藏→冰箱；主锅/炒锅/灶→灶具。烟机/洗碗机/净水机在真实菜谱中极少出现，归为背景设备。
- **时间抽取**：正则统一换算为分钟，支持 `5分钟 / 1.5小时 / 2小时30分 / 30秒`。
- **温度抽取**：优先 `℃`，兜底 `NNN度`。
- **人工介入 vs 无人值守**：切/洗/拌/翻炒/取出→人工；炖/焖/熬/蒸/烤/冷藏/腌制且有时长→无人值守（后台运行，释放双手）。
- **依赖关系**：默认菜内线性依赖（第N步依赖第N-1步）；调度层可在不违反前置的前提下并行。

### 2.3 在 2000 道菜上的批处理结果

> ⚠ **历史数据**（2026-09 在 2000 道外部抓取库上测得）。该库已于 2026-10-02 弃用，
> 菜谱库收敛到官方 100 道（`data/recipes_official_100.csv`）。
> 现行口径见 `python -m scripts.l1_audit`（官方 100 道）。

- 步骤总数 11645，平均 5.8 步/菜
- 时长抽取率 25.7%、温度抽取率 15.0%
- 设备分布：人工切配 69%、灶具 19.4%、蒸箱 6.1%、烤箱 3.2%、冰箱 1.9%

### 2.4 LLM 兜底策略（Prompt）
对规则未命中设备/时长的句子，用 Few-shot Prompt 让 LLM 输出同 Schema JSON，Pydantic 校验后回填。Prompt 示例：
```
你是菜谱解析器。把下面这条烹饪步骤解析为 JSON，字段：
device∈{烟机,灶具,蒸箱,烤箱,冰箱,洗碗机,净水机,人工}, temperature_c,
duration_min(分钟), needs_human, unattended。不要编造数字，缺失填 null。
步骤：{text}
```
规则先跑、LLM 只兜底，兼顾正确率与性能/成本。

## 3. L2/L3 调度算法（移植自成熟排产系统 paichan）

### 3.1 资源建模
把烹饪抽象为带资源约束的有限能力调度（finite-capacity scheduling）：
- 资源：灶具=2 个灶眼、蒸箱/烤箱/冰箱各 1、人工"双手"=1。
- 每个任务请求一个设备资源；**需要动手的任务（如翻炒）同时占用双手**；无人值守任务（蒸/炖/腌制）只占设备、不占双手。
- 纯腌制/冷藏等待：不占任何资源，只是时间延时，可与其他菜并行。

### 3.2 成本函数选槽（移植 paichan SchedulingPolicy）
对每个就绪任务，在多个资源单元上试排，按成本选最优槽位：
```
cost = 等待成本(start-前置完成)×1.0
     + 设备换型/升温惩罚 ×2.0
     + 软冻结任务被挪动惩罚 ×10000  (最小扰动)
```
不是简单贪心，而是带成本权衡的有限能力调度——这是 paichan 已通过测试的成熟算法。

### 3.3 优先级
关键路径（LPT）优先：剩余工序总时长最长的任务先排，保证长任务后台跑、短任务见缝插针。

### 3.4 正确性
调度后自动校验：同 unit 时间不重叠（设备零冲突）、后置任务开始≥前置结束（依赖不违反）。实测 0 冲突 0 违反。

## 4. L4 两级冻结动态重排（移植 paichan rescheduler）

### 4.1 两级冻结模型
- **硬冻结（hard freeze）**：已完成/已开始步骤，时间和资源占用原样锁定，绝不移动；
- **软冻结（soft freeze）**：临近但未做的任务，允许挪动但成本极高（重罚），实现"最小扰动"。

### 4.2 紧急加菜
临时插入一道汤时，只重排非冻结任务，硬冻结任务保持不动。系统输出 `perturbed`（被挪动任务数）作为扰动指标。

### 4.3 KPI 指标（移植 paichan metrics）
- 出锅时间差、总时长、设备利用率、冲突数、依赖违反数；
- 重排前后对比：被挪动任务数、新增冲突数。

### 4.4 通知生成机制
基于时间线触发三类提醒：
- 人工任务到点：`现在可以开始:倒入蒸肉米粉搅拌 [玉米粒蒸排骨]`
- 无人值守临近结束（提前 3 分钟）：`约3分钟后清蒸鳜鱼即将完成, 请准备取出`

## 5. 性能（L5）
- 排程核心纯 Python 启发式，无 LLM 调用；
- 实测 4 道菜端到端 HTTP 约 75ms（优秀线 5s），重排同量级（优秀线 3s）。

## 6. 已知改进方向（交付前迭代）
1. 复合步骤拆分：`设置A；再设置B` 的多段句目前只取首段，需按"；再设置"二次切分。
2. 动态加菜后出锅对齐：对新插入菜的无人值守长任务做延后启动，压缩出锅差。
3. 接入正式 100 道菜谱与 7 类设备真实参数后校准时长缺省值。
4. 甘特图前端可视化（专家评审加分项）。
