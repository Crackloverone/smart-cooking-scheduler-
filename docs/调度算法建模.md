## 1. 排程的重点到底是什么

### 1.1 三类量必须严格分开

这是排程建模最容易翻车的地方。赛题里提到的四个词——**时间、设备利用率、出锅差、冲突**——**不属于同一类数学对象**：

| 类别 | 数学身份 | 出现在模型里的位置 | 能不能进目标函数 |
|---|---|---|---|
| **设备冲突** | 可行性约束 | $s_i + p_i \le s_j \;\lor\; s_j + p_j \le s_i$ | ❌ **绝对不能**。约束违反 = 不可行解，权重再大也只是"罚到不违反"，等于把硬约束软化成"尽量" |
| **依赖关系** | 可行性约束 | $s_j \ge s_i + p_i$ | ❌ 同上 |
| **总时长 / 出锅差 / 连续手动** | 目标函数 | 加权或分层 | ✅ 但必须**语义正确、不可博弈** |
| **设备利用率** | **导出指标** | 求解后统计 | ❌ **不该进目标**（见 1.3） |

**冲突和依赖是约束，不是目标。** 把"冲突数 × 1e6"塞进目标函数，等于承认"允许少量冲突"，
在自动评分里是**一票否决**级别的错误建模。现有实现这一点是对的（`check_plan` 独立校验、
`score_plan` 里 1e6 罚项仅用于策略择优而非最终输出），要保留。

### 1.2 排程的真正重点：三个"不可博弈"的目标

$$\underbrace{C_{\max} = \max_{j} e_j}_{\text{总时长}} \qquad \underbrace{\Gamma}_{\text{出锅差}} \qquad \underbrace{\Omega = \max_k \sum_{\tau=t_k}^{t_k+L-1} \omega_\tau}_{\text{连续手动}}$$

重点是：**每一个都必须是"用户真实体验"的单调函数，而不是一个可以被算法反向利用的代理量。**

- **总时长** $C_{\max}$：单调、不可博弈。做好。
- **出锅差** $\Gamma$：赛题原文是 $\max_d F_d - \min_d F_d$（**原始跨度**）。
  它确实**可博弈**（把菜都拖到最后出锅 → $\Gamma \to 0$ 而 $C_{\max}$ 暴涨），
  但**解法不是换一个量**，而是**用 ε-约束把博弈的口子堵死**：
  阶段 1 先把 $C_{\max}$ 压到最优并锁死 $T \le T^\star + \varepsilon$，
  阶段 2 再最小化 $\Gamma$——此时"拖到最后"已经不可能，因为 $T$ 被钉住了。
  （我曾把 $\Gamma$ 换成语义冷等待 $\sum_d \sigma_d (T-F_d)$，结果与评分表口径相反，见 D9。）
- **连续手动** $\Omega$：**现有项目完全没有这个变量**。它是"人手时间轴上最长的一段连续占用"，
  是一个 **max-run 量**，非线性、需要时间索引建模（见 §3.3 C5）。赛题把它单列为 25 分项，
  实测交付版均值 52.8 min，而精确模型可以压到 33.6 min（**−36.4%**）。

### 1.3 设备利用率：为什么不能进目标函数

现有 `metrics.py` 已经把口径修对了（并集时长 ÷ (腔体数 × makespan)），这很好。但要注意：

$$\text{Util} = \frac{\sum_k \text{busy}_k}{|\mathcal{K}| \cdot C_{\max}}$$

- 分子分母**都**依赖排程结果。最大化利用率等价于"把 $C_{\max}$ 压到最小 + 把设备塞满"，
  而设备塞满会**直接破坏出锅差**（长任务被推迟去填缝）。
- 利用率是**诊断指标**：它告诉你瓶颈在哪台设备（`util_detail` 已经这么做了），
  用来**指导建模**（比如发现蒸箱利用率 95% → 说明瓶颈在蒸箱 → 该考虑同温合炉），
  而不是塞进目标函数。

> **一句话：利用率是仪表盘，不是方向盘。**

## 2. 现有模型的缺陷清单（逐条可验证）

| # | 缺陷 | 证据 | 影响评分项 |
|---|---|---|---|
| **D1** | 出锅差是**可博弈的伪目标** | `cpsat.py` 目标 `min(makespan + gap·k)`；`engine._post_align` 靠右移刷小 gap | 多目标 25 分 |
| **D2** | 同温合炉只做**事后检查**，没进模型 | `cpsat.py` 对蒸箱用 `AddNoOverlap`；`metrics.py` 事后放行 ±15℃ 重叠。求解器不知道"同温可以共用腔体"，**不会主动凑炉** | 并行调度 25 分 |
| **D3** | 加权和的**交换率是拍脑袋的** | `engine.py` 硬编码 `align_w=60.0`；`cpsat.py` 默认 `gap_coef=0.25`，靠环境变量 `FT_CPSAT_GAP_COEF` 手调 | 多目标 25 分 |
| **D4** | **连续手动操作时长根本没进模型** | 全仓库 `grep`：`hand_streak` 只在 `metrics.py` 里**被统计**，没有任何求解器使用它 | 多目标 25 分（单列项） |
| **D5** | **两条轨口径不一致** | `cpsat.py` 无条件丢弃超长冷藏步；`engine._build_tasks` 要求"前缀链"才丢。**任务集不同**，`engine.schedule` 里"取出锅差更优者"的比较**失去意义** | 并行调度 25 分 |
| **D6** | **没有下界，无法证明最优性** | 赛题明确要求"总耗时与理论最优解对比"，项目未提供任何 $LB$ | 并行调度 25 分 |
| **D7** | 保热语义缺失 | 排程不知道"清蒸鱼出锅 10 min 就凉了，红烧肉可以等 30 min" | 多目标 / 动态重排 |
| **D8** | 口径细节：`estimate_duration` 浮点 vs CP-SAT 整数向上取整 | 两轨时长粒度不同（`cpsat.py` 已用 `ceil` 修，但 `engine` 仍是浮点），比较仍不完全对齐 | 并行调度 |
| **D9** | **目标函数与评分表口径不一致（最隐蔽、代价最大）** | 赛题原文把出锅差定义为"**最后一道菜与第一道菜完成的时间差**"，即原始跨度 $\max F-\min F$；而模型优化的是语义冷等待 $\sum\sigma_d(T-F_d)$。两者在"冷菜可以早出锅"时**方向相反** | 多目标 25 分 |
| **D10** | **`_bucket(None)` 把"温度未标注"当成独立温度档** | 独立档与所有档两两互斥 ⇒ 强制该步骤独占一炉。实测 139 个蒸/烤步骤中 **49 个（35%）温度未解析**，受影响实例总时长被抬高最多 **+54%**（74 → 114 min） | 并行调度 25 分 |
| **D11** | **下界公式 `lb_cp` 用"菜内时长求和"代替关键路径** | 菜谱存在并行分支（如"浸泡 3 min"与"上锅蒸 15 min"互不依赖）。求和在 80 组里踩中 1 组，报出 `总时长 42 < 下界 46` 的自相矛盾结论 | 并行调度 25 分 |
| **D12** | **两阶段目标存在并列最优，导致结果不可复现** | 阶段 2 只 `min 出锅差` 时，$[T^\*, T^\*+\varepsilon]$ 内所有同出锅差的解并列最优，求解器返回哪个 $T$ 是**任意的**——实测同一实例随机报 74 或 79 min | 多目标 / 可复现性 |

**其中 D5 是我在实测中最先撞到的**：对同一组菜，交付版算出 makespan 65 min，而按菜谱重算的
理论下界是 335 min —— 差异全部来自"哪些步被算作提前准备"。这不是 bug，是**口径没定义清楚**。

**D9–D12 是第二轮"还能不能更好"的排查中才暴露出来的**，而且它们比 D1–D8 更值钱：
D9 是**优化了错的量**，D10/D11 是**下界/约束写错**，D12 是**结果不可复现**。
修掉这四条之后，精确模型才第一次在三项评分上**同时**优于交付版（见 §4）。

## 3. 完整数学模型

### 3.1 问题归类

$$\text{本问题} = \text{RCPSP} \;+\; \underbrace{\text{批次机}}_{\text{同温合炉}} \;+\; \underbrace{\text{时间滞后}}_{\text{腌制/保热}} \;+\; \underbrace{\text{可替代模式}}_{\text{设备故障}} \;+\; \underbrace{\text{spread 型目标}}_{\text{出锅差}}$$

即 **带批次机与时间滞后的资源受限项目调度问题（RCPSP-Batch-Lag）**，是 NP-hard（Blazewicz 1983）
的强形式。因此**唯一正确的架构**是：精确 CP-SAT 求解 + 启发式暖启动 + 下界汇报间隙。

### 3.2 集合、参数、决策变量

**集合**

| 符号 | 含义 |
|---|---|
| $\mathcal{D}$ | 菜品集合，$d \in \mathcal{D}$ |
| $\mathcal{J}_d$ | 菜 $d$ 的工序集合；全局任务集 $\mathcal{J} = \bigcup_d \mathcal{J}_d$ |
| $\mathcal{E}$ | 依赖弧，$(i,j) \in \mathcal{E}$ 表示 $i$ 是 $j$ 的前置 |
| $\mathcal{K}$ | 设备类型：灶具 / 蒸箱 / 烤箱 / 冰箱 / 净水机 / 洗碗机 / 烟机 |
| $\mathcal{K}^{\text{batch}}$ | 批次机：蒸箱、烤箱 |
| $\mathcal{B}_k$ | 设备 $k$ 的**温度档**集合（由温度按 5℃ 分桶、15℃ 容差合并得到） |
| $\mathcal{F}$ | 动态重排中的**冻结任务集**（已完成 / 已开始） |
| $\mathcal{H}$ | 时间离散化 $t = 0,1,\dots,H$（分钟粒度） |

**参数**

| 符号 | 含义 | 来源 |
|---|---|---|
| $p_j \in \mathbb{Z}_{\ge 1}$ | 工序时长（分钟） | L1 解析；缺省按工序类型估计 |
| $\kappa_j \in \mathcal{K}$ | 工序所需设备 | L1 解析 |
| $h_j \in \{0,1\}$ | 是否占用人工 | L1 解析（$h_j = 1 \wedge \text{unattended}$ 互斥） |
| $\theta_j$ | 温度（℃ 或 $\bot$） | L1 解析 |
| $c_k$ | 设备 $k$ 的单元数（灶具 2 眼） | 设备清单 |
| $Q_k$ | **腔体批次容量**（蒸箱 4 层、烤箱 1 层） | 设备清单 + 建模假设 |
| $\underline{L}_{ij}$ | 最小时间滞后（腌制 ≥ X 分钟） | L1 解析 |
| $\sigma_d \in [0,1]$ | **趁热系数**（0.95 = 爆炒，0.15 = 凉拌） | **LLM 语义先验** |
| $\rho_d$ | **保热上限**（出锅后还能等多久） | **LLM 语义先验** |
| $M$ | 大 M（$\ge H$） | — |

**决策变量**

$$s_j \in [0, H] \quad \text{工序开始时刻} \qquad e_j = s_j + p_j \quad \text{结束时刻}$$
$$F_d = \max_{j \in \mathcal{J}_d} e_j \quad \text{菜品完成时刻} \qquad T = \max_{d} F_d \quad \text{上桌时刻}$$
$$\omega_t \in \{0,1\} \quad \text{人工在 } t \text{ 时刻是否忙碌} \qquad c_{jt} \in \{0,1\} \quad \text{工序 } j \text{ 在 } t \text{ 是否执行}$$

### 3.3 约束

**(C1) 工序依赖** —— 硬约束，不可软化

$$s_j \ge e_i \qquad \forall (i,j) \in \mathcal{E}$$

**(C2) 可重复资源（灶具、冰箱）** —— 容量约束

$$\sum_{j \in \mathcal{J}_k} \mathbb{1}\!\left[s_j \le t < e_j\right] \le c_k \qquad \forall k \notin \mathcal{K}^{\text{batch}},\ \forall t$$

CP-SAT 实现：`AddCumulative(intervals, demands=1, capacity=c_k)`。

**(C3) 批次机（蒸箱、烤箱）** —— **本模型的核心创新**

设备 $k$ 的温度档 $b \in \mathcal{B}_k$，把工序按档分组。**同档可共享腔体，异档必须串行**：

$$\underbrace{\sum_{j \in \mathcal{J}_{k,b}} \mathbb{1}\!\left[s_j \le t < e_j\right] \le Q_k}_{\text{同档：容量 } Q_k} \qquad \forall b \in \mathcal{B}_k, \forall t$$

$$\underbrace{\mathbb{1}\!\left[s_i \le t < e_i\right] \cdot \mathbb{1}\!\left[s_j \le t < e_j\right] = 0}_{\text{异档：强制串行}} \qquad \forall i \in \mathcal{J}_{k,b},\ j \in \mathcal{J}_{k,b'},\ b \ne b'$$

CP-SAT 实现：同档 `AddCumulative(..., Q_k)`；异档两两 `AddNoOverlap`。

> **为什么这比"事后放行"强**：事后放行只是"不判它冲突"，求解器**没有任何动力**去凑炉。
> 写成约束后，求解器会**主动**把两道 180℃ 的烤菜排在同一时间段——因为这样可以
> 把蒸箱/烤箱的时间轴压短，直接改善 $C_{\max}$。实测这一条把蒸箱利用率从"被动共享"
> 变成"主动合炉"。

> **⚠ 温度档 $\mathcal{B}_k$ 必须在数据层定好（D10）。**
> 实测 139 个蒸/烤步骤里有 **49 个（35%）温度未被解析**。若把"温度未知"当成一个独立档，
> 它会与**所有**档两两互斥 ⇒ 强制该步骤独占一炉，受影响实例 $C_{\max}$ 被抬高最多 **+54%**。
> 看似"让求解器自己选档"更优，但**做不到**：同一任务的两个候选档会落进同一个 `AddNoOverlap` 列表，
> 反而禁止它与本档成员并行（我实测踩过这个坑，$C_{\max}$ 从 86 退回 96）。
> 正确做法是**先定温度**：同菜同设备取众数 → 蒸箱默认 100℃（常压蒸就是 100℃ 水蒸气）→
> 烤箱留空（温度差异太大，不猜，保守独占一炉）。见 `model._infer_temp()`。

**(C4) 人工单资源** —— $\sum_{j: h_j = 1} \mathbb{1}[s_j \le t < e_j] \le 1$，实现用 `AddNoOverlap`。

**(C5) 连续手动操作时长上限** —— 精确线性化

先定义人工忙碌指示：

$$c_{jt} = 1 \Rightarrow s_j \le t \le s_j + p_j - 1, \quad \sum_t c_{jt} = p_j, \quad \omega_t \ge c_{jt}, \quad \omega_t \le \sum_j c_{jt}$$

再限制"不存在 $B+1$ 分钟的连续忙碌"：

$$\sum_{\tau = t}^{t+B} \omega_\tau \le B \qquad \forall t = 0, \dots, H-B-1$$

$B$ 可作决策变量二分，也可直接给定。**注意 $B \ge \max_j p_j$**，否则不可行（工序不可拆分）。

> **✅ 已重写为 $O(m)$ 行程编码（2026-10-06）。** 上面那套时间索引 $\omega_t$ 编码规模是
> $O(|\mathcal{J}_{\text{hand}}| \cdot H)$ —— 一个 5 菜实例就有 4725 个布尔变量、
> `#kLinearN: 450 (#terms: 13959)`，实测 **3 s 预算下 7/8 组解不出来**，阶段 1 返回 `UNKNOWN`，
> 而 `_give_up()` 会**静默丢弃**该约束并退回无约束解（报出来的"连续手动 54 min"其实**根本没受约束**）。
>
> **新编码的关键观察：人工容量 = 1 ⇒ 人工任务天然全序。** 于是不需要时间轴指示变量，
> 只要按"参考开工时间"（`_est()`，或先验给的 `hint`）定一个**序**，令
> $s_{k+1} \ge e_k$，再对每个起点 $i$ 与每个 $j>i$ 用**行程和**约束
> "段 $[i,j]$ 的总工时 + 空隙 $\le B$（除非中间存在一次 $> \text{tol}$ 的断点）"。
> 规模与时间轴 $H$ **解耦**，1.5 s 内 OPTIMAL。
> ⚠ 两个实现坑：① CP-SAT 线性约束只接受**整数**系数 ⇒ 时长必须 `int(round(...))`、
> big-M 也必须 `int(...)`，否则报 `Linear constraints only accept integer values`；
> ② $B$ 的定义必须与 `metrics.hand_streak` **同源** —— 现在直接
> `from app.scheduler.metrics import HAND_GAP_TOL`，`tol = round(HAND_GAP_TOL) = 1 min`，
> 模型与评分表报同一个数。
>
> ⚠ **还修了一处"择优丢弃"**：`engine.schedule()` 原先三轨择优只按 $(\Gamma, T)$ 字典序比较，
> 于是**满足 cap 的精确解会被不满足 cap 的贪心解换掉** —— 约束"生效了"但结果被丢掉。
> 现在改为 **cap 可行性优先**（`hand_cap` 未开启时逐字保留原语义，不动基线）。
> 实测 `FT_HAND_CAP=30`：超限 **8/40 → 0/40**（max 30.0，修复前 97.0）。

**(C6) 时间滞后（腌制 / 冷藏 / 保热）**

$$s_j \ge e_i + \underline{L}_{ij} \quad (\text{腌制}) \qquad T - F_d \le \rho_d + \text{slack}_d \quad (\text{保热，软})$$

**(C7) 多模式替代（设备故障）** —— 引入 $x_{jm} \in \{0,1\}$，$\sum_m x_{jm} = 1$，$p_j = \sum_m p_{jm} x_{jm}$。

**(C8) 动态重排冻结** —— $s_j = s_j^{0}$，$\forall j \in \mathcal{F}$。

**(C9) 分钟粒度整数化** —— $p_j \in \mathbb{Z}_{\ge 1}$（**必须与启发式轨共用同一个 `estimate_duration`**，否则 D5 复现）。

### 3.4 目标函数：三层字典序 + ε-约束（不是加权和）

**为什么不能用加权和**：$\alpha C_{\max} + \beta \Gamma$ 里的交换率 $\beta/\alpha$ 无法标定。
1 分钟出锅差到底等于几分钟总时长？没人说得清，于是只能手调 `gap_coef`，调出来的结果
既不可复现也不可解释，还会随菜谱组合漂移。

**第一步：先抄评分表的公式。** 赛题原文把出锅差定义为
> "出锅时间差（**最后一道菜与第一道菜完成的时间差**，小于 5 分钟为优秀）"

即 $\Gamma = \max_d F_d - \min_d F_d$ —— **原始跨度**。
我在第一版里把它"升级"成语义冷等待 $\sum_d \sigma_d \max(0, T-F_d)$，结果在"冷菜可以早出锅"时
**方向相反**：模型主动让凉菜提前很久出锅，语义上对，评分表上 $\Gamma$ 反而变大（见 D9 / §4.4）。
**先对齐评分表，再谈建模深度。**

**第二步：ε-约束法（教科书级多目标处理）**

$$\textbf{阶段 1:} \quad \min \; T \qquad \Longrightarrow \quad T^{\star}$$

$$\textbf{阶段 2:} \quad \min \; \underbrace{W_{\Gamma}\cdot \Gamma}_{\text{① 评分表口径}} \;+\; \underbrace{W_T \cdot T}_{\text{② 总时长}} \;+\; \underbrace{\sum_d \sigma_d W_d + \lambda \sum_d \sigma_d \max(0, W_d - \rho_d)}_{\text{③ 语义保热兜底}}$$

$$\text{s.t.} \quad T \le T^{\star} + \varepsilon$$

其中 $W_d = \max(0, T - F_d)$ 是冷等待。**位权必须动态计算**：

$$W_T = A_{\text{cold}} + 1,\qquad W_{\Gamma} = W_T (H+1) + A_{\text{cold}} + 1,\qquad
A_{\text{cold}} = 60000\,H\,|\mathcal{D}|$$

（$A_{\text{cold}}$ 是 ③ 的取值上限，$H$ 是时间视界。）用常数权重会在大实例上被 ③ 反超，字典序直接失效。

**为什么是"三层"而不是"两层"**：

1. **① 原始跨度**是评分表直接读的量，必须是主序。
2. **② 总时长**也是评分项（"耗时对比 / 压缩率"），所以它必须排在**语义项之前**——
   语义只能做兜底，不许拿评分项去换。第一版把语义放在 ② 之前，实测因此多输了 2 个实例。
3. **③ 语义保热**只在①②都并列时才起作用。它的职责是**防止**"为了对齐而让热菜放凉"，
   不是主导方向。同时它还顺手解决了 D12：**若目标里不显式出现 $T$**，
   $[T^\star, T^\star+\varepsilon]$ 内所有 ① 相同的解并列最优，求解器返回哪个 $T$ 是**任意的**
   ——实测同一实例会随机报 74 或 79 min，结果不可复现。

**$\varepsilon$ 是唯一的自由参数**，物理含义是"最多允许总时长比最优多几分钟"。
$\varepsilon=0$ 得到总时长最优解；$\varepsilon$ 调大得到"更齐但略慢"的解，形成一条 **Pareto 前沿**（§4.3）。
默认 $\varepsilon = 15$（前沿饱和点）。

**连续手动** $\Omega$ 作为约束（C5）而不是目标，避免与 $T$、$\Gamma$ 的交换率纠缠。

### 3.5 语义层的接入：模型在环（Model-in-the-Loop）

LLM **不排程**（不可靠、6 s 延迟会打爆性能分），它提供三样求解器结构上拿不到的东西：

| LLM 产出 | 进入模型的哪个位置 | 影响 |
|---|---|---|
| $\sigma_d$（趁热系数）、$\rho_d$（保热上限） | 目标函数权重 + 保热约束 | 让"出锅差"有了语义 |
| $\underline{L}_{ij}$（腌制最短时长）、可提前备菜步集合 | 约束 C6 + 时间线裁剪 | 压缩 $C_{\max}$ |
| $\varepsilon$、$B$、目标偏好权重 | 阶段 2 的 ε、C5 的 $B$ | 把用户口语翻译成模型参数 |

**关键工程约束**：先验 $\sigma_d, \rho_d$ **离线**对 100 道菜预计算并落盘缓存
（`app/agent/priors.py`，`data/llm_agent_cache.json`），在线排程只读缓存 → **模型在环但不占在线耗时**。

### 3.6 下界与最优性间隙

赛题要求"总耗时与理论最优解对比"。教科书下界

$$LB_{\text{textbook}} = \max\left\{ \max_d \sum_{j \in \mathcal{J}_d} p_j, \; \max_k \left\lceil \frac{\sum_{j \in \mathcal{J}_k} p_j}{c_k} \right\rceil, \; \sum_{j: h_j = 1} p_j \right\}$$

**对本问题有两处是错的**：

1. $\max_k \lceil \sum p_j / c_k \rceil$ 假设同一设备上的任务可**任意并行**，而蒸箱/烤箱是
   **批次机**（只有同温档能共腔，异温档必须串行）。把异温档混在一起打包，等于允许
   "100℃ 的 10 min"与"120℃ 的 10 min"同时进行——公式会给出 $\lceil 20/4 \rceil = 5$，
   而按档打包是 $\lceil 10/4 \rceil + \lceil 10/4 \rceil = 6$。即照抄教科书会得到一个
   **更松**的下界（仍然有效，但更弱），无法反映批次机的串行代价。
2. $\max_d \sum_{j \in \mathcal{J}_d} p_j$ 假设"菜内所有步骤串成一条链"。但菜谱里存在**并行分支**
   （例如"浸泡 3 min"与"上锅蒸 15 min"互不依赖），求和会得到**高于真实最优**的"下界"，
   在 80 组里踩中 1 组，报出 `总时长 42 < 下界 46` 这种不可能结论。
   —— 这是本模型里**唯一**能产生 `C_max < LB` 的项，必须用关键路径取代。

**修正后的下界**：

$$LB = \max\left\{ \underbrace{\text{CP}(\mathcal{G})}_{\text{依赖 DAG 最长路}},
\; \underbrace{\max_k \sum_{b \in \mathcal{B}_k} \left\lceil \frac{\sum_{j \in \mathcal{J}_{k,b}} p_j}{Q_k} \right\rceil}_{\text{批次机产能}},
\; \underbrace{\sum_{j: h_j=1} p_j}_{\text{人工单资源}} \right\}$$

- $\text{CP}(\mathcal{G})$ 用 `_critical_path()` 在依赖 DAG 上求带权最长路（$O(n^2)$ 记忆化，带环保护）。
- 设备项含义：**每个温度档各自打包，再把各档的时间相加**。对烤箱（$Q=1$）退化为全串行；
  对蒸箱（$Q=4$）允许同温档内并行。
- 温度未知（$Q$ 档不明）的步骤**不摊到任何档**——强行摊到某一档会得到一个可能高于真实最优的
  "下界"。不计入只会让下界更松，但保证恒有 $LB \le C_{\max}$。

实测 $LB$ 从未被任何可行解击穿（80 组自洽性检查 **0 违反**）；$C_{\max} = LB$ 在 40% 的实例上成立
（即这些实例已被**证明**是全局最优）。

**最优性间隙**：$\text{gap} = \dfrac{C_{\max} - LB}{LB} \times 100\%$ —— 这是可以直接写进答辩材料的硬指标。

### 3.7 复杂度与求解架构

RCPSP 本身 NP-hard；加上批次机与时间滞后，是 NP-hard 的强形式（不存在 FPTAS）。
因此架构只能是：

```
        用户自然语言偏好
              │
              ▼
   ┌── 离线（一次性）─────────────────────────┐
   │ LLM 抽取语义先验 σ_d, ρ_d, L_ij  → 落盘   │  模型在环，不占在线耗时
   └──────────────┬───────────────────────────┘
                  ▼
   ┌── 在线 ────────────────────────────────────────────────┐
   │ ① 目标塑形：口语 → (ε, B, 权重)      [规则快路径，<1ms] │
   │ ② 三轨并行求解，按 (Γ, T) 字典序取最优：                │
   │      · 贪心启发式（5 条策略，毫秒级，永远可用的兜底）   │
   │      · CP-SAT 加权和（cpsat.py，不支持冻结）            │
   │      · 精确模型（model.py，两阶段 ε-约束 + 支持冻结）   │
   │ ③ 校验：check_plan（独立硬约束校验）                    │
   │ ④ 下界汇报：LB + 最优性间隙                            │
   │ ⑤ 通知生成：模板 + LLM 语境化                          │
   └────────────────────────────────────────────────────────┘
```

**性能预算**：赛题要求初始排程 < 5 s（优秀）。三轨合计实测 `/api/plan`
**4 道菜中位 184 ms / 5 道菜中位 262 ms**，余量 19–27×；单看精确轨在 1.5 s 预算下
实测约 50 ms 收敛（远未用满预算）。

| 30 | 72.5 | 2.75 | 36/40 |

**结论**：前沿在 $\varepsilon \ge 15$ 处**饱和**。默认取 $\varepsilon=15$——总时长只比最优多
1.7 min，却把出锅差从 5.85 压到 2.75，且"优秀档"组数从 30/40 提到 36/40。

### 4.4 为什么 D9 之前一直"出锅差更差"

第一版精确模型出锅差**比交付版差**，原因不是模型弱，而是**优化了错的量**：
模型按"热菜不要干等"（$\sum\sigma_d\cdot\text{cold}_d$）优化，于是**允许冷菜（低 $\sigma_d$）提前很久出锅**；
而评分表的出锅差是 $\max F-\min F$，冷菜提前出锅**直接抬高**这个值。
一个"语义上更对"的解，在**评分表上更差**。这是排程建模最容易翻车的地方：
**先抄评分表的公式，再谈建模深度。**

#### 4.5.1 接入时踩到的两个坑（都是"轨自己把自己锁死"）

**(1) `slack` 必须给足，否则精确轨被 ε-约束锁死。**
精确轨最初沿用了 `solve_exact` 的默认 `slack=0`，即"阶段 2 严格不许超过最优总时长 $T^*$"。
这在语义上很干净，但**把用于对齐出锅时刻的余量也一并掐死了**：

| 实例（4 菜） | `slack=0` | `slack=5` | `slack=15` |
|---|---|---|---|
| 总时长 / 出锅差 | 148.0 / **44.0** | 148.0 / **44.0** | 158.0 / **3.0** |

`slack=0` 时出锅差 44 min（比贪心还差），`slack=15` 时降到 3 min，总时长只多 10 min。
即 **ε-约束里的 $\varepsilon$ 是"买出锅差的钱"，给 0 就等于不买**。
线上取 15（= `solve_with_gap` 的默认值，也是 Pareto 前沿的饱和点），
可用 `FT_EXACT_SLACK` 覆盖。
> 教训：ε-约束方法里 $\varepsilon$ **不是**"越严格越好"的参数，
> 它是两个评分项之间的**显式交换率**，必须按评分表调，不能按"数学上干净"调。

**(2) 精确轨的 `allow_preprocess` 不能只跟随当前策略。**
第一版让精确轨的备菜口径**跟随获胜策略**（保证与贪心解同任务集）。听起来最严谨，实际是把
精确轨绑在了贪心策略的排序质量上：某 4 菜实例中，获胜策略恰好是 `critical_path`
（`prep_ahead=False`），于是精确轨只能给 158 min / 出锅差 3；而它本可以给
**102 min / 出锅差 3**（同出锅差，总时长少 35%）。

关键事实：**"备菜移出当天时间线"本来就是本系统设计空间的一部分** ——
策略表里 `prep_first` / `compress` 两条策略的 `prep_ahead=True`，交付版本来就会产出
"备菜在 $t<0$、不计入官方 `cookingTimeline`"的计划（官方适配器显式跳过 `start_min < 0` 的任务）。
所以正确的做法不是二选一，而是**把两个变体都作为候选**，让选策略用的同一个
`score_plan` 目标来裁决 —— 这和策略集里同时保留备菜/不备菜两条策略是同一个逻辑。

默认行为：`FT_EXACT_PREP=both`（两个变体都试，取更优）；
`FT_EXACT_PREP=off` 严格跟随策略（供口径审计）；`FT_EXACT_PREP=on` 只用备菜变体。
接入 (1)(2) 后，线上指标**与精确模型上限参考完全一致**（82.3 / 2.11），
说明"最好的模型"终于真的在线上跑着了。

**一句话**：把求解器算到死也拿不到那 1.06；真正的提升空间在
