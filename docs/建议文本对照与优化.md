## 1. 第一块（7 节）逐条对照

### 1.1 §一 设备约束：独占 / 容量 / 切换成本

**建议文本原话**：
> 「设备切换成本 —— 模式切换需要等待降温 / 升温，不能立刻从高温烘烤切低温蒸制；排程时预留切换缓冲时间。」

**现状**

| 子项 | 落点 | 说明 |
|---|---|---|
| 独占（容量 1） | `engine.RESOURCE_UNITS` | 灶具 / 人工容量 1，蒸箱 / 烤箱容量 N |
| 容量覆盖 | `engine.resource_override()`（ContextVar） | **全局字典永不被改写** —— 请求级临时改容量不会污染其它请求 |
| 同温合炉 | `_temp_share_fit` + `model._bucket()` | 温差 ≤ `STEAM_TEMP_TOL`(15℃) 可并行一炉 |
| 切换成本 | **本轮新增** | 见下 |

**差距（本轮前）**：`cooldown` 在整个代码库里 **0 处实现**。搜索 `cooldown / 降温 / 冷却等待`，只有 L1 解析层的「晾凉」等**文本词**降级为 `等待`，而**排程层完全不知道**"200℃ 刚出炉不能立刻 180℃ 进炉"。
实测（`.cache/_chamber_physics.py`，50 组 seed42）：同腔体**异温背靠背 5~6 处**，且**全部**是「高温 → 低温」方向 —— 这正是建议文本点名的那个坑。

**本轮动作**

```python
# app/scheduler/engine.py
COOLDOWN_MIN_PER_100C = 2.0        # 每降 100℃ 需要 2 分钟
COOLDOWN_ENV = "FT_COOLDOWN"       # on/off; off 时行为与旧版逐字一致（供 A/B）
COOLDOWN_RATE_ENV = "FT_COOLDOWN_RATE"

def cooldown_minutes(prev_temp, next_temp) -> float:
    if not cooldown_enabled():                       return 0.0
    if prev_temp is None or next_temp is None:       return 0.0
    drop = float(prev_temp) - float(next_temp)
    if drop <= STEAM_TEMP_TOL:                       return 0.0   # 同温合炉不受影响
    return round(drop / 100.0 * cooldown_rate(), 4)
```

三条纪律（都写进了注释，避免后人改坏）：

1. **只罚降温，不罚升温** —— 升温成本已经由 L1 的**预热步**显式建模（`insert_preheat_steps`），再罚一次就是双重计价。
2. **同温容差与合炉共用** `STEAM_TEMP_TOL` —— 180℃ 与 182℃ 照旧一炉出，否则"加了降温"会把同温合炉一起干掉。
3. **降温是可行性，不是目标项** —— 它**不进** `(Γ, T)` 字典序。理由：任何能被"优化"的东西都会被反向利用（比如求解器发现"把菜改成一直高温"就没有降温了）。

**接入点（四处，缺一不可）**

| 位置 | 作用 |
|---|---|
| `_ResourceTimeline._fit` | **烤箱**（按独占处理，`shared=False`）排下一段时按余温顺延 |
| `_temp_share_fit` | **蒸箱**（同温合炉，`shared=True`）串行段之间插入缓冲 |
| `engine.schedule` 的 `_cd_ok` + `prefer_cd` | **交付前**的 ε-约束选择（见下） |
| `metrics.device_switches` | 校验器：返回 `[(腔体, 前任务, 后任务, 降温需求)]`，判据与 `cooldown_minutes` **同源** |

> ⚠ **降温缓冲有"两份实现"**（`_fit` 给烤箱、`_temp_share_fit` 给蒸箱），
> 测试与变异都必须**各覆盖一条** —— 只测烤箱时把 `_temp_share_fit` 里的降温删掉
> **照样全绿**（本轮实测漏网过一次）。

**⚠ 一个必须记住的教训：可行性门不能"无界"**

`_better` 里原来有两道门（`hand_cap` 与 `cooldown`）。第一版把降温写成**无界**的
字典序优先（"只要合规，Γ 差多少都认"）。实测被狠狠打脸（seed=42 第 23 组）：

| | Γ | T |
|---|---|---|
| `FT_COOLDOWN=off`（旧基线） | **2.0** | 226.0 |
| `FT_COOLDOWN=on` + **无界**门 | **191.4**（95 倍） | 262.4 |

原因：精确轨 / CP-SAT 轨的批次机里**没有"降温"这一项**，它们给出"Γ 很好但违规"的解；
贪心轨插了缓冲、合规，但 Γ 可能很差。无界地"合规优先"就变成**拿一处降温违规换掉整份计划**。

**修法：降温走 ε-约束**（`engine.prefer_cd(best, best_cd, budget)`，`FT_CD_BUDGET` 默认 **5.0 分钟 Γ**）：

```python
def prefer_cd(best, best_cd, budget):
    if best is None:  return best_cd
    if best_cd is None or best_cd is best:  return best
    if best_cd.finish_gap_min <= best.finish_gap_min + budget:
        return best_cd          # 预算内：合规优先
    return best                 # 预算外：保留更优解，违规交给 insight 报红色预警
```

**为什么 `hand_cap` 仍然无界、降温却要有界** —— 两者的约束强度不同：

- `hand_cap` 是**用户/赛题显式给的硬指标** ⇒ 不满足就是不可行，无界过滤；
- 降温是本系统**自己加的物理精化** ⇒ 只在"代价可控"时才换解，超出预算就
  **如实报出来**而不是偷偷把分数做烂（后者正是建议文本 §七.1 要的"风险提示"）。

**A/B 实测（修正后）**：见 §5 —— `on` 与 `off` 在**全部指标上完全一致**，
即降温的净代价降到 **0**，同时保留了"能免费合的地方就合"与"超预算就报警"。

**证据**：`tests/test_insight.py` **13 项**（降温口径 4 + 校验器 4 + 贪心两轨各 1 + 择优门/ε-约束 3）；变异自检 `scripts/_mutate_insight_guards.py` 命中 **11 条**。

### 1.2 §二 菜品工序与时序约束

**建议文本原话**：
> 「强依赖：A 完成后 B 才能开始」「软时间窗：某道菜最好在 18:30 前后上桌」「固定时长：蒸 8 分钟就是 8 分钟」

| 子项 | 现状 | 差距 |
|---|---|---|
| 强依赖 | ✅ `RecipeStep.depends_on`，L1 解析建 DAG；`model.py` 里是关键路边 | 回指型指代未识别（「三味蒸鳗鱼」#4 未连 #3）—— **已知，只放宽不收紧** |
| 固定时长 | ✅ `estimate_duration()` | `等待`步（腌制/浸泡）**必须计入关键路**，只从 energy/hand 排除 |
| 软时间窗 | ❌ **未做** | 见 §9 理由 |

**关键路下界的两个静默陷阱**（已修，写在这里是因为它们不报错）：

1. `lower_bound_from_plan` 必须走 `_dep_key()`。`tuple(d.split("#"))` 给出的是**字符串** step_id，而 `dur` 字典的键是 **int** ⇒ 依赖边**全部丢失**，关键路退化成"最长单步"，下界虚低。
2. `等待`步必须计入关键路。腌制 4 小时是**真实流逝时间**，漏掉它下界就假了。

修后 `gap` 中位 **0.0%**、**68~72% 实例 makespan == 可证下界**。

### 1.3 §三 人力操作资源约束

**建议文本原话**：
> 「同一个厨师不能同时做两件事」「连续工作多久要休息」

- **容量 1**：`双手-1`，`engine.RESOURCE_UNITS["双手"] = 1`；灶具步**全占人工**（`uses_hands`），所以三个 3 min 的灶具步只能串行。
  > ⚠ 肉眼看甘特图最容易漏掉这条耦合 —— 灶具看起来是"三台设备"，实际背后是"一双手"。
- **连续手动上限**：`FT_HAND_CAP` → `metrics.hand_streak(plan, gap_tol=HAND_GAP_TOL=1.0)`（口径：间隔 ≤ 1 min 视为连续）。
- **本轮校准**：不满足上限时**退化成按 (Γ, T) 比，而不是拒用**。原实现直接拒用 ⇒ 三条轨可能全被拒 ⇒ 交空计划。现在"尽力而为 + 如实报告"。

### 1.4 §四 排程优化目标

**建议文本原话**：
> 「不要把所有东西塞进一个加权和 —— 硬约束不进目标函数」

| 纪律 | 落地 |
|---|---|
| 硬约束（设备冲突 / 依赖）**绝不进目标函数**，只做可行性 | `_better` 的两道门 + `checker` |
| 目标函数不得含**可被反向利用的代理量** | 设备利用率是**仪表盘不是方向盘**；可博弈时用 **ε-约束堵口子** |
| 多目标用**字典序**而非加权和 | 位权 `W_T = A_cold+1`、`W_Γ = W_T*(H+1)+A_cold+1`、`A_cold = 60000*H*|D|`；优先级 **Γ ≫ T ≫ 语义冷等待** |

**口径铁律（照抄评分表，不许"改良"）**

- 出锅差 **Γ = `max F − min F`**（原始跨度）。**不要**换成语义冷等待 `Σσ_d(T−F_d)` —— 冷菜可以早出锅时两者**方向相反**，会得到"语义更对、评分更差"的结果。
- **"完成时刻" ≠ "出锅时刻"**：Γ 用"最后一步结束"（评分表口径，**不动**）；**保热惩罚**用"最后一次进加热设备结束"（`metrics.dish_cook_finish`）。混用 ⇒ 求解器**被奖励**"早做熟干等"，实测差额中位 **23 min**。
- **保热项必须"以 Γ 计价"**：`min(hot, w_gap × FT_HOT_BUDGET)`，默认 **0.5 分钟 Γ**。用完成时刻 ⇒ 恒 ≈ 0（等于没参与择优）；无界 ⇒ 一道菜等 170 min 就**夺走 Γ 的权**（`<5min` 从 90.3% 掉到 80.3%）。

### 1.5 §五 异常与鲁棒性

**建议文本原话**：
> 「设备坏了怎么办」「某道菜做久了怎么办」

| 场景 | 现状 | 差距 |
|---|---|---|
| 设备故障顶替 | ✅ `engine.DEVICE_FALLBACK`（蒸箱/烤箱坏 → 灶具 → 人工） | 多模式顶替未做（见 §9） |
| 步骤超时 | ❌ | 无"实际耗时偏离计划"的输入通道 |
| 插单 | ⚠ 部分 | `reschedule(..., hard_frozen=)` 支持冻结已完成步骤，但没有"运行中插入新菜"的接口 |
| **降温违规拦截** | ✅ **本轮** | 见 §1.1 |

**顶替实现里踩过的坑（写进护栏）**：

- **顶替必须同步改 `device`，不能只改 `res`**。只改 `res` 会产出 `device="蒸箱"` + `unit_id="灶具-1"` 的矛盾任务；而 `checker.overlap_allowed()` 按 `device` 判"蒸箱同温可共享"豁免 ⇒ **把真实灶具冲突判成合法重叠**（静默漏报）。护栏 `tests/test_device_substitution.py`（13 项）。
- `use_cpsat=False`（设备故障）**只许关 CP-SAT**。写成 `if use_cpsat:` 把整个精解块跳过是错的 —— **精确轨认容量覆盖**，故障时仍然该跑。也**不能**写 `max(1, cap)`。

### 1.6 §六 排程算法选型

**建议文本原话**：
> 「小规模用精确解，大规模用启发式 + 局部搜索，按菜数分流」

本系统是**三轨并行取优**（不是二选一）：

```
贪心（6 策略，含 composite）
  → CP-SAT（加权和，不支持冻结）
    → 精确模型 model.py（支持 fixed）
      → 按 (Γ, T) 字典序取优
        → _add_kitchen_semantics() → _restore_missing_steps() → _rebase_to_first_resource()
```

- `composite` 必须**新增**而非替换原 5 条 —— 收敛成一条掉 3~5 个点。
- **可证最优率 ~98–100%**（`plan.solver_status`）：1.5 s 生产预算下 3–5 菜 **100/100**、6–9 菜 **60/60** 为 OPTIMAL。公平版预算探针 20 组 **dT = dG = 0.0** ⇒ **预算不是瓶颈**。
- ⚠ 调用方**显式传** `use_exact=` 会绕过"`is None` 才读 `FT_EXACT`"的分支 ⇒ **`dispatch.solver_budgets` 也必须自己认 `FT_EXACT`**，否则消融实验 / `verify_model` 对照组**静默失效**。

### 1.7 §七 常见坑总结

| 坑 | 本系统的处置 |
|---|---|
| 时间锚点漂移 | `_rebase_to_first_resource`（`FT_ANCHOR` 默认 on）。原定义"提前准备段结束"会在备菜后夹**纯等待**（腌制）⇒ t=0 之后"四行设备全空"（最简复现：腌制 10 + 烤箱 25，T 从 35 掉到 25）。**有 `hard_frozen` 时绝不平移**。 |
| 非备菜任务早于 t=0 | `dep_ready = max(0.0, …)`。备菜右对齐到 0 ⇒ `end_min` 为负；若烹饪步前置只是**早早结束的备菜步**，贪心 `dep_ready` 就是负数 ⇒ 把占设备/占人工的步排到 t<0 ⇒ 被 `_to_plan` 的 `start>=0` 漏掉（**不计入 T/Γ 也不进 `check_plan`**）。实测 **8/100 中招**。护栏 `test_no_resource_task_before_day_start`（必须走 `adapter.plan_recipes`）。 |

### §七 排程结果输出与校验规范

**建议文本原话**：

> 「§四.3 冲突处理：优先告警，返回冲突原因（例如：蒸箱容量不足 / 操作员不足）」

**本轮前**：`/schedule` 只回 `plan / kpi / check / elapsed_ms`。用户拿到计划后**看不出**"哪一步是瓶颈""哪里在硬撑"。冲突有 `check_plan`，但**只给结论不给归因**。

**本轮动作**：新建 `app/scheduler/insight.py`，只读旁路，**不参与任何优化决策**。

```
insight.analyze(plan, priors) → {
  critical_path: {task_ids, dishes, span_min, makespan_min, method, note},
  risks: [{level, kind, task_id, dish, message}],   # kind ∈ cooldown|conflict|critical|bottleneck|hot_wait
  high, mid, summary
}
```

**关键路径为什么用"零余量链"而不是"最长时长链"**

教材式的"按任务时长累加找最长链"在这里会**指错方向**：本系统会刻意给短菜加空等让它和长菜同时出锅（同出锅对齐），于是那条"时长最长"的链往往只到 makespan 的一半左右，真正的瓶颈在别处。
本模块改用**零余量链**：从决定出餐时刻的任务往回走，每一步都要求"前一步结束 == 后一步开始"（中间没有缓冲，容差 `ZERO_SLACK_EPS=0.01`）。语义非常干净 —— **链上任何一步延误 X 分钟，出餐就晚 X 分钟**。

⚠ 但零余量链在"到处是对齐空等"的计划里会**退化成长度 1**（实测某 5 菜实例 `span_min=1.0, steps=1`）。所以：

- `len(chain) < 2` 时退回 `_longest_duration_chain`（记忆化递归 + `onstack` 环检测）；
- 返回 `method` 字段**显式说明用了哪种口径** —— 两种口径的 `span_min` 完全不同，不标注就会有人拿"最长工序链"去对"零余量链"的数字，怎么算都对不上。

**风险清单刻意"不吵"**

第一版做了"逐任务余量为 0 就报警"，报出 **14 项**、其中 13 项是噪声 —— 紧凑排程里背靠背**本来就是优化目标**。改成只报**集合级**结论：

| kind | level | 判据 |
|---|---|---|
| `cooldown` | **high** | 同腔体异温背靠背且留的时间不够（`device_switches`） |
| `conflict` | **high** | `check_plan()` 的 details 非空 |
| `critical` | mid | 关键路径 ≥ 2 步全程无缓冲 |
| `bottleneck` | mid | 单设备占用率 ≥ `BOTTLENECK_UTIL=85%` |
| `hot_wait` | mid | 必须趁热的菜（`serve_hot ≥ 0.85`）出锅后等待 > `hold_min` |

`analyze()` 任何异常都返回 `{"error": …}` —— **诊断失败绝不能拖垮排程**。

### 3.1 设备降温缓冲

- 代码：`engine.py`（`cooldown_minutes` / `_ResourceTimeline._fit` / `_temp_share_fit` / `_cd_ok` / `prefer_cd` / `_feas_ok` / `_better`）、`metrics.py`（`device_switches`）
- 开关：`FT_COOLDOWN`（默认 on）、`FT_COOLDOWN_RATE`（默认 2.0 分钟/100℃）、`FT_CD_BUDGET`（默认 5.0 分钟 Γ）
- 实测：违规 5~6 → **0**；三档 A/B（`off` / 只插缓冲 / 全开）**逐项完全一致**（Γ 中位 1.5、均值 3.40、<5min 82%、T 59.42，**Γ 变差 0 组**）⇒ **净代价 0**
- 护栏：`tests/test_insight.py` **26 项**（含降温 11 项）+ 变异 **17 条**（含降温 13 条）

**为什么最终要加 ε-约束**：降温是**附加**的物理精化 —— 如果把它当成"无界的可行性门"
（"宁可 Γ 更差也要合规"），实测 seed42 的 #23 会把 Γ 从 **2.0 抬到 191.4**（95 倍）。
所以收口成 `prefer_cd(best, best_cd, budget)`：**预算内**换合规解、**预算外**保留更优解，
并把违规交给 `insight` 报红色预警 —— 分数与物理都不撒谎。

⚠ **`best_cd` 的登记条件必须是 `_feas_ok`（hand_cap **且** 降温），不能只判降温**。
第一版只判降温，于是"降温合规但超连续手动上限"的贪心解，把 hand_cap 达标的精确解按 Γ 换掉了
—— 全量回归当场红：`hand_streak 99.0 > 30`。修法是显式约束优先（hand_cap 先、降温后）。

> ⚠ **降温缓冲有"两份实现"，必须各测一条**：烤箱按独占处理（`shared=False`）走

### 3.4 真浏览器探针抓到的布局回归（**这条只有真 Edge 看得见**）

新面板一加，`ui_layout_probe.mjs`（真 Edge + CDP，11 个视口）当场红：

```
==== 汇总: 113 通过 / 1 失败 ====
  · 时间轴高度显著大于任务明细  gantt=35 tasks=104
```

**根因**：`.riskpanel` 是 `#ganttWrap`（`display:flex;flex-direction:column`）的**兄弟节点**，
而 `#gantt` 是 `flex:1`。面板一有内容就去抢甘特图的余量 —— 5 条风险时甘特图只剩 **35px**。
桌面断点下 `#v-plan` 是**固定高度**（`calc(100vh - --chrome)`），且**没有** `#gantt{min-height}`
兜底（只有 641~1024px / ≤640px 两个断点才有 300/240px），所以这个挤压是**静默**的：
jsdom 探针全绿、pytest 全绿，只有真浏览器排版探针会红。

**修法**（`.riskpanel` 加两个性质）：

```css
.riskpanel{flex:none;max-height:110px;overflow-y:auto;margin-bottom:10px}
```

- `flex:none` —— 不参与抢余量，余量留给甘特图（否则 `cardFill.slack` 也不再为 0）；
- `max-height` + `overflow-y:auto` —— 风险多时面板内部滚动，而不是无限长高。

**判定性实验（证明"上限真的在起作用"，而不是碰巧没超）**：把 `max-height` 从 `110px` 改成
`10px` 再跑同一探针 —— 甘特图 **152px → 252px**，正好差 100px ⇒ 面板此前确实顶在上限上。

## 4. 明确不做的（含理由）

| 项 | 为什么不做 |
|---|---|
| **软时间窗 / 上桌时刻**（二.3） | 官方接口规范与评分表里**没有这个输入**。凭空加一个"上桌时刻"字段，要么没数据源、要么得自己编默认值 —— 那是把赛题口径改掉。真要做，应该等输入契约里出现该字段。 |
| **口感随时间的连续衰减函数**（五） | 同理：评分表只有 `hold_min` 阈值，没有衰减曲线。自己发明一条曲线 ⇒ 指标不可比、无法与官方对齐。 |
| **多模式顶替**（五.1） | `DEVICE_FALLBACK` 已覆盖"设备整机故障 → 灶具 → 人工"。多模式顶替需要"灶具能不能替代烤箱的某个模式"这套**能力语义**，官方设备参数清单里没有该信息，硬编会造出非法任务。 |
| **收紧 makespan 下界** | `Γ_lb = Σd − max d` 已经是可证下界，`verify_model` 40/40 OPTIMAL。再收紧要引入更复杂的下界推导，收益（gap 中位已经是 **0.0%**）不成比例。 |
| **时间粒度取整到 5 分钟** | 会让 `Γ_lb` 与 `makespan == 下界` 的等式失效（68~72% 实例会破），并且与评分表的原始跨度口径冲突。 |
| **逐任务余量预警** | 实测报 14 项、13 项噪声（见 §2 §七）。 |
