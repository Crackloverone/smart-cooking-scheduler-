## 1. §2.2 资源模型：烟机为什么不进求解

设计文档把烟机列为"联动资源，不参与调度求解"。本系统的落地方式：

- `device_spec.hood_level(text, mode)` 按灶具任务类型派生档位：`爆炒/煎炸/油炸 → 强档`，`炖煮/煲汤 → 弱挡`；
- 默认 `FT_HOOD=off`，**不生成独立时间轴行**。

**为什么不生成独立行**：官方《接口规范》全文 **0 次**提到"烟机"，官方 100 道菜谱 **0 次**提及。
凭空生成"烟机联动"行会被 `scripts/step_provenance.py` 判为 **R2 非法合成行**（实测打开 `FT_HOOD=on`
后立刻报出 3 条）。旧实现还给它 `end+3` 分钟，直接把 `timeSpent` 顶高（实测某 3 菜实例 136 → 142 分钟）。

> 折中：**档位算出来、挂在任务上**（满足 §4.2"按灶具任务类型生成联动参数"），
> 但默认不污染时间轴。需要展示联动行时 `FT_HOOD=on` 即可，代价是溯源护栏会报警（这是刻意的）。

## 2. §3.1.2 设备别名映射

`DEVICE_ALIAS_RULES` 是**有序**表，按"配件 → 复合设备 → 模式名 → 常规设备"的优先级匹配：

```python
(["蒸烤盘","烤盘","蒸盘","烤架","蒸架","油纸","锡纸","铝箔"], PART, None)   # 配件：命中即跳过
(["蒸烤一体机","蒸烤箱"],                                     AMBIGUOUS, None)
(["方太智能烹饪设备","智能烹饪设备","烹饪机","方太"],            AMBIGUOUS, None)
(["全开烤"], DEVICE_OVEN, "全开烤")   # 官方烤箱 7 个模式名全部收录
...
(["电蒸箱","蒸箱","蒸笼","蒸锅"], DEVICE_STEAMER, None)
(["主锅","炒锅","汤锅","平底锅","铁锅","锅"], DEVICE_STOVE, None)
```

**三个必须踩过的坑**：

1. **配件词必须先于设备词**：`"蒸烤盘"` 里的"蒸/烤"若被当设备，会让**纯备料句**占满蒸箱/烤箱。
   实测 19 条备料句（如「将在烤盘中铺上锡纸，将烤串放在烤架上」）被推成 25 分钟烤箱任务。
2. **不能收裸「净水」**：会命中**食材**「纯净水」（100 道菜里出现 4 次），凭空多出 4 条净咖一体机任务。
3. **官方烤箱模式名要收全**：漏了 `全开烤` ⇒「茯苓饼干」的「设置全开烤150℃」被判成**蒸箱 150℃**
   （越界，又被钳到 120℃）—— 一句话两个错。

**验收**：`audit_doc` 的 3.1.2 条**直接调 `find_device()`** 跑 8 条探针，而不是查"词在不在表里"
（别名是**子串匹配**，「方太蒸箱」由表里的「蒸箱」覆盖；查整词会造出一堆假缺陷 —— 第一版就踩了这个坑）。

## 3. §3.1.4 + §4.1 预热：独立任务 + 同温共享

**预热是 L1 拆出来的真实 `RecipeStep`**（`device_source = "预热"`），进 DAG、占真实设备槽、
`needs_human=False`（因此可与人工切配并行，对应 §4.1.3）。

拆分规则（数据驱动，不凭空造）：

| 规则 | 理由 |
|---|---|
| 原文写了"预热"**且未被否定** | 「豆沙松糕」写"**无需预热**"，必须排除 |
| 正式烹饪步 ≥ `PREHEAT_MIN_TASK_MIN`（5 min） | 太短不值得单列 |
| 同菜同设备**只预热一次** | 避免重复占炉 |
| 预热节点排在正式步**紧前面** | 依赖链自然 |

**正确产出恰好 5 条**：半熟芝士蛋糕 / 草莓蛋挞 / 油醋汁剁肉饼蒸和乐蟹 / 烹香酷炒汇 / 蔬菜塔。

**同温共享**（§4.1.2）：`engine._merge_preheat()` 把**同设备 + 同温（±10℃）** 的预热区间合并成一行，
`recipeNames` 带上所有受惠的菜。实测 `[半熟芝士蛋糕, 草莓蛋挞, 蔬菜塔]` → 合出
`烤箱预热 48-58 → ['草莓蛋挞','蔬菜塔']`。

### ⚠ 本轮修掉的缺陷：预热节点**不能用 `endswith("预热")` 识别**

`「豆沙松糕」第 9 步` 原文是：

```
再次放入方太智能烹饪设备，选择蒸模式-普通蒸，100℃，25分钟，无需预热
```

句尾**恰好是"预热"**。旧过滤器 `raw_text.endswith("预热")` 会把它当成预热节点；
一旦它和别的菜的预热区间相邻，`_merge_intervals_meta` 就把它并进"预热共享"行 ——
**这条真实的 25 分钟蒸箱烹饪步从甘特图上凭空消失**。

修法：`engine.PREHEAT_NODE_TEXTS = ("蒸箱预热", "烤箱预热")` **精确文本匹配**
（合成节点的文本恒为 `f"{dev}预热"`；实测 100 道菜原文里没有任何一句恰好等于这两个词，所以安全）。

## 4. §3.3.1 四级复合优先级

`engine.STRATEGIES["composite"]` 实现文档的 `关键路径 > LPT > 人工优先 > 短任务填充`：

```python
on_dev = 0 if t["res"] else 1
return (-rank[k],                                   # ① 关键路径（决定总时长下界）
        on_dev,                                     # ② LPT 只对占设备任务有意义
        (-t["dur"] if on_dev == 0 else 0.0),
        0 if t["uses_hands"] else 1,                # ③ 人工是单资源瓶颈，同档先占坑
        t["dur"],                                   # ④ 短任务填充，尽快让出设备
        t["step_id"])
```

**为什么是新增一条策略，而不是替换原来的 5 条**：原来 5 条的 `order`（`rank`/`long`/`hot`/`prep`）
是**刻意互相拉开**的取向，组合择优靠的就是这种多样性；把复合键塞进去等于把 5 条收敛成 1 条，
实测会掉 3~5 个百分点。新增策略对"取最优"是**单调不劣**的（`consider()` 保留最低分），
代价只是每次多跑一遍毫秒级贪心。

**验收**：`audit_doc` 真的跑一次排程并从 `AgentResult.trace` 里确认 `composite` 进了评估链。

## 5. §3.3.3 求解器按菜数分流

### 文档原意 vs 落地方式

文档写"N ≤ 6 用 CP-SAT、N > 6 用启发式"。**照字面实现会比现状更差**：本系统不是二选一，
而是**三轨集成**（贪心 5 策略 → CP-SAT 加权和 → 精确模型），各产一份可行解后按
`(出锅差 Γ, 总时长 T)` 字典序取最优。实测 60 组：开三轨 88.3 / 2.33 / 27.9 vs 关三轨 109.3 / 3.97 / 38.6。

文档这条规则的**真实意图是控制响应时间**，而实测证明大 N 确实会破线：

| N | 旧口径最大耗时 | 分流后 |
|---|---|---|
| 6 | 545 ms | 545 ms |
| 12 | 4492 ms | 2532 ms |
| 20 | **5044 ms（2/9 破线）** | **2295 ms（0/9 破线）** |

根因：最终精解段的预算是**写死的**（CP-SAT ≤1.2 s + 精确模型 ≤1.5 s），不随 N 收缩。

**落地**：`scheduler/dispatch.py::solver_budgets(N, pool)` —— 按 `6/N` 收缩，留 25% 余量，
低于 `MIN_USEFUL`（0.25 s）就**直接关掉该轨**而不是给个 0.01 s 假装在跑。
贪心轨永远先跑，所以**任何 N 下都有一份合法排程**。

> ⚠ 一个真实的坑：调用方一旦**显式传** `use_exact=`，`engine.schedule` 里
> "`use_exact is None` 才读 `FT_EXACT`"的分支就被绕过 —— 于是 `FT_EXACT=off` 失效，
> `verify_model` 的"关第三轨"对照组 60 组全打平（看起来像"第三轨毫无价值"）。
> 所以 `solver_budgets` 自己也必须认 `FT_EXACT`。回归：`tests/test_dispatch.py`（7 项）。

## 6. §3.4.2 同类食材合并用量

`adapter._merge_unit(a, b)`：同单位数值相加（`30克 + 20克 → 50克`），单位不同则并列
（`75克 + 1个`）。旧实现是同名食材直接**覆盖** `unit`，于是「五花肉 200克」+「五花肉 300克」
只剩 300 克，**采购量凭空少一半**。

**验收**：`audit_doc` 构造两道共用蛋黄的菜，断言出现"多份单位"的合并项且没有未合并的重复项。

## 8. 步骤溯源（本轮新增的护栏，隐含要求）

**排程出的每一步都必须能在菜谱原文找到出处，且原文的每一步都不许消失。**
`scripts/step_provenance.py`，四条断言，每条都是实测事故换来的：

| 断言 | 防的事故 |
|---|---|
| **R1 凭空步骤** | `_add_kitchen_semantics()` 曾合成「烟机联动」45 个 +「预热」148 个 |
| **R2 非法合成行** | 无 `dish` 的任务只允许"预热共享"，且 `raw_text` 必须是精确文本 |
| **R3 真实步骤消失** | 精解轨把「半熟芝士蛋糕」#1–#8（含两条**灶具**步）整段删掉 |
| **R4 依赖违反** | 步骤挪到 t<0 而它的前置还在当天 |

### ⚠ R3 背后的缺陷：精解轨"少干活换指标"

`model.extract_tasks` 与 `cpsat.slim` 都会把备菜步**整步删掉**，而贪心轨是排到 t<0。
精确轨胜出时甘特图丢掉整段备菜 —— 实测「半熟芝士蛋糕」12 步只剩 4 步，
连"锅置火上，倒入牛奶和黄油""放入芝士，开小火，拌匀，略煮"这两条**灶具**步都不见，
看上去就是"没做糊就直接烤"。

**更严重的是**：它正是靠少排 16 步把 `makespan` 从 124 压到 82、出锅差从 20 压到 1 ——
**指标是"少干活"换来的**，属于目标函数被求解器反向利用。

修法两层：

1. **统一备菜判据**（`app/scheduler/prep.py::prep_keys`，三轨共用）。原来三轨各写各的：
   - `engine._schedule_once`：`(hard or soft) and 前置链完整` ← 正确
   - `model.prep_keys`：`hard or (soft and 前置链完整)` ← **hard 分支跳过链检查**
   - `cpsat` 的 `slim`：只看硬判据，连语义先验都不看

   后果：删掉「抹茶红豆白玉卷」#2（冷藏 180 min）与 #9（冷藏 120 min）却留下 #9 的前置 #8
   （当天 215 min 处）—— **300 分钟真实工作在计划里根本不存在**。

2. **`engine._restore_missing_steps`** 把缺的步骤按贪心轨口径补回 t<0
   （同菜串行、整体右对齐到 0，因此 `makespan` / 出锅差不变），
   且**只补链式闭合的菜**，否则会造出 R4 依赖违反。

**代价与结论**（A/B，50 组 seed=42）：

| 配置 | 出锅差均值 | <5min | 总时长均值 |
|---|---|---|---|
| 旧口径 | 3.24 | 82% | 71.5 |
| **统一后（当前）** | 3.24 | 82% | 82.0 |

**出锅差一分未损**；总时长的 +14.7% 全部来自 3/50 个"以前在撒谎"的组。
⇒ **这是修对了，不按分数回滚。**
