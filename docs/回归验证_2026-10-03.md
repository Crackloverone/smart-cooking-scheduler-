## 三、问题一：探针 `colTracks` 恒为 1 ⇒ 桌面分支 7 条检查**从未执行**

### 症状

`VP=1280x720` 跑出 `95 通过 / 1 失败`（`窄屏：甘特图仍有可用高度 ≥200px`，实测 104px），
而文档声称"1280×720 也跑过，108/0"——两者对不上。

### 取证

1. 探针报 `colTracks = 1`，但 CSS 里 **1280 > 1024** ⇒ `.grid3` 应为三列
   （`grid-template-columns:260px minmax(0,1.8fr) 260px`）。
   同一次测量里 `vpH=655`、`midH=579`、`colH=[579,579]` —— **全是桌面三列的特征**。
2. `fitExpr` 是一段**模板字符串**，会被送进 CDP 当 JS 源码求值。里面写的是
   `t.split(/\s+/)` —— **单反斜杠**。
3. 模板字符串把 `\s` 解析成 `s`（反斜杠被吃掉）⇒ 求值时是 `split(/s+/)`；
   而 `"260px 639px 260px"` 里**没有任何字母 s** ⇒ 永远只切出 1 段。
4. 同文件 `VP_MEASURE` 写的是 `split(/\\s+/)`（**双反斜杠，正确**）—— 只有 `fitExpr` 漏了一个。

### 后果（比表面严重）

`stacked = fit.colTracks !== 3` **恒为 true** ⇒ 永远走"窄屏"分支 ⇒ 桌面分支这 **7 条从未执行**：

```
页面无纵向滚动条（不超出浏览器界面）      计划视图内部不溢出
悬浮球不遮挡排程页任何交互元素            中列卡片无浪费空间（余量已全部分给时间轴）
任务明细已收窄（≤160px）                  时间轴高度显著大于任务明细
三列等高（模块对齐规整）
```

而窄屏分支在桌面尺寸下**也照样全绿**（`vpScrollH>=vpClientH-1`、`vpH>=innerH-2` 在桌面同样成立）
⇒ 探针一直报"通过"。这是典型的**"绿得毫无意义"**，比没有护栏更危险。

### 修复

1. `split(/\s+/)` → `split(/\\s+/)`。
   ⚠ 改的时候真踩了一次：注释里写了反引号 `` `/\s+/` ``，而**注释就在模板串内部** ⇒
   模板串被提前闭合，`node --check` 报 `SyntaxError`。**模板串内的注释不许出现反引号。**
2. **加互证断言**：新增 `colTracksByLayout`（按子元素左边界去重数**真实**列数），
   断言 `colTracks === colTracksByLayout`。**分支判据一旦选错就硬失败**，不允许静默。
3. **加静态护栏** `tests/test_probe_source.py`：扫描 `scripts/*.mjs` 的**模板字符串**，
   禁止出现"单个反斜杠 + 词类字符"（`\s \d \w \S \D \W \b \B`）的正则片段。
   第 2 项是**变异自检**（把双反斜杠改回单个，扫描器必须报出来）⇒ 证明护栏有牙齿。
   扫描器跳过**行首 `//` 注释**（注释里出现 `\s` 是合理说明）。

> **附带修掉一个"护栏报不出结论"的毛病**：`_mutate_web_guards.py` 的 `finally` 里
> `SCRATCH.unlink()` 被批量删除守卫拦下时会**中止进程**，把后面的**汇总行**一起吞掉、
> 退出码变成 1 —— 看起来像"护栏失败"，实际 **60/60 全过**（实测踩到两次）。
> 已把 `try/finally` 展开、**清理移到汇总之后**：结论先落地，清理失败只打提示。
> 改动经 `diff` 确认**只动收尾**（变异循环逐字未变），并用"只跑 2 条变异"的短程运行
> 验证汇总行与退出码（`==== 变异测试: 2/2 条被守卫捕获 ====`，exit 0）。

## 四、问题二：矮桌面视口下甘特图与「任务明细」等高

分支修正后，1280×720 的真实结果是 **98 通过 / 1 失败**：

```
[FAIL] 时间轴高度显著大于任务明细   gantt=104 tasks=104
```

`cardFill.slack = -1` ⇒ 空间**没有浪费**，是真的不够分。中列卡片只有 579px，固定占用：

```
备菜提示条(~82) + 视图切换(~35) + 标题/统计/图例/播放条(~148) + 明细表头(25) ≈ 290
```

剩下的给 `#ganttWrap`，而 `#tasks` 上限 104px 与时间轴**平分**，主次颠倒。

### 修复（`app/web/index.html`，3 行）

```css
@media (min-width:1025px) and (max-height:800px){
  #v-plan #tasks{max-height:64px}
}
```

任务明细是**次要信息**，矮屏下压到 64px 并自带滚动，把空间让给时间轴。
**1440×900 及以上不触发** ⇒ 观感与修复前逐字一致。

修后 1280×720：`gantt=144 > tasks=64` ⇒ **99 通过 / 0 失败**。

> 这条属于**已知未修**里"矮窗口甘特图被压扁"的具体化（1280×720 / 1366×768 是常见笔记本分辨率）。

## 五、订正：`ui_layout_probe` 的基线不是 108

文档里的 `108/0` 由两个错误叠加而来：

1. **Turn R 删了 2 个视图（7 → 5）**，而 §2 是**逐视图 6 项** ⇒ 少 12 项：`108 − 12 = 96`。
   Turn R 更新文档时**照抄了旧值**。
2. **探针 bug**（见第三节）⇒ 桌面分支 7 条从未执行，实际跑的是窄屏分支 5 条。
   修 bug 后：桌面 `96 + 7 − 5 = 98`，再加 1 条互证断言 = **99**；堆叠分支为 **97**。

| 指标 | 旧值 | 新值 |
|---|---|---|
| `ui_layout_probe` | 108 / 0 | **99 / 0**（桌面三列）· **97 / 0**（堆叠） |
| `pytest` | 244 | **246** |
| `_mutate_web_guards` | 59 / 59 | **60 / 60** |
| `ui_probe` | 122 / 0 | **125 / 0** |

### 一条方法论教训

文档原写"1440×900 / 390×844 / **1280×720** / 1600×1000 四档视口各跑一遍 108/0"，
但 2026-10-01 的日志里**只跑过 1440×900 与 390×844 两档**。

> **没跑过的档位不要写进"已验证"清单。**
> 否则真出问题时，报告里"一直是绿的"会让人直接忽略——和"过期的审计脚本比没有更危险"是同一类病。

## 六、遗留

- **`/parse` 不做官方菜库补全**（`/schedule` / `/reschedule` / `/notify` 都做）—— 契约差异，探针已记为 note。
- **L1 依赖漏边**：回指型指代未识别（如「三味蒸鳗鱼」#4 未连到 #3）。属**只放宽不收紧**（无依赖边 = 允许更早），不造违反。
- **多模式顶替未编码**（蒸箱 ⇄ 灶具蒸锅）：容量置 0 时精确轨判不可行、回落贪心轨（故障场景仍能出计划，只是用不上精确轨）。
- **组合下界偏松**：`lb_probe` gap 中位 26.4%、`makespan == LB` 仅 18%；根因是人工项假设单人零空闲 ⇒ 报出的是**保守上界**。最优性证据是 `OPTIMAL 60/60`，**两项都要写**。
- 界面残留：极窄甘特条刻意保持比例；甘特条拖拽不持久。
