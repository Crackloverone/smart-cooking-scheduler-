## 二、P0 —— 直接丢分，必须先补

### P0-1 · `/api/plan` 对库外菜名**静默丢菜**（违反接口规范第 8 条）

实测：请求 `[{"id":1,"name":"佛跳墙"},{"id":2,"name":"鸡翅包饭"}]`
→ **HTTP 200，`recipeCount=1`，`recipeDetail` 只有 1 条**，只在服务端日志里留了 warning。

```python
# app/api/main.py:397
miss = [r["name"] for r in req if not get_recipe(r["name"])]
if miss:
    _LOG.warning("菜名未命中官方菜库, 这些菜不会出现在排程里: %s", miss)
```

赛题《接口规范》第 8 条："`cookingTimeline` 和 `recipeDetail` 必须覆盖请求中的全部菜谱，不得遗漏或增加菜谱。"

**风险**：赛题 L1 明确要求"从自然语言烹饪步骤中自动提取"，评委会不会只用库内 100 道菜是未知数。
一旦评委用自有菜谱或改写过的菜名，当前实现会**返回一份看起来正常的残缺计划**，自动评分脚本不会报错、只会按缺失计 0。

**缺什么**：
1. `/api/plan` 的 `PlanItem` 需要**可选**接受 `ingredients` / `steps`（`RecipeIn` 已有，只是没接到 `PlanItem` 上），库外菜名走在线解析；
2. 完全无法解析时，要有显式失败语义（HTTP 422 + 明确 error，或在响应里按规范把该菜补成最小可执行步骤），**不能静默丢**；
3. 补一条护栏：任何请求菜名数与输出 `recipeCount` 不等即视为失败。

### P0-2 · L1「时间提取准确率」67% 靠兜底推断，是 20 分里的最大单点风险

`data/l1_report.json` 直读：

```
设备工作步骤 232：有时长 126（54.3%），其中显式抽取 76（32.8%）、兜底推断 50
原文显式时长命中 105 / 总步数 767 → 提取率 13.7%
```

也就是说，**设备步骤里有 40% 的时长是"猜"出来的**（50/126），而 L1 的 20 分中"时间提取准确率"是与标注答案逐条比对的。
兜底推断的默认值（如蒸箱 15 min、烤箱 25 min）在标注答案面前大概率判错。

**缺什么**：
1. **一份人工标注 gold set**（建议 20 道菜 × 全部步骤，覆盖蒸/烤/灶/冰箱四类），把"准确率"从自证变成可测；
2. 兜底时长改为**按菜品类 + 主导工序**分档（现在基本是一个设备一个常数），至少让 `香菇烤芦笋` 和 `巴斯克蛋糕` 不该同为 25 min；
3. `scripts/l1_audit.py` 目前只报"覆盖率"，应改为报**与 gold set 的逐项准确率**（设备/温度/时长/依赖/人工介入五项），直接对应赛题评分口径。

### P0-3 · 厨房设备条件无法通过 `/api/plan` 传入

```python
class PlanItem(BaseModel):
    id: object
    name: str          # 只有两个字段
```

赛题原题："根据用户选定的菜谱组合**及厨房设备条件**，自动生成最优烹饪执行计划。"
当前设备配置只能通过 `data/devices_user.json`（进程级全局状态）或 `/api/devices` 写接口改。

**风险**：
- 评委若按"标准厨房 / 单灶眼厨房 / 无蒸箱厨房"分档测评，无法在一次请求里指定；
- 并发测评时两个请求的设备配置会**互相踩**（`/api/devices` 写的是共享文件）；
- `/api/plan` 的响应不可复现，评委无法核对。

**缺什么**：
1. `/api/plan` 增加**可选**顶层包装或可选字段 `devices`（不传则用默认），保持纯 schema 的兼容性；
2. 至少补一个**请求级**设备覆盖参数（照抄已有的 `resource_override()` ContextVar 思路，不要写全局）；
3. 文档里给出"三档厨房配置"的示例请求。

## 三、P1 —— 专家评审 35% 会扣分

### P1-1 · 通知文案有语病，且离线时质量降级

实测离线模式（`FT_LLM=off`）产出的通知：

```
现在开始取出苹果芒果派、放入苹果芒果派，共8步
趁鸡翅包饭还在烘烤，先取出鸡仔饼、备菜酿苦瓜，共4步
3分钟后备菜苹果芒果派完成，趁热上桌     ← "备菜…趁热上桌"语义不通
```

三条问题：
1. **"取出X、放入X"自相矛盾**（`取出` 是出锅动作，`放入` 是入炉动作，被并进同一句）；
2. **"共N步"把具体动作吞掉了** —— 赛题要求"可操作"，"共8步"不可操作；
3. **"备菜…趁热上桌"** —— `备菜` 不该挂趁热提示。

赛题 20 分里"通知质量由专家评审（精准性、及时性、可操作性）"，且评审机大概率**离线** ⇒ 走的正是模板兜底这条路。

**缺什么**：
1. 模板层加**动作归并去重规则**（同菜不并列 取出/放入；不同菜才并列）；
2. `趁热上桌` 只挂在 `finish` 类的真实加热步骤上，备菜/装盘类不挂；
3. "共N步"降级为**最多列 3 个具体动作**，超过才用概括；
4. 把这三条写成护栏测试（模板路径必须能在 `FT_LLM=off` 下离线断言）。

### P1-2 · 7 类设备只建模了 5 类的容量

```python
# app/scheduler/engine.py:145
RESOURCE_UNITS = {灶具: 2, 蒸箱: 1, 烤箱: 1, 冰箱: 1, "人工": 1}
```

**洗碗机、净水机、烟机** 三类不在容量表里 ⇒ 不可调度。
（说明：实测 100 道菜里"洗碗机/烟机"出现 **0 次**，"净水" 7 次全是食材"纯净水" —— 数据层面确实没有需求。
但赛题白纸黑字写了"7 类可调度设备"，专家评审看设备覆盖时这是**显性缺口**。）

另外 **冰箱容量=1** 建模偏保守：冷藏/冷冻是**可共享**的存储资源（同时腌两碗肉完全合法），
串行化会抬高总时长，直接影响 L3"总烹饪时间压缩率"。

**缺什么**：
1. 把 7 类补全进 `RESOURCE_UNITS`（洗碗机/净水机/烟机给合理容量，如 1/1/1），并在 `/api/device_spec` 里可见；
2. 冰箱改为**容量 ≥2 或按温区分容量**（冷藏室/冷冻室各 1），并验证改动后总时长下降多少；
3. 在技术方案里明确写一句"100 道菜中这 3 类 0 次出现，故不影响本次评分，但能力已具备"——把缺口变成有意识的决策。

### P1-3 · 动态重排只覆盖 2 类事件

```python
class RescheduleIn(BaseModel):
    completed: list[str] = []        # 已完成步骤
    extra: RecipeIn | None = None    # 临时加菜
    failed_device: str = ""          # 设备故障
```

赛题原文只举了"临时加 1 道排骨汤"，你覆盖了加菜 + 设备故障，比要求多一项。
但**执行过程**里更常见的是：

- 某步骤实际耗时超出预估（炒菜多花了 5 分钟）→ 没有对应事件；
- 某道菜提前完成 → 没有；
- 用户临时**去掉**一道菜 → 走了 `/api/revise_plan`，但那是"重排菜单"不是"执行中重排"，语义不同。

**缺什么**：补 `delays: list[{task_id, extra_min}]` 与 `cancel_dishes: list[str]` 两个事件字段，
并在 `/api/exec/report`（已有）之上暴露一个"执行中偏差 → 重排"的单一入口，让评委一次调用就能演示 Level 4。

## P0-1 · `/api/plan` 不再静默丢菜

**改了什么**

- `PlanItem` 新增可选 `ingredients` / `steps` —— 库外菜名可以随请求带步骤在线解析；
- `adapter.resolve_items()`：菜名命中官方库用库内容，未命中且没带 `steps` 则**收集**成
  `unresolved`（不再 `continue` 静默跳过）；
- `/api/plan` 在**排程之前**检查：只要有解析不了的菜名 ⇒ **HTTP 422** +
  `detail.unresolved`（点名是哪几道）+ `detail.how_to_fix`（告诉调用方怎么补）；
- `adapter.normalize_name()`：空白 / 零宽字符 / 全角字符归一后再查库（**不做模糊匹配** ——
  「豆豉蒸腐竹」不许命中「豆豉蒸腐竹（台式）」，规范第 7 条要求输出名与请求名完全一致）；
- `build_plan()` 里两处 `get(r["name"])` 改为直接用已解析好的内容（否则库外菜名会崩）。

**实测**

| 请求 | 修复前 | 修复后 |
|---|---|---|
| `[佛跳墙, 鸡翅包饭]` | 200，`recipeCount=1` | **422**，`unresolved=["佛跳墙"]` |
| `[佛跳墙]` | 200，空计划 | **422** |
| `[我家私房菜(带steps), 鸡翅包饭]` | — | **200，`recipeCount=2`** |
| `[ 鸡翅包饭 , 酿苦瓜]` | 200，`recipeCount=1` | **200，`recipeCount=2`**（输出名仍是请求原文） |
| 全库内 5 菜 | 200 | 200，`recipeCount=5` |

**护栏**：`tests/test_plan_no_silent_drop.py`（16 项）。
判据落在**行为**上：`200 ⇒ recipeCount == 请求数`，随机 12 组（库内+库外混搭）逐组验。
另有"422 必须发生在排程之前"一项（把 `plan_recipes` 换成会爆炸的替身，仍应安静报 422）。

**变异自检**：① 去掉 422 闸门 → 5 项失败 ✓；② `resolve_items` 改回静默跳过 → 5 项失败 ✓。

## P0-3 · `/api/plan` 接受厨房设备条件

**改了什么**

- 请求体支持**两种形态**：官方裸数组（一字不改），或
  `{"recipes":[…], "devices":{"灶具":1,"蒸箱":0}}` 包装对象；
- `devices` 走**请求级 `ContextVar` 覆盖**（复用 `engine.resource_override()`），
  全局 `RESOURCE_UNITS` 永不被改写 ⇒ 并发请求互不干扰；
- 参数校验：未知设备名 / 负容量 / 非整数 / `devices` 不是对象 ⇒ **400** + 明确 error。

**顺带修掉一个真 bug**：容量覆盖生效时必须**关掉 CP-SAT 轨**（它的模型是固定编码、
不读 `resource_units()`）。实测 `devices={"蒸箱":0}` 修复前排出来的计划主设备仍是蒸箱。
修复点在 `adapter.plan_recipes()` —— 它是全项目唯一决定"怎么排"的地方，
散到各调用方就会漏（`/reschedule` 当初就漏过一次）。

**实测**：`{"蒸箱":0}` 后计划里不再出现蒸箱；同一输入两次调用**逐位一致**；
`{"灶具":1}` 的总时长 ≥ `{"灶具":2}`；排完 `RESOURCE_UNITS` 与调用前完全相同。

**护栏**：同文件 6 项（无蒸箱 / 单灶眼 / 可复现 / 不污染全局 / 非法输入 400 / 裸数组仍可用）。

## P0-2 · L1 准确率从"自证"变成"可测"

**改了什么**

1. **新增 `data/l1_gold.json`** —— 20 道菜 / 148 步人工标注，四类设备全覆盖
   （蒸箱 6 道 / 烤箱 8 道 / 灶具 8 道 / 冰箱 5 道，含交叉）。标注**只依据原文**，
   不参考解析器输出（否则是循环论证）。
2. **`scripts/l1_audit.py` 改为两块**：A 全量覆盖率（原样保留）+ B 对照标注准确率。
   准确率**只在 gold 非 null 的步上统计** —— 原文没写的值本来就无从判对错。
3. **按原文步号对齐**（`align_steps`）：解析器会插入「蒸箱预热」这类合成步、`step_id`
   整体后移，直接按 id 比对会把 gold#6 拿去和"预热步"比。相似度 <0.5 判为合成步，
   不参与比对，但在依赖判断里继承紧随其后那个真实步的原文步号。
4. **兜底时长品类分档**（`FT_DUR_TIERS`，默认 on）：原来蒸箱一律 15/18、烤箱一律 25
   —— 一个设备一个常数。现在按菜名+食材分档：
   蒸箱 蒸肉 18 / 蒸鱼虾蛋 10 / 默认 15；烤箱 烘焙 22 / 烤肉 20 / 蔬菜 10 / 默认 25。
5. **中文数字时长**：`冷藏两小时` 原来解析出 `None`（只认 `\d+`）⇒ 现在 120 分钟。
   同时守住误伤：`十分美味` / `五分熟` / `一起` / `一半` 一律不判为时长。

**实测（对照 20 道菜 / 148 步）**

| 评分项 | 修复前 | 修复后 |
|---|---|---|
| 设备识别准确率 | 无此指标 | **92.6%**（137/148） |
| 温度提取准确率 | 无此指标 | **100.0%**（8/8） |
| 时长提取准确率 | 无此指标 | **100.0%**（20/20） |
| 人工介入判断准确率 | 无此指标 | **94.6%**（140/148） |
| 依赖推理正确率 | 无此指标 | **99.3%**（141/142） |

**A/B（分档 on/off，50 组，同一 seed）**：出锅差中位 2.0 / 2.0，均值 2.9 / 3.4，
<5min 占比 82% / 82%，总时长 62.0 / 59.6。**在噪声内** —— 分档只改相对次序，
不动绝对量级（历史教训：烤箱硬编码 25 分钟会把容量 1 的烤箱变成瓶颈，优秀率 96%→84%）。

**护栏**：`tests/test_l1_gold.py`（9 项）—— 标注集完整性 + 五项准确率**下限** +
中文数字 + 分档差异化（用户点名的"香菇烤芦笋 8 vs 巴斯克蛋糕 22"）+ 一键退回旧行为。
**变异自检**：打坏中文数字 / 打坏分档 / 把"鸡精"当肉 → 三处全部触发失败 ✓。

**已知残留（由 gold set 暴露、未修）**：

- `豉汁蒸草鱼#3`、`麻辣对虾#3`、`香烤鲫鱼#4` —— 纯装载/取放句被判成设备作业（假设备）；
- `香烤排骨#4` —— 「水箱/加水」被当成蒸箱信号，而方太蒸烤一体机的烤菜也要加水 ⇒ 烤菜判成蒸箱；
- `蒜香烤茄子#5`、`香菇烤芦笋#6` —— 真设备步被"纯装载句"守卫抹掉；
- `油醋汁剁肉饼蒸和乐蟹#7` —— 合成预热步插入后，后置步漏了对它的依赖（2 道菜受影响）。

这些**全部是解析正确性问题、不是评分口径问题**，且依赖图一项按项目铁律「只放宽不收紧」
处理 —— 收紧依赖有把可行计划判成不可行的风险，故本轮不动，已在 gold 报告里可见。
