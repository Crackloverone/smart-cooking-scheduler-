# 测评接口清单（评委专用）

> 赛题 ZX-2026-030《智能烹饪调度 Agent》· 面向**自动评分**与**专家评审**
>
> 《智能烹饪调度Agent接口规范.md》只规定了官方计分端点 `POST /api/plan`（L2/L3）。
> 赛题另外三项 —— **L1 结构化解析、L4 动态重排与通知、L5 重排响应** —— 的入口在本文档。
>
> 所有端点均为 `application/json`，无鉴权，本机部署默认 `http://127.0.0.1:8137`。
> 下文 `BASE` 即该地址，实际部署时替换为你的地址即可。
>
> **离线可用性**：全部端点在 `FT_LLM=off`（默认容器档）下行为完全一致，
> 通知落模板、排程走确定性求解器，**不依赖外网**。

---

## 0. 五分钟上手（评委最短路径）

```bash
# 1) 起服务
docker build -t cooking-agent . && docker run -p 8000:8000 cooking-agent
#   或本机：python -m uvicorn app.api.main:app --host 127.0.0.1 --port 8137

# 2) 健康检查
curl --noproxy '*' $BASE/health          # -> {"status":"ok"}

# 3) 拿菜名（官方 100 道菜）
curl --noproxy '*' $BASE/api/recipe_names

# 4) L2/L3 官方计分：排 5 道菜
curl --noproxy '*' -X POST $BASE/api/plan \
  -H 'Content-Type: application/json' \
  -d '[{"id":1,"name":"清蒸鲈鱼"},{"id":2,"name":"香烤排骨"},
       {"id":3,"name":"蒜香烤茄子"},{"id":4,"name":"竹荪排骨汤"},
       {"id":5,"name":"清炒时蔬"}]'

# 5) L1 结构化解析
curl --noproxy '*' -X POST $BASE/parse \
  -H 'Content-Type: application/json' \
  -d '[{"name":"清蒸鲈鱼"}]'

# 6) L4 动态重排（临时加一道菜）
curl --noproxy '*' -X POST $BASE/reschedule \
  -H 'Content-Type: application/json' \
  -d '{"recipes":[{"name":"清蒸鲈鱼"},{"name":"香烤排骨"}],
       "completed":["清蒸鲈鱼#1","清蒸鲈鱼#2"],
       "extra":{"name":"竹荪排骨汤"}}'

# 7) L4 通知
curl --noproxy '*' -X POST $BASE/notify \
  -H 'Content-Type: application/json' \
  -d '{"recipes":[{"name":"清蒸鲈鱼"},{"name":"香烤排骨"}],"notify":true}'
```

> ⚠ 若评测机设了 `http_proxy`，curl 请带 `--noproxy '*'`，否则 `127.0.0.1` 会被代理劫持返回 502。

## 2. `POST /api/plan` —— 官方计分端点

**请求**（严格按《接口规范》，只有两个字段）

```json
[
  {"id": 1001, "name": "清蒸鲈鱼"},
  {"id": 1002, "name": "香烤排骨"}
]
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | integer/string | 是 | 同一次请求内不得重复 |
| `name` | string | 是 | 必须与菜谱库名称完全一致（`GET /api/recipe_names` 可取全部 100 个） |

**响应**：严格五个字段 `overview / cookingTimeline / ingredientsSummary / detailTimeline / recipeDetail`，
不加 `code`/`message`/`data` 包装，详见《智能烹饪调度Agent接口规范.md》。

**验收要点**（本系统已内建保证）

- 设备零冲突、依赖零违反 —— 返回前由 `scheduler.checker.check_plan` 独立复验；
- `cookingTimeline` 与 `recipeDetail` 覆盖全部请求菜谱 —— 见 §7「库外菜名」；
- `detailTimeline` 先按 `type` 升序、同 `type` 按 `timeInterval` 起点升序。

### 2.1 扩展形态：带厨房设备条件（可选，向后兼容）

赛题原文要求"根据用户选定的菜谱组合**及厨房设备条件**"生成计划。
默认（裸数组）用系统当前厨房；若要在**一次请求里**指定厨房，改用包装对象：

```json
{
  "recipes": [
    {"id": 1, "name": "清蒸鲈鱼"},
    {"id": 2, "name": "香烤排骨"}
  ],
  "devices": {"灶具": 1, "蒸箱": 0}
}
```

`devices` 的语义是**容量覆盖**（不是增量），键取 7 类设备名：

| 写法 | 含义 |
|---|---|
| `{"灶具": 2}` | 2 个灶眼（默认） |
| `{"灶具": 1}` | 单灶眼厨房 |
| `{"蒸箱": 0}` | 无蒸箱 / 蒸箱故障 —— 相关任务按顶替关系改走灶具 |
| `{"烤箱": 0, "蒸箱": 0}` | 无蒸烤设备 |
| `{"冰箱": 0}` | 无冰箱（冷藏/解冻类步骤降级为人工等待） |
| `{"洗碗机": 0}` / `{"烟机": 0}` / `{"净咖一体机": 0}` | 该设备不可用 |

> **`冰箱` 记的是「温区数」而不是「几台冰箱」**：冷藏室与冷冻室可同时使用，
> 默认 **2**（冷藏 + 冷冻）。记 1 会把长时腌制/冷藏串行化，白白抬高总时长。
>
> **七类设备全部在册**（灶具 / 蒸箱 / 烤箱 / 冰箱 / 洗碗机 / 烟机 / 净咖一体机）。
> 说明：官方 100 道菜里「洗碗机 / 烟机」出现 **0 次**，「净咖一体机」只作为食材
> 来源（"加纯净水"）被提到 —— 所以这三台的容量当前是**空置**的。
> 在册的意义是：设备能力覆盖在 `/api/device_spec` 上可见，且 `devices` 覆盖参数
> 认得这些设备名（否则传 `{"洗碗机":0}` 会拿到 400，看起来像只支持 5 类设备）。

**三档厨房配置示例请求**

```bash
# ① 标准厨房（等价于不传 devices）
curl --noproxy '*' -X POST $BASE/api/plan -H 'Content-Type: application/json' \
  -d '{"recipes":[{"id":1,"name":"清蒸鲈鱼"},{"id":2,"name":"香烤排骨"},
                  {"id":3,"name":"蒜香烤茄子"}],
       "devices":{"灶具":2,"蒸箱":1,"烤箱":1,"冰箱":1}}'

# ② 小户型：单灶眼、无烤箱
curl --noproxy '*' -X POST $BASE/api/plan -H 'Content-Type: application/json' \
  -d '{"recipes":[{"id":1,"name":"清蒸鲈鱼"},{"id":2,"name":"香烤排骨"},
                  {"id":3,"name":"蒜香烤茄子"}],
       "devices":{"灶具":1,"烤箱":0}}'

# ③ 蒸箱故障（动态事件）：蒸菜顶替到灶具
curl --noproxy '*' -X POST $BASE/api/plan -H 'Content-Type: application/json' \
  -d '{"recipes":[{"id":1,"name":"清蒸鲈鱼"},{"id":2,"name":"香烤排骨"}],
       "devices":{"蒸箱":0}}'
```

**三条保证**

1. **请求级隔离** —— `devices` 走 `ContextVar` 覆盖，**全局 `RESOURCE_UNITS` 永不被改写**；
   并发请求互不干扰（不会出现"请求 A 把蒸箱置 0，请求 B 的蒸箱凭空消失"）。
2. **可复现** —— 同一份 `{菜名列表, devices}` 给出**逐位一致**的计划。
3. **参数校验** —— 未知设备名 / 负容量 / 非整数容量 / `devices` 不是对象，
   一律 HTTP `400` + 明确 error（`unknown_device` / `bad_capacity` / `bad_devices`）。

> 覆盖生效时会自动**关闭 CP-SAT 轨**（其模型是固定编码、不读容量覆盖），
> 精确模型轨不受影响（它读 `resource_units()`）。这条在 `adapter.plan_recipes()`
> 里统一处理 —— 它是全项目唯一决定"怎么排"的地方。

### 2.2 错误码

| 状态码 | `detail.error` | 触发条件 |
|---|---|---|
| `200` | — | 正常（`recipeCount` 恒等于请求菜谱数） |
| `400` | `bad_payload` / `bad_recipes` / `bad_recipe_item` | 请求体结构不对 |
| `400` | `unknown_device` / `bad_capacity` / `bad_devices` | `devices` 非法 |
| `422` | `unresolved_recipes` | 菜名不在官方库且未提供 `steps` —— **绝不返回缺菜的计划** |

## 3. `POST /parse` —— L1 结构化解析

**请求**

```json
[
  {
    "name": "清蒸鲈鱼",
    "ingredients": "主料：新鲜鲈鱼500克；辅料：生姜3片、小葱2段、盐2克、料酒15克",
    "steps": "第1步：……；第2步：……",
    "label": ""
  }
]
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | string | 是 | 菜名 |
| `ingredients` | string | 否 | 食材清单。**留空则自动从官方菜库取** |
| `steps` | string | 否 | 自然语言步骤。**留空则自动从官方菜库取** |
| `label` | string | 否 | 分类标签 |

**响应**

```json
{"parsed": [ { "name": "清蒸鲈鱼", "ingredients": [...], "steps": [ ... ] } ]}
```

`steps[]` 每项即赛题 L1 要求的五要素：

| 字段 | 类型 | 对应赛题评分项 |
|---|---|---|
| `step_id` | int | — |
| `raw_text` | string | 原文（可溯源） |
| `device` | string | **设备识别准确率**（七类设备 / `人工`） |
| `device_source` | string | 命中的原文词；`(推断)` 表示兜底推断 |
| `mode` | string | 工作模式（普通蒸 / 烘烤 / 翻炒 / 熬煮 …） |
| `temperature_c` | float\|null | **温度参数** |
| `duration_min` | float\|null | **持续时间**（分钟） |
| `needs_human` | bool | **是否需人工介入** |
| `unattended` | bool | 是否无人值守（炖/焖/蒸/烤/冷藏等待） |
| `depends_on` | int[] | **步骤依赖**（同菜内前置 step_id） |
| `prep_type` | string | 切配 / 腌制 / 等待 / 烹饪 … |

**样例（真实输出节选）**

```json
{
  "step_id": 3,
  "raw_text": "腌制结束后，将鱼盘放在附送的有孔蒸盘或架子上，放入设备第2层…",
  "device": "蒸箱",
  "device_source": "(推断)",
  "mode": "普通蒸",
  "temperature_c": 100.0,
  "duration_min": 15.0,
  "needs_human": false,
  "unattended": true,
  "prep_type": "等待",
  "depends_on": [2]
}
```

> `device_source == "(推断)"` 表示该步设备由兜底规则得出、原文未明写 ——
> 这一比例是 L1「设备识别准确率」的公开自查口径，详见 `data/l1_report.json`。

## 4. `POST /schedule` —— 排程 + 可验证指标（内部扩展）

与 `/api/plan` 走**同一条求解闭环**，但额外返回 KPI、理论下界与诊断，供评审核对。

**请求**

```json
{
  "recipes": [{"name": "清蒸鲈鱼"}, {"name": "香烤排骨"}],
  "text": "家里来客人，希望所有菜一起上桌",
  "notify": false
}
```

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `recipes` | RecipeIn[] | — | 菜名（食材/步骤留空则从官方库取） |
| `text` | string | `""` | 用户自然语言偏好 → 多目标权重 |
| `notify` | bool | `true` | 是否生成通知 |

**响应**

| 字段 | 说明 |
|---|---|
| `plan` | 任务级排程（`tasks[]` 含 `device/unit_id/start_min/end_min/temp_c/needs_human`） |
| `kpi` | **可直接计分的硬指标**，见下 |
| `check` | `checker.check_plan` 的冲突/依赖复验结果 |
| `insight` | 关键路径与风险提示（只读，不参与决策） |
| `lb` / `gap_pct` | **理论下界与最优性间隙**（赛题「总耗时与理论最优解对比」） |
| `elapsed_ms` | 服务端耗时 |

**`kpi` 字段对照赛题评分项**

| 字段 | 对应赛题 |
|---|---|
| `conflict_count` | L2 设备冲突检测（本系统恒为 0） |
| `depend_violation` | L2 依赖校验（本系统恒为 0） |
| `makespan_min` | L2/L3 总烹饪时间 |
| `finish_gap_min` | L3 同出锅时间差（**优秀 <5 min**） |
| `hand_streak_min` | L3 用户连续手动操作时长 |
| `device_utilization` | L2 设备利用率（仪表盘，不进目标函数） |

## 5. `POST /reschedule` —— L4 动态重排

**请求**

```json
{
  "recipes": [{"name": "清蒸鲈鱼"}, {"name": "香烤排骨"}],
  "completed": ["清蒸鲈鱼#1", "清蒸鲈鱼#2"],
  "extra": {"name": "竹荪排骨汤"},
  "failed_device": "",
  "text": ""
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `recipes` | RecipeIn[] | 当前菜单 |
| `completed` | string[] | **已完成步骤的 `task_id`**（取自 `/schedule` 的 `plan.tasks[].task_id`）。列入者**硬冻结，绝不推翻** |
| `extra` | RecipeIn\|null | 临时新增的菜（赛题示例：临时加 1 道排骨汤） |
| `failed_device` | string | 设备故障，如 `"蒸箱"`。相关任务按 `DEVICE_FALLBACK` 顶替到灶具 |
| `text` | string | 本次重排的用户偏好 |

**响应**

| 字段 | 说明 |
|---|---|
| `plan` / `kpi` | 新计划与指标 |
| `locked` | 冻结的已完成步骤数 |
| `perturbed` | **最小扰动**：被挪动的步骤数 |
| `event` | 事件类型（`插单` / 设备名） |
| `stance` | 重排姿态仲裁结果（`{name, desc, reason, by_llm}`） |
| **`pareto`** | **可验证的不劣化保证**，见下 |
| `notice` | 人可读的变更明细（已完成步骤保留 N / 调整步骤数 M / 新总时长） |
| `elapsed_ms` | **L5 重排响应时间** |

**`pareto` —— 两条当场可判真伪的断言**

```json
{
  "保证": {
    "已完成步骤零变动": true,
    "不劣于串行基线": true
  },
  "串行基线": {"总时长": 95.0, "出锅差": 64.0},
  "重排前": {"出锅差": 10.0, "总时长": 95.0, "连续手动": 27.0},
  "重排后": {"出锅差": 10.0, "总时长": 95.0, "连续手动": 27.0},
  "改善": [], "劣化": []
}
```

> **为什么不是"总时长不增加"**：新增一道菜必然增加总工作量，该断言不可能成立。
> 本系统保证的是 ① 已完成步骤零变动（硬保证，逐任务比对开始时刻）
> ② 不劣于"原计划不动 + 新菜整体串行接在末尾"这个**必然可行**的朴素基线。
> 三项指标的涨跌在 `改善`/`劣化` 里如实列出，不粉饰。

## 6. `POST /notify` —— L4 通知生成

**请求**：同 `/schedule`（`notify: true`）。

**响应**

```json
{"notifications": [
  {"at_min": 0.0,  "level": "info",  "kind": "manual", "text": "现在开始…"},
  {"at_min": 6.0,  "level": "warn",  "kind": "finish", "text": "2分钟后烘烤…完成，趁热上桌"},
  {"at_min": 8.0,  "level": "info",  "kind": "device", "text": "烤箱空了，可以放入…"}
]}
```

| 字段 | 说明 |
|---|---|
| `at_min` | 相对计划起点的触发时刻（分钟） |
| `level` | `info` / `warn` |
| `kind` | `manual`（人工操作前）/ `finish`（出锅）/ `device`（设备空闲，可插活） |
| `text` | 通知正文 |

**四类通知对应赛题要求**

| kind | 赛题原文示例 | 本系统 |
|---|---|---|
| `manual` | "现在可以开始切西兰花" | 人工操作前提醒，并利用"某菜正在蒸/烤/炖"的等待窗口插活 |
| `finish` | — | 出锅前 2–3 分钟预警，需趁热的菜附"趁热上桌" |
| `device` | — | 设备腾空提示，便于立即接续下一道 |

> `FT_LLM=off` 时走**确定性模板**（零延迟、可离线断言）；
> `FT_NOTIFY_LLM=on` 且模型可用时走 LLM 语境化，失败自动回落模板。

## 7. 菜谱库与库外菜名

- 官方 100 道菜为**只读基线**（`data/recipes_official_100.csv`，SHA-256 校验，永不被改写）。
- `GET /api/recipe_names` 返回全部菜名；`GET /api/recipes` 返回完整元数据。
- `/parse`、`/schedule`、`/reschedule`、`/notify` 的 `RecipeIn` **接受自由文本**：
  传 `ingredients` / `steps` 即按传入内容解析，**支持库外菜谱**。
- `/api/plan` 受官方 schema 限制、只接收 `{id, name}`：
  **菜名不在官方库时不会静默丢弃**，行为见 §8。

## 8. 错误处理与可复现性

| 情形 | 行为 |
|---|---|
| `/api/plan` 菜名命中官方库 | 正常排程，`recipeCount == 请求数` |
| 菜名带空白 / 零宽字符 / 全角字符 | 归一后命中（输出名仍是**请求原文**，符合规范第 7 条） |
| `/api/plan` 任一菜名不在库、且未提供 `steps` | **HTTP 422** + `detail.unresolved` 列出具体菜名 + `how_to_fix`，**不返回残缺计划** |
| `/api/plan` 库外菜名**自带 `steps`** | 正常排程，支持任意自有菜谱 |
| 请求含重名菜 | 服务端告警；重名会合并为同一道菜（官方 schema 无"份数"字段），`recipeCount` 仍等于请求数 |
| 设备配置 | 默认取 `data/devices_user.json`；`/api/plan` 支持可选 `devices` 做**请求级覆盖**，并发互不干扰（见 §2.1） |

> **为什么不是"把无法解析的菜补成最小可执行步骤"**：那样会返回一份"名字对、
> 内容却是编的"计划，比直接报错更难排查。规范第 8 条要的是"覆盖全部菜谱"，
> 而"覆盖"的前提是**确实能排**——排不了就如实说，并给出可照做的修法。

**可复现性**：同一份 `{菜名列表, 设备配置}` 在离线档下**逐位一致**（确定性求解器，无随机性）；
在线档下 LLM 只影响权重/策略提议，且受 `FT_AGENT_BUDGET` 硬预算约束，超时即收敛。

## 9. 环境变量（评审相关）

| 变量 | 默认 | 说明 |
|---|---|---|
| `FT_LLM` | `on` | 全局模型总闸。**`off` = 完全离线**，评审机推荐 |
| `FT_WARM_LLM` | `on` | 启动时探测模型可用性（让熔断状态在接客前落定，避免首个请求超时） |
| `FT_AGENT_BUDGET` | `3.6` | 排程闭环总预算（秒），保证不破 5 s |
| `FT_REPLAN_BUDGET` | `2.5` | 重排闭环预算（秒），保证不破 3 s |
| `FT_EXACT` | `on` | 精确模型轨（关掉退回贪心+CP-SAT，质量下降约 26%） |
| `FT_HOOD` | `off` | 烟机联动行（官方规范与 100 道菜均 0 次提到烟机，默认不生成） |
