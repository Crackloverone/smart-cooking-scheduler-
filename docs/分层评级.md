## 1. Level 1 菜谱结构化解析 —— **S**

### 官方要求
> 从自然语言烹饪步骤中自动提取**设备名称**（烟机/灶具/蒸箱/烤箱/冰箱/洗碗机/净水机）、
> **温度参数**、**持续时间**、**步骤依赖关系**、**是否需人工介入**等结构化信息，输出标准化 JSON。

### 实测（`data/l1_report.json`，官方 100 道菜 / 762 步）

| 抽取项 | 达成 | 判据 |
|---|---|---|
| 设备识别 | **99/100 道菜有加热设备** | 8 类设备全支持（`DEVICE_RULES` 长词优先，含"蒸烤一体机→蒸箱"这类归并）。唯一例外是 `披萨面团`（只做面团，本身不含烹饪） |
| 温度参数 | 良好 | `parse_temperature` 支持 `180℃` 与 `180度`；且按设备把烹饪手法**归一成官方模式名**（`_MODE_BY_DEVICE`），不会出现"蒸箱·腌制"这种设备与模式对不上的组合 |
| 持续时间 | **显式抽取 77 步 + 兜底推断 85 步** | 设备工作步骤 **293 步**，其中 162 步有时长（55.3%）。**原文里写了时长的只有 105 步（13.8%）—— 这是解析能力的理论上限** |
| 依赖关系 | **86.9% 标注 + 66 条并行分支** | 线性依赖 `depends_on=[i-1]`；无人值守步骤后的切配改为指向更早的前序步，形成真实并行分支 |
| 需人工介入 | **100% 执行主体识别率** | 已修掉"装载/启动型"误判（官方 57 步 × 618 分钟曾被错记成人工占用） |
| 标准化 JSON | ✅ | `POST /parse` → `{parsed:[{step_id, device, mode, temperature_c, duration_min, needs_human, unattended, prep_type, depends_on}]}` |

设备分布（762 步）：灶具 87 · 烤箱 63 · 冰箱 25 · 蒸箱 98 · 净水机 4，其余为人工（72.3%）。

### 为什么给 S

**① "时长提取率 29%"曾是一个口径错误。** 762 步里有 481 步是**人工准备**（切配/装盘），
原文里本就不写时长、排程时按 `estimate_duration` 估 1–3 分钟 ——
把它们算进分母，得出的"29%"没有任何意义。
按正确口径（**设备工作步骤**）重算：293 步里 162 步有时长 = **55.3%**。
而**原文显式写了时长的只有 105 步（13.8%）** —— 也就是说，"缺时长"绝大部分**在上游就不存在**。

**② 修掉了一处会直接毁掉整条排程的解析缺陷（本轮新增）。**
复合句 `"…放入烤箱第3层，选择'开始烹饪'按键…烘烤结束，取出晾凉"` 里的"晾凉"
被 `SOAK` 词表命中，导致**整句降级为等待，真实的烤箱作业被一起抹掉**。
官方 100 道菜里有 **12 句**中招，其中 6 句是"开始烹饪 + 烘烤结束 + 取出晾凉"这种标准写法。
极端例子：`法式羊排` 全菜只有 1 步，被抹掉后**整道菜没有任何设备任务**。
修复方式：`SOAK` 命中后加三条**保守**放行判据（设备程序启动信号 / 点名设备 + 显式时长 /
灶具 + 主动烹饪动作），并在 `tests/test_core.py` 加了正反例各 3 条的回归用例。
效果：**有加热设备的菜 95/100 → 99/100**。

**③ 依赖图从纯线性链放开到真实并行分支**（66 条）。赛题 L2 的"识别可并行步骤"
现在由依赖图本身表达，而不只是靠 `unattended` 标记 + 设备不冲突来间接实现。

**④ 幽灵设备占用清零。** `"打开烤箱门，将烤好的鸡翅包饭取出即可"` 曾被当成烤箱任务，
`estimate_duration` 给它编了 8 分钟 —— 实测 **17 句 / 136 分钟虚假设备占用**，现在 **0**。

### 残留缺口
1. **显式时长只有 13.8%** —— 但这是**上游数据的属性**，不是解析器的问题：
   官方菜谱里 87% 的设备步骤原文就没写时长。当前用「兜底推断 + 按设备/工序估时」覆盖，
   敏感性实测：只扰动缺失时长的步骤 ±30% ⇒ 总时长 −7.4% / +16.0%。
2. **多模式顶替未编码**（蒸箱 | 灶具蒸锅）：容量为 0 时精确轨直接判不可行并回落贪心轨。
   故障场景仍能出计划（贪心兜底 + 设备顶替链），但用不上精确轨。见 §2 缺口。

## 2. Level 2 多菜并行调度 —— **S**

### 官方要求
> 给定 3–5 道菜及厨房设备配置，生成最优执行排程，输出结构化排程 JSON。
> 要求**设备零冲突**（同一灶眼不能同时炒两道菜、蒸箱不能同时进行不同温度的蒸制）、
> **识别可并行步骤**（如炖煮无人值守时可切另一道菜的食材）。

### 实测

| 要求 | 实测 | 证据 |
|---|---|---|
| 设备零冲突 | **0 冲突 / 50 组** | `checker.check_plan()` 在返回前**再独立验一遍**，异常直接暴露 |
| 蒸箱异温串行 | ✅ | 同温（±15℃）共享腔体用 `AddCumulative`；异温用两两 `AddNoOverlap` 强制串行 |
| 同一灶眼不并发 | ✅ | `灶具` 容量 = 灶眼数，`AddCumulative` 限流 |
| 可并行步骤识别 | ✅ | `unattended` 步骤不占双手 → 炖煮期间可切另一道菜；依赖图另有 **66 条并行分支** |
| 结构化排程 JSON | ✅ | 官方 schema `overview / cookingTimeline / ingredientsSummary / detailTimeline / recipeDetail` |

**这是"超出要求"的一层**：赛题只要求"零冲突"，我们额外做到了
**批次机同温合炉**（两道菜同为 100℃ 蒸制时共用一炉，而不是串行两轮）——
实测这一项单独贡献 **总时长 −8.1%**。

### 缺口
- 多模式顶替（蒸箱坏了改走灶具蒸锅）未编码进数学规划：容量置 0 时精确轨判不可行，回落贪心轨。
  当前故障场景仍能出计划（贪心兜底 + `DEVICE_FALLBACK` 顶替链），但用不上精确轨。

## 3. Level 3 多目标优化 —— **S**

### 官方要求
> 所有菜品尽量同时完成（**时间差小于 5 分钟为优秀**）；**总烹饪时间最短**。

### 实测（50 组随机 3–5 菜，seed=42，离线）

| 指标 | 实测 | 优秀线 | 判定 |
|---|---|---|---|
| 出锅差 中位数 | **2.0 min** | <5 min | ✅ 优秀 |
| 出锅差 <5min 占比 | **90%** | 越高越好 | ✅ |
| 出锅差 均值 | **2.9 min** | <5 min | ✅ 优秀 |
| 总时长 均值 | **74.8 min** | 越短越好 | — |
| 求解状态 | **OPTIMAL 60/60**（60 组独立复测） | — | ✅ 已证最优 |
| 交付计划 vs 模型上限参考 | **逐项一致**（74.1 / 2.03 / 28.7） | — | ✅ |
| `总时长 < 下界` | **0 / 60** | 0 | ✅ |

> 说明：更早的快照是 92% / 73.5 min。差异来自 §1 的**等待词误杀修复** ——
> 恢复了 12 个真实设备任务，问题变难也更真实。**宁可指标低一点，不要靠丢任务刷分。**

### 关键设计（这层是真功夫）
1. **目标口径严格抄评分表原文**：「最后一道菜与第一道菜完成的时间差」= `max F − min F`，
   而不是语义冷等待 `Σσ_d(T−F_d)`。两者在"冷菜可以早出锅"时**方向相反**。
2. **三层字典序 + 动态位权**：原始跨度 Γ ≫ 总时长 T ≫ 语义冷等待，
   权重按实例规模算（`A_cold = 60000·H·|D|`），大实例不会被冷等待项反超。
3. **两阶段 ε-约束**：阶段 1 先 `min T` 得 T\*，阶段 2 在 `T ≤ T*+ε` 下优化 Γ ——
   把"可被求解器反向利用的代理量"这个口子堵死。
4. **硬约束不进目标函数**：设备冲突、依赖关系只做可行性约束，不做罚项。
5. **设备利用率只做仪表盘，不做方向盘**：它不进目标函数（进了会激励"少用设备"）。

### 可解释性（本轮补齐）
- `/schedule` 响应新增 `bound`：`lb_cp` / `lb_energy` / `lb_hand` / `lb` / `makespan` /
  `optimality_gap_pct`，并附口径说明。`/api/plan` 保持**纯官方 schema 不变**。
- 新增 `model` 字段：暴露求解状态、horizon、耗时、`hand_cap_enforced`。
- 新增 `scripts/lb_probe.py` 量下界紧致度：`总时长 < 下界` **0/60**；gap 中位 26.4% / 均值 42.4%；
  起约束作用的下界项 = 人工总工时 27 / 批次机产能 22 / 关键路径 7。

> **诚实说明**：26%–42% 的 gap **不代表解差 26%–42%**。
> `lower_bound_from_plan` 的「人工总工时」项假设**单人零空闲连续作业**，
> 而真实排程里人必须等无人值守步骤结束，这类等待物理上不可消除 —— 所以这是个**偏松**的下界，
> 报出来的 gap 是**真实最优间隙的保守上界**。
> 真正的最优性证据是：**精确模型 `OPTIMAL` 60/60，且交付计划与模型上限参考逐项一致**。

## 4. Level 4 动态重排与通知生成 —— **S**

### 官方要求
> 执行过程中注入突发事件（如：临时加 1 道排骨汤），要求**实时调整排程且不推翻已完成步骤**；
> 在关键节点生成**精准、简洁、可操作**的用户通知
> （如"3分钟后需要翻炒红烧排骨""现在可以开始切西兰花"）。

### 实测

| 要求 | 实测 | 证据 |
|---|---|---|
| 实时调整 | 重排 **45 ms**（优秀线 3000 ms） | `POST /reschedule` |
| 不推翻已完成 | ✅ **形式化可检验** | 两级冻结：`completed` 步骤 `hard_frozen` → 精确模型 `fixed` 约束；响应返回 `locked: N` |
| 插单 | ✅ | `extra` 字段注入新菜，与既有菜一起重排 |
| 设备故障 | ✅ | `failed_device` → 请求级 `ContextVar` 把容量置 0，**不改全局**（消除并发竞态） |
| 通知：精准 | ✅ | 动作词表 55 个，兜底词从"处理"改"备菜"；每条必带**菜名 + 动作** |
| 通知：简洁 | ✅ | 连续手动操作合并成一条，超 2 步用"，共N步"概括 |
| 通知：可操作 | ✅ | 四类节点，**含赛题原句举例的"趁X在蒸，先切Y"** |

四类通知节点：

| 节点 | 示例 |
|---|---|
| 人工操作前 | "现在开始切配蒜蓉西兰花、清洗鸡翅包饭，共17步" |
| **趁等待间隙插活** | "趁家常鲈鱼还在蒸制，先切配西兰花" |
| 出锅前 1–3 分钟 | "2分钟后蒸制家常鲈鱼完成，趁热上桌" |
| 设备释放 | "烤箱空了，可以放入黄油小饼干" |

**额外加分项**：重排姿态由**模型仲裁**（`minimal` 最小扰动 / `rebalance` 重新对齐 /
`freeze_hot` 保热优先）。纯代码只能三选一写死，而选哪个取决于语义 ——
新插入的是"10 分钟快手菜"还是"要炖 1 小时的汤"，被影响的菜里有没有必须趁热的清蒸鱼。

### 本轮补齐的三项（把 A 抬到 S）

**① `hand_cap`（连续手动上限）从"静默失效"到"真的被约束"。**
旧实现用时间索引 `ω_t` 编码，规模 `O(n·H)`：5 菜实例 4725 布尔变量 / 13959 项约束，
3 s 预算下 **7/8 组解不出来**，而 `_give_up()` 会**静默丢弃**该约束 ——
报出来的 54 min 其实没受任何约束。
现在：`skip_stage1`（带约束时跳过 `min T` 阶段，省 9–17 s）+ EST/LFT 时间窗裁剪 +
**降级阶梯**（钉住非人工任务重试 → 仍失败则显式标注 `hand_cap_enforced=false` 与原因，
绝不静默）。实测 **3 s 预算 → 8/10 组被约束住；10 s → 10/10**。

**② `B`（连续手动时长）的定义统一。**
精确模型按"严格无空闲"算连续，而 `metrics.hand_streak` 允许 **1 min 空隙** ——
同一份计划模型说 20 min、评分表可能报 38 min。
现在 `metrics.HAND_GAP_TOL = 1.0` 是**唯一来源**，模型约束与评分函数读同一个常量，
并由 `test_hand_gap_tol_is_single_source_of_truth` 守住。

**③ 重排的"不劣化"从口头承诺变成可检验的结构。**
`/reschedule` 响应新增 `pareto` 字段，给出两条**可被第三方验证**的保证：

| 保证 | 含义 |
|---|---|
| 已完成步骤零变动 | 冻结集的每个 (菜名, 步骤号) 在重排后位置不变 |
| 不劣于串行基线 | 串行基线 = 原计划原样保留 + 新菜**严格串行追加**（构造上必然可行的朴素解） |

并附 `违反明细`、`串行基线 / 重排前 / 重排后` 三项指标对照、以及 `改善` / `劣化` 明细。
实测一例：重排 98 min / gap 2，串行基线 154 min / gap 72 —— 改善项与劣化项**都列出来**，
不做单向美化。

### 残留缺口
- 重排后"不劣于重排前"仍**不是硬约束**（无法在不牺牲插单收益的前提下保证）——
  现在改成"**可检验的诚实汇报**"：给出两条必然成立的保证 + 完整的劣化明细。
  这是我认为正确的工程取舍：把不可能保证的东西显性化，而不是假装它成立。

## 5. Level 5 性能效率 —— **S**

### 官方要求
> 初始排程生成合格 <10s、优秀 <5s；动态重排响应合格 <8s、优秀 <3s。

### 实测

| 场景 | 实测 | 优秀线 | 余量 |
|---|---|---|---|
| 初始排程 均值 | **130.7 ms** | <5000 ms | **38×** |
| 初始排程 p95 | **274.2 ms** | <5000 ms | **18×** |
| 初始排程 max | **320.5 ms** | <5000 ms | **16×** |
| 动态重排 | **45 ms** | <3000 ms | **67×** |
| **首个请求**（默认档、模型端"通但慢"） | **154 ms**（修复前 **6735~7813 ms**） | <5000 ms | — |

（前四行：50 组随机 3–5 菜，seed=42，离线模式，`python -m scripts.bench 50`）

**这一层毫无悬念**。三轨取优（贪心 → CP-SAT → 精确模型）看似更贵，但因为：
- 贪心毫秒级兜底，任何时候都有合法解；
- 精确轨预算 `min(1.5s, 剩余预算)` 二次收紧；
- 语义先验/参数补全/策略结论**离线算好落盘**，在线只读缓存，模型决策 **0 延迟、0 网络依赖**。

所以"模型在环"没有换来任何在线延迟。**且模型不可用时（实测 429 额度耗尽）全部指标不变**。

### 缺口

唯一风险是**首个请求**，而且它比看上去更微妙 —— 稳态 131 ms 是**熔断器打开之后**的数字。
熔断没在启动阶段落定的话，第一个真实请求要自己攒够失败次数，每次调用各等一次超时：

| 模型端状态 | 旧版探测判定 | 首个请求 | 修复后 |
|---|---|---|---|
| 连不上（DNS/连接被拒） | 不可用 → 熔断 ✅ | ~111 ms | 不变 |
| **能连通但单次 > 超时**（实测 2.3~4.0 s vs 默认 3.0 s） | **误判"可用"** ❌ | **6735~7813 ms** | **154 ms** |
| 能连通且 < 1.5 s | 可用 | 正常 | 不变 |

旧版探测有两个错：① 走纯文本 `llm.chat`，而 Agent 实际用 `chat_json`（请求体不同）；
② 判据是"连不连得上"而不是"能否在预算内返回"。已改为 **`chat_json` + 1.5 s 紧预算**
（一次排程发 1~2 次调用，单次 >1.5 s 本来也落不进 <5 s），探不通即在启动阶段
`force_open`。回归用例 `tests/test_warmup_probe.py` 6 项（含变异测试）。

### 后续追加：逐控件可用性审计（"点下去有没有反应"）

排程页布局修完之后，又按"**遍历每个按钮、每个模块**"做了一轮可用性专项。做法是写一个
**穷举式**探针 `scripts/ui_click_audit.mjs`（与场景化的 `ui_probe.mjs` 互补）：

* 遍历**全部 252 个可交互控件**，逐个派发它绑定的那个事件，判定
  "DOM / 网络 / alert / 焦点"四者有没有任何一处发生变化；
* 再遍历**全部单行输入框**派发一次回车，看有没有绑 keydown；
* 跳过 6 个破坏性控件（删菜谱 / 保存配置 / 清令牌…），它们由 `ui_probe.mjs` 覆盖。

静态接线其实是**完整**的：0 个未定义处理器、0 个重复函数、0 个"定义了从不被调用"的
死函数、0 个无副作用的死按钮、0 个 JS 异常。但**动态**层面查出两类"用户以为界面坏了"
的静默缺口：

| # | 问题 | 证据 | 严重度 |
|---|---|---|---|
| C1 | **13 个单行输入框敲回车毫无反应** —— 全站原来只有悬浮对话框的 `#chatInput2` 绑了 keydown | 回车遍历：`#agentText` / `#search` / `#libSearch` / `#setRemoteUrl` / `#setRemoteKey` / `#setModelInput` / `#setToken` / `#dev-*`(4) 全部 `onkeydown=(无)` | 🟠 中 |
| C2 | **「开饭时间」是纯摆设** —— HTML 有、样式有、用户能改，但全文件没有一行 JS 读它，后端也不接受 `dinner` 字段 | 全文件仅 3 处引用（标签、文案、一条注释）；`grep -rn dinner app/api/main.py app/scheduler/*.py` 无命中 | 🟠 中 |

修法与结果：

* **C1** —— 给 9 个输入框补 `onkeydown`，且**接到它旁边那个按钮的同一个动作**上
  （AI排→`agentPlan()`、令牌→`saveToken()`、设备数量→`saveDevices()`、模型三项→`saveModel()`、

  ⚠ 判据必须是"**有没有绑 keydown**"，不是"这次有没有反应"：保存类操作在**空输入**时
  早退是**正确**行为（否则"空着敲一下回车"会把已有配置清掉）。
* **C2** —— 把它做成**墙上时钟锚点**：排程结果是相对分钟（`t=0` = 第一个占用资源的任务），
  单看"t=17 分"用户没法对上自己的时间表。现在按 `开始下厨 = 开饭时间 − 总时长` 换算，
  并在三处消费：提示条、通知区（`⏱ t=17分（18:30）`）、步骤详情的时间行。
  ⚠ 它**不是约束** —— 不会反过来逼求解器压缩总时长（那会动摇 Γ 口径）；真来不及就
  如实提示"来不及"。

**这一轮顺手补掉的两个"探针自己不可靠"的问题**（都属于本项目铁律的范畴）：

### 一、A1 排程历史落盘（本轮唯一有后端语义的改动）

改造前 `_SCHEDULE_HISTORY` 是 `deque(maxlen=20)` 纯内存，且每条只存
`time/dishes/makespan/gap` 四个字段 —— 重启即失；即使不重启，点开历史也看不到当时的
完整计划（甘特图 / 任务明细 / 诊断全回不来）。

- 落盘到 `data/schedules_user.json`（与 `devices_user.json` / `llm_settings.json` /
  `recipes_user.json` 同一套两层纪律）⇒ `sync_publish.SKIP_NAMES` 从**三份变四份**。
- 新增 `FT_SCHEDULES_FILE` 隔离开关（与 `FT_DEVICES_FILE` 同一套纪律）。
  ⚠ 与另外两个**不同**：设备/模型配置只在"用户主动保存"时写，而**排程历史每跑一次
  `/schedule` 就写一次** ⇒ `conftest` 必须指到 `tempfile.mkdtemp()` 而不是
  `tests/_no_such_*.json`，否则 tests/ 下会积累几十条测试计划。
- 三个端点：`GET /api/schedules`（**只回摘要**，绝不带 `plan`）、
  `GET /api/schedules/{sid}`（完整记录，找不到 ⇒ **404**）、`DELETE /api/schedules`。
- 落库放在 `/schedule` 的**最后**：`insight` / `bound` / `model` / `agent` 都是后续
  追加进 `res` 的，提前落库会把它们漏掉。
- 记录页行**整行可点还原**，走 `/api/schedules/{sid}`，**不重新调 `/schedule`**
  （否则用户点几次"看看以前的计划"，历史就被自己刷满了）。

⚠ **一处探针口径缺陷（本轮修）**：行内复选框原本挂
`onclick="event.stopPropagation()"`。语义没错，但「全控件反应遍历」是**按 `onclick`
属性枚举控件**的 ⇒ 复选框被当成"点下去什么都没发生"归入待判断，于是**每多一条历史
就多一个待判断**，退出码跟着变 1，基线数字不再稳定（实测 7 条历史 ⇒ 待判断 7）。
改成由**行自己**判事件源（`restoreSchedule(sid,ev)` + `ev.target.closest('input')`
让路），复选框不再带 `onclick`。同时探针在记录页段前先 `DELETE` 再**固定造一条**，
让控件集合恒定。

⚠ **一处探针时序缺陷（本轮修）**：`__apiLog` 是在**响应回来之后**才记一笔（要拿
`r.status`），而默认判定窗口只有 220ms ⇒ 同步等后端的 `run()` **时红时绿**
（服务热就绿、冷就红，同一份代码两种结论）。给
`run` / `agentPlan` / `triggerEvent` / `testModel` 一类慢控件放宽到 8s。
修后连跑两次**逐行一致**（250 / 0 / 5 / 8）。

### 一、按"能不能真的回退"分工，而不是一刀切加确认

危险操作要有两条腿：**事前确认**（说清后果）与**事后撤销**（点错了能回来）。
只有确认没有撤销 ⇒ 点快了只能认栽；只有撤销没有确认 ⇒ 容易误触。
本轮按"这个操作**能不能真的回退**"来分：

| 操作 | 二次确认 | 撤销 | 为什么这样分 |
|---|---|---|---|
| 删除菜谱 | 保留 `confirm()` | **新增**：官方菜走 `/restore`；自建菜用 `raw_*` 原文**重建** | 两者都能真的回来 |
| 恢复默认厨房 | **不加** | **新增**：把重置前的 `window._dev` 写回 `POST /api/devices` | 本身可逆，再加确认只是多一次点击 |
| 清空对话 | **新增**弹层 | **新增**：写回内存 + localStorage + 重绘 | 数据在本机，备份一份就能立刻撤 |
| 清除令牌 | **新增**弹层 | **新增**：把原值填回去再存一次 | 同上 |
| 清空历史 | 保留弹层 | **新增**：**延迟提交** 8 秒 | 后端没有"写回"端点，见下节 |

⚠ **两个操作刻意没加确认层**：`deleteRecipe` 与 `resetKitchen` 会被两个 UI 探针
**直接调用**（`ui_probe.mjs` 的「删除」与「恢复默认」用例），加确认会让它们红 ——
而且这两个操作本来就可撤销，撤销比确认更强。

### 二、清空历史：用"延迟提交"换撤销窗口

后端一删落盘文件就真回不来了（`/api/schedules` 没有"写回"端点），所以
"不新增后端接口、又能真撤销"的唯一做法是：**先给 8 秒窗口，到点再提交**。

- `doClearHist()`：**不调** `DELETE`，只备份 `HIST` → 清 UI → `setTimeout(commitClearHist, 8000)`。
- `undoClearHist()`：`clearTimeout` + 把备份放回 + **只重绘**（`renderHist()`）。
  ⚠ 撤销时**绝不能**去 `loadHist()` 重新拉 —— 后端还没清，拉回来的是旧列表，
  看着像"撤销失败"。
- `commitClearHist()`：8 秒到点才真的 `DELETE`；失败**如实说**并重拉一次。

代价：窗口内刷新页面 ⇒ 删除没生效，历史还在。这是**更安全**的方向
（宁可"没删掉"，也不要"删了回不来"）。

### 三、撤销条为什么必须 fixed

`.undo-bar` 走 `position:fixed` 底部**居中**，与 `.llm-toast` 同一条纪律：
排程页高度是三列 flex 算出来的，插一个**流内**元素进去会把甘特图挤到 35px
（见 MEMORY §五）。⚠ 底部**居中**而不是左下 —— 左下已经被 `.llm-toast`（降级提示）占了。

撤销回调**只保留最近一次**（新操作覆盖旧的）：多个撤销条叠在一起，
用户根本不知道该撤销哪一个。这是有意的取舍，不是漏了队列。

⚠ 撤销按钮必须显式写 `width:auto` + `color` + `box-shadow:none`：全局 `button` 是
`width:100%;color:#fff;box-shadow:橙色`，不覆盖会被撑成整行、字变白（在浅色条上看不见）。

| 项 | 改前 | 改后 |
|---|---|---|
| 未选中态 文字/底色 对比度 | `#fff` / `rgb(253,253,253)` = **1.02** ❌ | `#111` / `rgb(253,253,253)` = **18.53** ✅ |

hover 检查踩了两个"**检查自身失效**"的坑，都已封死：
`button` 上的 `transition:all .3s` 会让立刻读取的 `getComputedStyle` 拿到过渡起始值
（假通过，需 `sleep(500)`）；合成鼠标事件若不生效也会假通过（额外加一条
「hover 真的被触发」断言反查 `:hover`）。

这条纪律立刻抓到一处自己的假通过：`.vbtn` 的 `color` 断言原本写成子串
`"color:" in css`，而 `transition:...,color .2s ease` 与 `border-color:` 里都含
`color:`，于是"删掉 color 声明"的变异**不被捕获**（14/15）。收紧为声明级
`(?:^|;)color:` 后才真正守住。

### 后续追加：顶栏"穿模"（sticky 的流内位置 ≠ 渲染位置）

用户反馈：`智能排程界面的ui与其他站点不一致，上方的模块和导航栏穿模了`。

**根因（一个 CSS 语义坑）**：`.nav` 是 `position:sticky`，而 **`top` 只挪渲染位置、
不占文档流空间**。顶栏渲染在 `14..65`，但它在流里仍只占 `0..51` ⇒ 紧跟其后的
`#v-plan` 从 51 开始，**首行模块顶部 14px 永远压在顶栏底下**。

**为什么只有排程页明显**：`.view` 写的是 `padding-top:28px`，`28 > 14` **侥幸**躲开；
`#v-plan` 自己写 `padding:10px`，`10 < 14` ⇒ 被压 4px + 顶栏投影 = 用户看到的"穿模"。
也就是说这条 bug 靠"某个数字恰好比 14 大"来掩盖，**不是**结构性保证。

**修法（把"碰巧"改成结构保证）**：新增两个唯一真源变量，各断点只覆盖变量本身：

| 变量 | 作用 | 为什么必须同源 |
|---|---|---|
| `--nav-top:calc(14px + var(--sa-t))` | **同时**用在 `.nav` 的 `top` 与 `margin-top` | `margin-top` 让流内位置 = 渲染位置 ⇒ `--chrome`(= 顶栏下沿) 与文档流自洽，谁都不可能再被压住 |
| `--page-top-gap:14px` | **全站唯一**的顶部留白（`.view` 与 `#v-plan.active` 共用） | 排程页原来自己写 10px，是第二个真源；统一后"内容永远在顶栏之下"由结构保证 |

**A/B 取证（真 Edge，同一支探针）**：改动前在 **1088×557**（用户截图的视口，宽 >1024 但矮）：

```
[FAIL] 所有站点首行内容都在顶栏之下   home=-14 plan=-4 recipes=14 settings=14 history=14
[FAIL] 排程页首行模块不被顶栏盖住     首行顶=61 顶栏下沿=65
[FAIL] 所有视口…不被顶栏盖住          768×1024 / 1024×768 / 1084×570 / 1280×720
                                     / 1366×768 / 1440×900 / 1920×1080 / 2560×1440
```

即**每一个桌面视口都红**，只是排程页压得最狠 ⇒ 改动后同一视口 **117 / 0**。

**顺带修掉的同源缺陷（矮视口下三列仪表盘整体崩坏）**：仪表盘成立的前提是
「右列最小内容 606 + 顶栏 65 + 底部留白 78 + 顶部间距 14 都塞得进视口」= **视口高 ≳ 763px**。
再矮就**必然**同时出现：① 甘特图被压成 0（`1084×570` 实测）；② 右列溢出到悬浮球留白里
（球压住「生成排程」）；③ 内容把 `<body>` 顶高 ⇒ 出滚动条 + sticky 顶栏浮在内容上。
新增 `@media (min-width:1025px) and (max-height:760px)` **换布局档**：与平板/手机同策
解除"锁视口高度"，三列各拿自然高度、`#gantt` 保 300px 下限、滚动交给页面
（列数**不变**，宽度够仍三列）。阈值 760 是**算出来的**：763 是临界，1366×768 这类
常见笔记本仍留在仪表盘档（768 > 760）。

| 视口 | 改动前 | 改动后 |
|---|---|---|
| 1088×557（用户截图） | 14 项失败（`plan=-4` · `gantt=0` · `docH=667/557` · 球遮挡 `#kitchenResetBtn`） | **117 / 0**（矮桌面长页） |
| 1084×570 | 6 项失败（`gantt=0` · `docH=667/570` · 球遮挡 `#kitchenreset/preset`） | **117 / 0** |
| 1280×720 | 右列溢出 39px · 球压住「生成排程」 | **117 / 0** |
| 1440×900 | 穿模守卫红（首行顶 80 < 顶栏下沿 84） | **119 / 0**（`planFirstTop=79`，`chrome=65`） |
| 390×844 | 4 项失败（`home=-8 plan=0 recipes=8`） | **117 / 0** |

**顺带修掉**：`.float-panel` 写死 `height:520px`，矮视口下从 `top` 捅出视口
（底部锚点 + 固定高度 = 顶部溢出，用户连输入框都看不到）⇒ 改为
`min(520px, calc(100vh - …))`，900px 以上逐像素不变。

**方法论两条**：

1. **探针不能自己再抄一份断点阈值**。三档布局（桌面仪表盘 / 矮桌面长页 / 堆叠）的硬要求
   完全不同（一个要求"不出滚动条"、一个要求"容得下内容"），混用一定假失败。判定信号
   取**实测值** `#v-plan .grid3` 的 `align-items`（`stretch`=仪表盘、`start`=长页）——
   探针与源码各改一处会漂移，所以这个属性同时是"档位信号"。
2. **扫描表的空档就是真回归的藏身处**。原 `VP_LIST` 11 个视口里有 `1024×768` 和
   `844×390`、`667×375`，**恰好漏掉"宽 >1024 且高度不到 800"**（1280×720 / 1366×768 /
   窗口没最大化时的窄桌面）。本轮把它补到 **14 个**，上面那条崩坏才被看见。

新增 3 项静态护栏（`test_顶栏的流内位置必须等于它的_sticky_位置`、
`test_所有站点共用同一个顶部留白变量`、`test_矮桌面摆不下仪表盘时降级成长页`）与
**6 条**变异条目，全部被捕获。

## 后续追加：执行态回写 + 经验回流（v3.9，2026-10-08 第九轮）

对「作为一个菜谱排程 Agent 是否完整」的审视结论是：**排程那半边完整，Agent 那半边不完整**
—— 感知→决策→执行的回路只闭合了前半段。本轮补后半段。

### 一、缺口取证（不是印象，是 grep 出来的）

| # | 缺口 | 证据 |
|---|---|---|
| 1 | **无执行态回写** | 32 个路由里搜 `task/step/exec/tick/state/progress`，**0 命中**。系统排完、通知完就失明；重排只能靠用户在「动态事件」下拉里手动选 |
| 2 | **不从历史学习** | `app/scheduler/` + `app/agent/` 里搜 `schedules_user\|history`，**0 命中**。A1 落盘的历史只供看/比/还原，不回流决策 ⇒ 第 100 次排程与第 1 次一样从零算 |
| 3 | **在线决策面窄** | 9 个 Prompt 里 P1 语义先验 / P7 参数补全都是离线落盘、在线只读缓存；真在线的只有 P2/P3/P4/P5/P6。远程不可用时静默降级为「确定性求解器 + 模板通知」 |

两项是**串起来的**：历史里只有计划时长、没有实际时长 ⇒ **经验回流必须建立在执行态回写之上**，顺序不能倒。

### 二、设计取舍

| 决策 | 理由 |
|---|---|
| **只建议，不自动重排** | 自动换掉一份正在执行的方案，比不重排更破坏信任（与 v3.8 确认纪律同源） |
| **偏差取「最大单步超出」而非求和** | 并行分支上的延迟**不叠加**；求和会把"3 道菜各晚 1 分钟"判成晚 3 分钟 ⇒ 噪音重排。宁可低估（漏一次建议）也不要高估 |
| **不做"重排有没有收益"的预测** | 交给 `/reschedule` 已有的 `pareto` 字段实测汇报。预测错了比不预测更糟 |
| **报延迟必须填实际用时** | 编一个数喂进校准样本比没有样本更糟（后端同口径：不填按"准时"记，绝不记 0） |
| **重复上报先扣旧样本** | 同一步点 5 次「完成」只应是 1 个样本，否则一次手抖能带跑整档系数 |
| **前端打点放弹层，不加明细表列** | 加列会动 `table-layout:fixed` 的列宽分配，而 14 视口排版探针盯的就是这套几何 |

### 三、经验回流的四条硬纪律

1. **`FT_CALIB=off` 默认关。** 校准会改时长，而时长直接决定 (Γ, T) 权衡 —— 开档必须先跑 A/B 证明 **0 组更差**才敢留。关档时 `apply()` 第一行就返回原值，与旧行为**逐位一致**。
2. **只校准「原文没写时长」的步骤。** 原文写了"蒸 15 分钟"是事实，不是估计。
3. **系数 clamp 到 [0.5, 2.0] + 样本门限 5。** 单次异常值（切菜时接了个电话）不该把整个档位抬走。
4. **按和算比值**（`Σ实际 / Σ预估`），不是"比值再平均" —— 后者会让 1 分钟的步与 30 分钟的步等权。

实现上把 `estimate_duration` 拆成 `_base_estimate` 返回 `(值, 档位键)`，四处调用点
（engine×3 / model / cpsat / prep）**自动生效且签名不变**。蒸箱与烤箱刻意分成两个 bucket ——
都兜底 8 分钟但真实分布不同，合并会互相污染。

### 四、新增端点

| 端点 | 作用 |
|---|---|
| `POST /api/exec/report` | 回写一步执行态，返回完整执行态 + 偏差评估 |
| `GET /api/exec/{sid}` | 取执行态（没记录 ⇒ 空快照，不是 404 —— 还没开始执行是正常状态） |
| `POST /api/exec/suggest` | 偏差评估 + 重排建议，**只建议**；额外回 `completed` 供前端直接塞进 `/reschedule` |
| `DELETE /api/exec` | 清空执行态（不影响排程历史） |
| `GET /api/calib` | 经验回流快照：每个档位攒了多少样本、算出多少系数、**是否真的生效** |
